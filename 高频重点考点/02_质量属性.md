# 质量属性

> 重要程度：P0  
> 考纲定位：系统架构设计、架构评估、软件可靠性、安全架构等案例题的共同基础。

## 优先掌握

1. 能把题干中的业务诉求判定为正确的质量属性。
2. 能按“刺激源、刺激、环境、制品、响应、响应度量”写质量属性场景。
3. 能把质量属性映射到架构策略，而不是只写口号。
4. 能识别质量属性之间的权衡。

## 概念和场景

| 重要度 | 质量属性 | 概念解释 | 场景式解释 | 常用架构策略 |
| --- | --- | --- | --- | --- |
| P0 | 可用性 | 系统在需要时能持续提供服务 | 支付系统单节点故障后，用户仍能提交订单 | 冗余、健康检查、故障切换、限流降级 |
| P0 | 性能 | 在给定资源下满足响应时间和吞吐要求 | 秒杀开始后，请求响应需稳定在 200ms 内 | 缓存、异步、并行、索引、负载均衡 |
| P0 | 安全性 | 防止未授权访问、篡改和泄露 | 外部接口调用必须防伪造、防重放、防越权 | 认证、授权、加密、签名、审计 |
| P0 | 可修改性 | 需求变化时修改成本可控 | 新增支付渠道时，不应改动核心订单流程 | 分层、抽象接口、插件化、配置化 |
| P1 | 可靠性 | 在规定条件和时间内正确运行 | 交易消息不能丢失，失败后可恢复 | 持久化、重试、幂等、事务、补偿 |
| P1 | 可扩展性 | 能通过增加资源或节点支撑增长 | 用户量增长 10 倍时，服务可水平扩容 | 无状态化、分片、负载均衡、队列削峰 |
| P1 | 易用性 | 用户能高效、少出错地完成任务 | 业务人员录入数据时要减少重复填写 | 流程简化、默认值、校验、提示 |
| P2 | 可测试性 | 能方便地验证功能和质量 | 核心规则变更后能自动回归验证 | 模块解耦、接口隔离、日志、可观测性 |
| P2 | 可移植性 | 系统迁移到新环境的成本可控 | 从本地机房迁移到云环境 | 标准接口、容器化、环境隔离 |

## 质量属性场景写法

| 六要素 | 写法 | 示例 |
| --- | --- | --- |
| 刺激源 | 谁触发 | 用户、攻击者、运维人员、外部系统 |
| 刺激 | 发生什么 | 发起高并发请求、节点宕机、提交变更 |
| 环境 | 何种状态 | 正常运行、高峰期、故障恢复、升级窗口 |
| 制品 | 影响对象 | 服务、数据库、接口、配置、架构组件 |
| 响应 | 系统怎么反应 | 自动切换、拒绝非法请求、完成扩容 |
| 响应度量 | 用什么衡量 | 5 秒内恢复、99.9% 可用、错误率低于 0.1% |

## 答题落点

1. 先判属性：题干出现“不中断、故障恢复”优先看可用性；出现“响应时间、吞吐”优先看性能。
2. 再写机制：不要只答“提高可用性”，要写“主备部署 + 心跳检测 + 自动故障切换”。
3. 最后写度量：案例题给了数字就引用数字，没给数字就写可验证指标。

## 易混点

| 易混项 | 区分 |
| --- | --- |
| 可用性 vs 可靠性 | 可用性关注服务是否可用；可靠性关注运行过程中少出错、不丢数据。 |
| 性能 vs 可扩展性 | 性能看当前响应和吞吐；可扩展性看增长后能否通过扩容继续满足。 |
| 安全性 vs 可靠性 | 安全性防攻击和越权；可靠性防故障和错误。 |
| 可修改性 vs 可维护性 | 可修改性偏需求变化；可维护性还包括定位、修复、运维。 |

本章不展开具体产品参数、算法细节和厂商方案；这些内容只有在题干指定时才作为场景材料使用。
