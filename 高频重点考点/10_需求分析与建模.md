# 需求分析与建模

## 考试中一般怎么考

1. 需求分类：判断功能需求、非功能需求、约束和业务规则。
2. 需求工程过程：说明如何获取、分析、验证和管理需求。
3. 需求规格说明：判断 SRS 内容是否完整，需求是否可验证、无歧义。
4. UML 图：补充用例图、类图、顺序图、状态图、活动图中的缺失元素。
5. 数据建模：补充数据流图、ER 图、实体、关系、数据存储。
6. 变更影响：说明需求变化会影响哪些设计、接口、数据和测试内容。

## 针对考法梳理知识点

### 功能需求和非功能需求

功能需求描述系统要做什么，例如登录、下单、审批、导出报表。

非功能需求描述系统做得怎么样，例如响应时间、安全性、可靠性、可用性、可维护性。

考试判断时看句子重心：

- “系统支持数据导出”是功能需求。
- “数据导出 3 秒内完成”是非功能需求，属于性能。

### 约束和业务规则

约束是系统设计必须遵守的外部限制，例如必须使用国产数据库、必须兼容旧系统、必须满足某法规、必须三个月上线。

业务规则是业务本身的处理规则，例如审批金额超过 10 万需要二级审批，订单取消后库存释放。

约束影响设计空间，业务规则影响业务逻辑。

### 需求获取方法

需求获取是从用户、业务人员、现有系统和业务文档中发现需求。

常见方法：

| 方法 | 适用场景 |
| --- | --- |
| 访谈 | 了解关键用户、管理者、专家的真实诉求 |
| 问卷 | 用户数量多，需要收集共性意见 |
| 现场观察 | 用户说不清流程，适合观察实际操作 |
| 文档分析 | 旧系统、制度、表单、报表、接口文档较完整 |
| 原型法 | 用户需求模糊，需要通过界面或流程样例确认 |
| 头脑风暴 | 早期发散业务想法和潜在需求 |
| JRP / 联合需求计划 | 多方利益相关者集中讨论并达成一致 |

案例题中如果出现“用户说不清需求、需求反复变化”，可以答：访谈关键用户、现场观察业务流程、制作原型确认、组织评审并形成需求基线。

### 需求工程过程

需求工程不是只写需求文档，一般包括：

1. 需求获取：收集用户目标、业务流程、现有问题和约束。
2. 需求分析：整理、建模、消除冲突，区分功能需求、非功能需求和约束。
3. 需求规格说明：形成需求规格说明书 SRS，明确系统应满足的需求。
4. 需求验证：通过评审、原型、测试用例检查需求是否正确和可实现。
5. 需求管理：控制需求变更，维护需求基线和需求跟踪关系。

考试问“如何做好需求分析”时，不要只答“加强沟通”，要按获取、分析、规格说明、验证、管理的闭环回答。

### 需求规格说明书 SRS

SRS 用来明确系统要实现什么，是需求评审、设计、测试和验收的重要依据。

常见内容：

- 项目背景、目标和范围。
- 业务流程和业务规则。
- 功能需求。
- 非功能需求，例如性能、安全、可靠性、可用性、可维护性。
- 外部接口需求，例如用户接口、系统接口、硬件接口、通信接口。
- 数据需求，例如数据项、数据结构、数据存储、数据迁移。
- 运行环境和设计约束。
- 验收标准和优先级。

SRS 的重点是“可理解、可验证、可追踪”。不要把设计实现细节写成需求，除非题干明确它是外部约束。

### 需求质量和需求验证

好的需求应满足：

| 特征 | 含义 |
| --- | --- |
| 正确性 | 真实反映用户和业务需要 |
| 完整性 | 重要功能、数据、接口、异常和约束没有遗漏 |
| 一致性 | 不同需求之间没有冲突 |
| 无歧义性 | 表述清晰，不同人理解一致 |
| 可行性 | 技术、成本、进度上可以实现 |
| 可验证性 | 可以通过测试、评审或验收判断是否满足 |
| 可追踪性 | 能追踪到来源、设计、代码和测试 |

需求验证常用手段：

- 需求评审。
- 原型确认。
- 编写验收标准。
- 从需求推导测试用例。
- 检查需求之间是否冲突、重复或遗漏。

题干中如果有“高性能、界面友好、尽快完成”这类模糊表述，应改成可度量需求，例如“查询响应时间不超过 2 秒”“支持 500 个并发用户”。

### 用例图看系统边界

用例图关注谁使用系统、系统提供哪些功能。

答题时先找参与者，再找参与者和系统之间的目标。参与者可以是用户、管理员、外部系统。

常见错误是把系统内部模块画成参与者。参与者应该在系统边界外部。

### 类图看对象关系

类图关注系统中的对象结构，包括类、属性、方法和关系。

常考关系：

- 关联：一个对象知道另一个对象。
- 聚合：整体和部分关系，部分可独立存在。
- 组合：强整体和部分关系，部分生命周期依赖整体。
- 继承：子类继承父类。

### 顺序图看调用过程

顺序图关注对象之间按时间顺序发送消息。

适合描述登录、下单、支付、审批等流程。

答题时看清楚：谁先调用谁，返回什么结果，是否有条件分支或循环。

### 活动图看业务流程

活动图关注业务活动、分支、并发和流程走向，适合描述审批、下单、报销、物流等流程。

常见元素：

- 初始节点和终止节点。
- 活动。
- 判断和合并。
- 分叉和汇合。
- 泳道，用于表达不同角色或部门负责的活动。

考试补图时先按业务步骤排序，再补判断条件和泳道责任。

### 状态图看对象状态变化

状态图关注一个对象在生命周期中的状态变化，适合订单、工单、审批单、设备等有明显状态流转的对象。

答题要找：

- 初始状态。
- 触发事件。
- 状态迁移。
- 终止状态。

例子：订单可以从“待支付”变为“已支付”，再变为“已发货”或“已取消”。状态图不是描述多个对象调用过程，调用过程更适合顺序图。

### 组件图和部署图

组件图关注软件组件之间的依赖关系，例如 Web 前端、订单服务、支付服务、消息队列、数据库访问组件。

部署图关注软件制品部署到哪些硬件或运行节点上，例如浏览器、Web 服务器、应用服务器、数据库服务器、缓存服务器。

易混点：

| 图 | 关注点 |
| --- | --- |
| 组件图 | 软件结构和组件依赖 |
| 部署图 | 运行节点、网络连接和制品部署 |
| 类图 | 类、属性、方法和类之间关系 |
| 顺序图 | 对象之间按时间顺序交互 |

### 数据流图看数据如何流动

数据流图关注外部实体、处理、数据流和数据存储。

它不强调控制逻辑，而强调数据从哪里来、经过什么处理、存到哪里、输出到哪里。

常见错误是把数据流画成控制流，或者漏掉数据存储。

### DFD 分层和平衡原则

数据流图常按层次分解：

- 顶层图 / 上下文图：把整个系统看成一个加工，表达系统和外部实体之间的数据交换。
- 0 层图：把系统分解为几个主要加工，展示主要数据流和数据存储。
- 1 层图及以下：继续分解某个加工的内部处理。

分层 DFD 要遵守平衡原则：父图中某个加工的输入、输出数据流，在子图中也应保持一致，不能无故增加或丢失对外输入输出。

常考错误：

- 子图漏掉父图已有输入或输出。
- 把控制条件、处理顺序画成数据流。
- 加工只有输入没有输出，或只有输出没有输入。
- 数据存储直接和外部实体相连，中间缺少加工。

### 数据字典

数据字典是 DFD 的配套说明，用文字定义图中的数据流、数据存储、数据项和加工逻辑。

常见内容：

- 数据流：名称、来源、去向、组成、流量。
- 数据存储：名称、组成、存取方式。
- 数据项：名称、类型、长度、取值范围、含义。
- 加工逻辑：输入、处理规则、输出。

数据字典解决的是“图上名称太简略，具体含义不明确”的问题。

### 加工逻辑描述工具

DFD 中的加工如果逻辑复杂，可用以下工具描述：

| 工具 | 适用 |
| --- | --- |
| 结构化语言 | 顺序、选择、循环逻辑较清晰 |
| 判定表 | 多个条件组合决定多个动作 |
| 判定树 | 条件层次明显，适合树形分支 |

判定表特别适合“多个条件组合产生不同处理结果”的题，例如会员等级、订单金额、是否促销共同决定折扣。

### ER 图细化

ER 图关注实体、属性和联系，常用于概念数据建模。

常见元素：

- 实体：业务中需要管理的对象，例如用户、订单、商品。
- 属性：实体的特征，例如订单号、下单时间、金额。
- 主键：唯一标识实体实例的属性。
- 联系：实体之间的关系，例如用户下订单。
- 基数：`1:1`、`1:N`、`M:N`。

多对多联系通常要转换成关联实体或中间表。例如学生和课程是多对多，可引入选课关系，保存学生、课程、成绩、选课时间。

类图和 ER 图易混：

| 图 | 重点 |
| --- | --- |
| 类图 | 类、属性、方法、对象关系，偏面向对象分析设计 |
| ER 图 | 实体、属性、联系、主键外键，偏数据建模 |

### 需求变更影响分析

需求变化不只影响代码。应从以下角度分析：

- 需求文档是否更新。
- 架构和模块设计是否调整。
- 接口是否变化。
- 数据库表结构和数据迁移是否变化。
- 测试用例和回归范围是否变化。
- 部署配置和用户文档是否变化。

### 需求跟踪矩阵

需求跟踪矩阵用于维护需求和后续工作产品之间的对应关系。

常见追踪链路：

```text
业务目标 -> 用户需求 -> 软件需求 -> 设计 -> 代码 -> 测试用例 -> 验收结果
```

作用：

- 确认每个需求都有设计、实现和测试覆盖。
- 需求变更时快速定位受影响的模块、接口、数据和测试。
- 防止遗漏需求或实现无来源的功能。
- 支持验收和审计。

案例题问“如何保证需求变更后相关内容同步修改”，可以答：建立需求跟踪矩阵，维护双向追踪关系，并结合变更控制和回归测试。

### 用例关系细化

用例图常考 `include`、`extend` 和泛化。

| 关系 | 含义 | 判断 |
| --- | --- | --- |
| 包含 include | 一个用例必然复用另一个公共用例 | 下单必然包含身份校验 |
| 扩展 extend | 在特定条件下追加行为 | 支付失败时扩展为重新支付 |
| 泛化 | 子用例继承父用例能力 | 在线支付和线下支付都是支付 |

易错点：公共步骤用 include，可选或异常流程用 extend。

### 类图关系细化

| 关系 | 说明 | 例子 |
| --- | --- | --- |
| 关联 | 一个类知道或使用另一个类 | 订单关联用户 |
| 聚合 | 弱整体-部分，部分可独立存在 | 班级和学生 |
| 组合 | 强整体-部分，生命周期绑定 | 订单和订单明细 |
| 继承 | 子类继承父类属性和行为 | 会员用户继承用户 |
| 实现 | 类实现接口 | 支付服务实现支付接口 |
| 依赖 | 临时使用，通常作为参数或局部变量 | 订单服务依赖短信服务发送通知 |

组合比聚合更强。判断关键是部分对象是否能脱离整体独立存在。

### 类图多重度和可见性

类图补图时还常考多重度和可见性。

常见多重度：

| 多重度 | 含义 |
| --- | --- |
| `1` | 恰好一个 |
| `0..1` | 零个或一个 |
| `0..*` 或 `*` | 零个或多个 |
| `1..*` | 一个或多个 |
| `m..n` | 至少 m 个，最多 n 个 |

常见可见性：

| 符号 | 含义 |
| --- | --- |
| `+` | public，公开 |
| `-` | private，私有 |
| `#` | protected，受保护 |
| `~` | package，包内可见 |

判断多重度时看业务约束。例如“一个订单至少包含一个订单明细”，订单到订单明细通常是 `1..*`。

### 顺序图补图步骤

补顺序图时按这个顺序：

1. 找参与对象：用户、界面、控制器、服务、数据库、外部系统。
2. 按业务流程排列消息顺序。
3. 补同步调用、返回消息、条件分支和循环。
4. 检查每个消息是否有明确接收方。
5. 对外部系统调用补超时、失败或异常处理。

如果题干描述“用户提交订单后系统扣库存、创建订单、调用支付服务”，顺序图中不要漏掉库存服务、订单服务、支付服务之间的调用顺序。

### 状态图和活动图易混点

活动图描述流程，强调活动先后顺序和分支。

状态图描述对象状态，强调状态如何因事件发生迁移。

例子：

- “报销申请从提交到审批、打款、归档的流程”可画活动图。
- “报销单有草稿、待审批、已驳回、已通过、已打款状态”可画状态图。

### 建模题检查清单

- 用例图：参与者是否在系统边界外，系统内部模块不要画成参与者。
- 类图：多对多是否拆关联类或中间类。
- 顺序图：消息方向是否符合调用关系。
- 活动图：分支条件是否互斥且完整。
- 状态图：是否有触发事件和终止状态。
- 部署图：软件制品是否部署到具体节点上。
