# 高可用与性能优化

> 重要程度：P0  
> 考纲定位：质量属性、软件可靠性、系统架构设计和工程改进题的共同考点。

## 优先掌握

1. 性能优化要先定位瓶颈，再选手段。
2. 高可用要消除单点，设计故障检测、切换和恢复。
3. 容量、吞吐、响应时间、并发数、RTO、RPO 要会解释。
4. 限流、熔断、降级、隔离、异步、缓存、负载均衡要能落到场景。

## 概念和场景

| 重要度 | 内容 | 概念解释 | 场景式解释 |
| --- | --- | --- | --- |
| P0 | 响应时间 | 请求从发出到返回的耗时 | 用户查询订单 1 秒内看到结果 |
| P0 | 吞吐量 | 单位时间处理请求数量 | 支付系统每秒处理 2000 笔交易 |
| P0 | 负载均衡 | 把请求分发到多个节点 | Web 集群多实例共同承担读流量 |
| P0 | 冗余 | 用多个组件避免单点故障 | 两台应用服务器任一宕机不影响服务 |
| P0 | 故障切换 | 故障后自动切到可用节点 | 主库异常后提升从库为主库 |
| P0 | 缓存 | 减少重复计算和数据库访问 | 首页热点数据缓存到 Redis |
| P0 | 异步 | 非即时动作放到队列处理 | 下单成功后异步发送短信 |
| P1 | RTO | 故障后恢复服务的时间目标 | 容灾切换要求 30 分钟内恢复 |
| P1 | RPO | 可接受的数据丢失量 | 最多允许丢失 5 分钟数据 |
| P1 | 隔离 | 限制故障影响范围 | 报表查询和交易库隔离，避免拖慢下单 |

## 性能优化顺序

1. 明确指标：响应时间、吞吐量、并发数、资源利用率。
2. 定位瓶颈：前端、网络、应用、数据库、缓存、第三方接口。
3. 对症处理：缓存、索引、异步、批处理、连接池、负载均衡、水平扩展。
4. 验证效果：压测、监控、容量评估。
5. 说明副作用：一致性、复杂度、成本、运维压力。

## 高可用设计顺序

1. 找单点：应用、数据库、缓存、网关、消息队列、机房、网络。
2. 做冗余：主备、主从、集群、多机房。
3. 做检测：心跳、健康检查、监控告警。
4. 做切换：自动故障转移、流量摘除、回滚。
5. 做恢复：备份、容灾演练、数据校验。

## 易混点

| 易混项 | 区分 |
| --- | --- |
| 高可用 vs 容灾 | 高可用处理日常故障；容灾处理机房级或区域级灾难。 |
| 限流 vs 熔断 | 限流控制进入系统的流量；熔断阻断故障依赖。 |
| 水平扩展 vs 垂直扩展 | 水平扩展加节点；垂直扩展加单机资源。 |
| RTO vs RPO | RTO 看恢复时间；RPO 看数据丢失量。 |

## 边界

不展开具体压测工具和中间件参数；案例题重点是“瓶颈判断 + 架构措施 + 风险验证”。
