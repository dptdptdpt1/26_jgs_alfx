# 系统计划与方案评估

## 考试中一般怎么考

1. 可行性分析：要求从技术、经济、运行、法律、进度等角度判断项目是否可行。
2. 可研报告：问项目背景、建设必要性、候选方案、投资估算、风险和结论。
3. 方案比较：给多个技术方案，要求比较优缺点、风险和适用场景。
4. 建设模式：比较自研、外购、外包、SaaS 或云服务。
5. 新旧系统比较：问是否替换、改造、集成或渐进迁移。
6. 实施路线：问如何分阶段建设、试点推广、迁移切换和验收。
7. 资源复用：问如何利用已有软件、硬件、数据和接口，降低成本和风险。
8. 改进建议：根据现有系统问题提出架构、数据、性能、安全和运维改进。

## 针对考法梳理知识点

### 系统规划内容

系统规划回答“为什么建、建什么、怎么建、分几步建”。

常见内容：

- 现状分析：已有系统、业务流程、数据、接口、组织和运维现状。
- 问题诊断：性能、安全、数据孤岛、流程割裂、维护困难等问题。
- 业务目标：提升效率、支撑监管、降低成本、支撑业务扩展。
- 建设范围：明确做什么、不做什么，避免范围失控。
- 总体方案：应用、数据、技术、安全和运维总体设计。
- 实施路线：阶段划分、试点、推广、迁移、验收和运维交接。
- 投资估算：建设成本、运维成本和收益预估。
- 风险分析：技术、进度、数据、集成、安全、供应商和用户接受度。

规划题不要只列技术方案，要先从业务目标和现状问题出发。

### 必要性和可行性

必要性回答“为什么要做”，可行性回答“能不能做、值不值得做”。

| 判断 | 关注点 | 例子 |
| --- | --- | --- |
| 必要性 | 业务痛点、政策要求、效率问题、风险问题 | 旧系统无法满足监管报送，必须建设 |
| 可行性 | 技术、经济、运行、合规、进度是否可行 | 技术成熟、预算充足、组织能配合 |

案例题中如果问“是否有必要建设”，要写业务驱动和问题后果；如果问“是否可行”，要按可行性维度评估。

### 可行性分析

| 角度 | 看什么 |
| --- | --- |
| 技术可行性 | 技术成熟度、团队能力、系统复杂度、集成难度 |
| 经济可行性 | 建设成本、运维成本、收益、投资回收期 |
| 运行可行性 | 组织流程、用户接受度、培训和运维能力 |
| 法律合规 | 数据安全、隐私、知识产权、行业监管 |
| 进度可行性 | 工期、资源、关键依赖、交付风险 |

答题不要只写“可行”。要指出可行的依据和主要风险。

### 可行性研究报告

可行性研究报告通常包括：

- 项目背景和建设必要性。
- 现状问题和需求分析。
- 建设目标和建设范围。
- 候选方案和技术路线。
- 技术、经济、运行、合规、进度可行性分析。
- 投资估算和资金来源。
- 组织实施计划和进度安排。
- 风险分析和应对措施。
- 结论和建议。

可研报告的结论不能只写“建议建设”。应说明推荐方案、主要依据、关键风险和配套措施。

### 约束条件

方案评估必须考虑约束，否则方案可能理论上好但落不了地。

常见约束：

- 预算上限。
- 工期和上线窗口。
- 政策法规和安全合规。
- 现有系统和接口限制。
- 数据迁移和历史数据质量。
- 团队能力和运维能力。
- 技术标准和国产化要求。
- 厂商锁定和迁移成本。

约束条件会影响方案选择。例如预算有限且需求标准化，可以优先外购或 SaaS；安全合规要求高、数据敏感，则要谨慎选择公有云或外部托管。

### 方案比较

方案题建议按同一维度比较：

- 功能满足度。
- 性能、可用性、安全性、可扩展性。
- 技术成熟度和团队掌握程度。
- 与现有系统集成难度。
- 建设成本和运维成本。
- 迁移风险和回滚能力。

如果题目要求“推荐方案”，要先说明业务目标，再说明为什么该方案更匹配目标。

### 方案评估指标体系

方案评估要用同一组指标比较，避免只说某方案“先进”。

| 指标 | 看什么 |
| --- | --- |
| 功能满足度 | 是否覆盖核心业务需求和未来扩展 |
| 质量属性 | 性能、可用性、安全性、可扩展性、可维护性 |
| 技术成熟度 | 技术是否成熟，团队是否掌握 |
| 兼容集成 | 是否容易接入现有系统、数据和接口 |
| 成本 | 建设、采购、运维、培训和迁移成本 |
| 风险 | 技术、进度、供应商、数据、安全和变更风险 |
| 实施周期 | 是否满足上线时间和阶段目标 |
| 厂商支持 | 产品路线、服务能力、SLA、案例和生态 |
| 合规性 | 数据安全、隐私、审计、行业监管和标准要求 |

如果某方案某项风险很高，即使总成本低，也不能直接推荐。

### 加权评分法

多方案比较时可使用加权评分法。

基本步骤：

1. 选定评价指标，例如功能、性能、安全、成本、风险、实施周期。
2. 为每个指标设置权重，权重反映业务重要性。
3. 对每个方案按指标打分。
4. 计算加权总分。
5. 结合关键风险和约束条件给出推荐。

注意：加权评分不是机械选最高分。若最高分方案存在不可接受的合规、数据安全或交付风险，应调整或否决。

### 建设模式选择

| 模式 | 优点 | 局限 | 适用 |
| --- | --- | --- | --- |
| 自研 | 贴合业务、可控性强、可持续演进 | 成本高、周期长、依赖团队能力 | 核心业务、差异化能力 |
| 外购产品 | 成熟稳定、上线较快、厂商支持 | 定制受限、可能厂商锁定 | 标准化管理系统 |
| 外包开发 | 缓解人力不足，可按需建设 | 质量和进度依赖供应商，知识沉淀弱 | 非核心或阶段性项目 |
| SaaS | 上线快、运维少、按需付费 | 定制弱、数据和合规需评估 | 标准化、轻量化业务 |
| 云服务 / PaaS | 弹性好、运维成本低 | 厂商绑定和迁移成本 | 需要快速扩展和托管能力 |

选型要看业务核心程度、定制需求、上线周期、预算、数据安全和组织能力。

### 供应商评估

涉及采购、外包或 SaaS 时，要评估供应商。

常见维度：

- 厂商资质和行业案例。
- 产品成熟度和功能匹配度。
- 技术架构、开放接口和可扩展能力。
- 安全合规、数据保护和审计能力。
- 实施团队能力和交付计划。
- 售后服务、SLA 和故障响应。
- 价格、授权模式和后续运维费用。
- 源码、文档、培训和知识转移。

供应商方案不能只看报价。低报价如果带来交付、质量、数据安全或锁定风险，整体成本可能更高。

### 新旧系统处理策略

| 策略 | 适合场景 | 风险 |
| --- | --- | --- |
| 直接替换 | 旧系统价值低、数据简单、停机窗口允许 | 切换风险高 |
| 渐进迁移 | 业务复杂、停机成本高、需要平滑过渡 | 双系统并行复杂 |
| 外围扩展 | 核心旧系统稳定但扩展困难 | 旧系统仍是瓶颈 |
| 集成保留 | 旧系统仍承载关键能力 | 接口治理和数据一致性复杂 |

常见答题点：先保留关键业务连续性，再逐步迁移低风险模块，最后迁移核心模块。

### 数据迁移和新旧切换

新旧系统切换是方案评估中的高风险点。

常见做法：

- 迁移前做数据清洗、去重、字段映射和编码转换。
- 先全量迁移历史数据，再做增量同步。
- 迁移后做行数、金额、状态、抽样和业务对账。
- 对关键业务采用新旧系统并行或灰度切流。
- 保留旧系统和数据备份，准备回滚预案。
- 明确切换窗口、冻结策略和责任人。

只写“导入旧数据”不够。要写校验、对账、增量同步、灰度切换和回滚。

### 现有资源利用

可复用资源：

- 硬件资源：服务器、网络、存储、机房、云资源。
- 软件资源：已有业务系统、中间件、统一认证、报表平台。
- 数据资源：历史数据、主数据、指标口径。
- 接口资源：已有服务接口、消息通道、数据交换平台。
- 运维资源：监控、日志、发布流水线、备份体系。

易错点：复用不是无条件复用。旧资源如果性能不足、安全不达标或接口不可治理，应改造后再接入。

### 成本收益分析

成本包括：

- 一次性建设成本。
- 软硬件和云资源成本。
- 数据迁移和接口改造成本。
- 培训、运维和安全合规成本。

收益包括：

- 提升处理效率。
- 降低人工成本和故障损失。
- 改善用户体验。
- 支撑业务扩展和监管要求。

### TCO 和 ROI

TCO 是总拥有成本，不只包括采购价。

TCO 常见内容：

- 软硬件、云资源和许可证成本。
- 实施、开发、集成和数据迁移成本。
- 培训、推广和组织变革成本。
- 运维、监控、备份、安全合规成本。
- 升级、扩容、续费和技术支持成本。
- 退出、替换和数据迁出成本。

ROI 关注投入产出。收益可以包括效率提升、人工成本降低、故障损失减少、收入增长、合规风险降低。

考试中如果比较方案成本，不能只看一次性采购成本，要看全生命周期成本和风险调整后的收益。

### 实施路线图

实施路线要体现阶段性和风险控制。

常见阶段：

1. 现状调研和需求确认。
2. 总体方案设计和技术验证。
3. 原型或试点建设。
4. 核心功能开发和集成联调。
5. 数据迁移和用户培训。
6. 试运行和问题整改。
7. 正式上线和验收。
8. 运维交接和持续优化。

大型系统不宜一次性大爆炸上线。分阶段、试点、灰度和回滚可以降低实施风险。

### 试点先行

试点用于在小范围验证方案可行性。

试点对象选择原则：

- 范围可控，风险较低。
- 业务有代表性，能暴露关键问题。
- 用户配合度较高。
- 数据和接口复杂度适中。
- 出问题时影响可控。

试点后应总结功能、性能、用户体验、数据质量、运维和培训问题，再优化方案并推广。

### 验收标准

验收标准应在方案和合同阶段明确。

常见验收内容：

| 验收 | 关注 |
| --- | --- |
| 功能验收 | 是否满足需求规格和业务流程 |
| 性能验收 | 响应时间、吞吐量、并发数、资源利用率 |
| 安全验收 | 认证授权、漏洞扫描、日志审计、数据保护 |
| 数据验收 | 迁移完整性、准确性、对账结果 |
| 集成验收 | 接口、消息、数据同步和异常处理 |
| 文档验收 | 需求、设计、接口、运维、用户手册 |
| 运维交接 | 监控、告警、备份、恢复、应急预案 |

验收标准要可度量。只写“系统运行稳定、性能良好”不够。

### 风险评估和应对

方案评估要配套风险分析。

| 风险 | 应对 |
| --- | --- |
| 需求不清或频繁变化 | 原型确认、需求评审、范围控制和变更流程 |
| 技术不成熟 | 技术预研、POC、备选方案 |
| 进度紧张 | 分阶段交付、优先核心功能、增加资源 |
| 数据迁移失败 | 清洗校验、全量加增量、对账、回滚 |
| 系统集成复杂 | 接口标准、联调计划、Mock、监控 |
| 用户接受度低 | 培训、试点、反馈迭代、流程优化 |
| 安全合规风险 | 等保、隐私保护、审计、数据分级分类 |
| 供应商依赖 | SLA、源码/文档交付、知识转移、退出条款 |

### 方案评估答题模板

```text
先明确业务目标和约束，再从技术、经济、运行、合规、进度维度评估方案；比较各方案在质量属性、集成难度、成本和风险上的差异；优先选择满足核心目标且风险可控的方案；对迁移、数据一致性、安全合规和回滚制定配套措施。
```
