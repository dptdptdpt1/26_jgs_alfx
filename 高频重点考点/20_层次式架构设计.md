# 层次式架构设计

## 考试中一般怎么考

1. 分层识别：要求指出表现层、业务层、数据访问层、数据层的职责。
2. 层间依赖：判断是否存在跨层调用、职责混乱、耦合过高。
3. 层次改造：给单体系统或混乱模块，要求按层拆分并说明好处。
4. 表现层设计：问多终端、前后端分离、用户体验和安全控制。
5. 数据访问层设计：问如何封装数据库访问、事务、缓存和数据源切换。
6. 分层反模式：问表现层写业务、跨层访问、循环依赖、数据模型暴露等问题。

## 针对考法梳理知识点

### 典型分层

| 层次 | 职责 |
| --- | --- |
| 表现层 | 页面展示、交互、输入校验、调用后端接口 |
| 接口层 | 对外 API、参数校验、鉴权、协议适配 |
| 业务层 | 业务规则、流程编排、事务边界 |
| 数据访问层 | 封装数据库、缓存、搜索、外部数据访问 |
| 数据层 | 数据库存储、索引、备份、主从、分区 |

分层的核心价值是职责分离、降低耦合、便于维护和替换。

### 二层、三层和四层

| 架构 | 典型结构 | 特点 |
| --- | --- | --- |
| 二层 C/S | 客户端 + 数据库或服务器 | 简单直接，但客户端维护和升级成本高 |
| 三层 | 表现层 + 业务层 + 数据层 | 职责较清晰，企业应用常见 |
| 四层或多层 | 表现层 + 接口层 + 业务层 + 数据访问层 + 数据层 | 适合复杂系统和前后端分离 |

层数不是越多越好。简单系统过度分层会增加调用和理解成本。

### 层间依赖规则

常见规则：

- 上层可以调用下层，下层不应依赖上层。
- 表现层不直接访问数据库。
- 业务规则不应散落在页面、SQL 或存储过程中。
- 数据访问层不应包含复杂业务流程。
- 跨层调用要通过明确接口。

易错点：分层不是简单建几个包。关键看职责是否清楚、依赖方向是否稳定。

### 严格分层和松散分层

| 类型 | 规则 | 优缺点 |
| --- | --- | --- |
| 严格分层 | 只能调用下一层 | 依赖清晰，但有时调用链较长 |
| 松散分层 | 可以跳过中间层调用更下层 | 灵活，但容易破坏边界 |

考试中如果题干出现“表现层直接访问数据库”“业务层直接操作页面对象”，通常是在考分层依赖违规。

### 表现层设计

表现层常考点：

- B/S 便于部署升级，C/S 适合本地能力和复杂交互要求高的场景。
- 前后端分离通过 API 解耦界面和后端服务。
- 多终端适配要考虑响应式、接口复用和权限一致。
- 前端校验只能提升体验，不能替代后端校验。

### MVC、MVP、MVVM

| 模式 | 核心 |
| --- | --- |
| MVC | Model 负责数据和业务状态，View 展示，Controller 处理请求 |
| MVP | Presenter 负责协调 View 和 Model，View 更被动 |
| MVVM | ViewModel 暴露状态和命令，适合数据绑定 |

这些模式主要解决表现层内部职责分离问题，不等于整个系统分层架构。

### 接口层设计

接口层负责隔离外部调用和内部业务。

常见措施：

- 统一认证、授权、限流、审计。
- 参数校验和错误码规范。
- API 版本管理，避免接口变更影响调用方。
- 对外协议和内部模型隔离，避免内部结构直接暴露。

### 业务层设计

业务层承担核心规则和流程编排。

常见答题点：

- 业务规则集中在业务层，避免散落。
- 事务边界通常放在业务服务方法。
- 复杂流程可用状态机、工作流或领域服务组织。
- 对外部服务调用要设置超时、重试和补偿。

### 应用层和领域层

复杂业务系统中，业务层还可细分为应用层和领域层。

| 层次 | 职责 |
| --- | --- |
| 应用层 | 编排用例流程、调用领域对象、控制事务和权限 |
| 领域层 | 承载核心业务规则、领域模型和状态变化 |

应用层回答“这个用例怎么走流程”，领域层回答“业务规则本身是什么”。不要把核心业务规则全部写在控制器或脚本流程里。

### 数据访问层设计

数据访问层用于隔离数据存储细节。

常见措施：

- 封装 SQL、ORM、缓存和搜索访问。
- 统一处理连接、事务、分页、异常。
- 支持读写分离和多数据源。
- 隐藏数据库表结构变化，降低上层影响。

易错点：数据访问层不是业务层。不要在 DAO 里写审批、支付、库存扣减等业务流程。

### DTO、VO、DO 模型隔离

分层系统中常用不同对象隔离层间模型。

| 模型 | 作用 |
| --- | --- |
| VO | 面向页面展示或接口返回 |
| DTO | 层间或服务间传输数据 |
| DO / Entity | 对应数据库表或领域实体 |

不要把数据库表结构直接暴露给前端或外部系统。接口模型稳定性应高于内部数据模型。

### 数据层设计

数据层关注数据持久化和性能可靠性。

常见答题点：

- 按业务访问模式设计表、索引、分区。
- 通过备份、主从、容灾保证可靠性。
- 通过冷热分离、归档控制数据量。
- 对敏感数据加密、脱敏和审计。

### 分层和微服务

分层架构是单个应用或服务内部的组织方式，微服务是系统级的服务拆分方式。

一个微服务内部也可以采用表现层、接口层、业务层、数据访问层。不能因为采用微服务就不需要内部职责分离。

### 分层反模式

| 问题 | 后果 | 改进 |
| --- | --- | --- |
| 表现层写业务规则 | 业务重复、难测试 | 规则下沉到业务层 |
| SQL 或存储过程承载复杂业务 | 难维护、难迁移 | 业务层集中规则 |
| 表现层直连数据库 | 安全和耦合风险 | 通过接口层和业务层访问 |
| 跨层随意调用 | 依赖混乱 | 统一层间接口 |
| 下层依赖上层 | 循环依赖 | 依赖倒置或抽象接口 |
| 数据模型直接暴露接口 | 内部变化影响外部 | 使用 DTO/VO 隔离 |

### 层次式架构答题模板

```text
将系统划分为表现层、接口层、业务层、数据访问层和数据层；表现层负责交互和展示，接口层负责鉴权、校验和协议适配，业务层集中业务规则和事务，数据访问层封装数据库和缓存访问，数据层负责存储、索引、备份和安全。通过明确层间依赖，避免表现层直连数据库和业务规则散落，提高可维护性、可测试性和可扩展性。
```
