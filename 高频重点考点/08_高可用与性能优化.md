# 高可用与性能优化

## 考试中一般怎么考

1. 性能瓶颈分析：根据访问慢、并发高、数据库压力大等描述定位瓶颈。
2. 扩展机制：问缓存、异步、负载均衡、水平扩展分别如何起作用。
3. 高可用机制：问集群、主备、故障检测、故障转移、容灾恢复的原理。
4. 稳定性治理：问限流、熔断、降级、隔离如何防止故障扩散。

## 针对考法梳理知识点

### 性能优化先定位瓶颈

性能问题不能直接堆技术名。先判断瓶颈在哪一层：

- 接入层：带宽、静态资源、TLS、负载均衡。
- 应用层：线程池、同步调用、锁竞争、代码逻辑。
- 缓存层：命中率、热点 Key、缓存失效。
- 数据库层：慢 SQL、索引、锁、连接数、IO。
- 外部系统：第三方接口慢、调用链过长。

定位后再选择措施，否则答案会显得空。

### 缓存为什么能提升性能

缓存把热点数据放到更快的位置，减少重复计算和数据库访问。

它适合读多写少、热点明显、允许短暂不一致的场景。

它的代价是缓存一致性、缓存穿透、击穿、雪崩和缓存容量管理。

缓存可以放在多个层次：

| 层次 | 例子 |
| --- | --- |
| 浏览器缓存 | 静态资源缓存 |
| CDN 缓存 | 图片、JS、CSS |
| 网关缓存 | 接口结果缓存 |
| 应用本地缓存 | Caffeine、Guava Cache |
| 分布式缓存 | Redis、Memcached |
| 数据库缓存 | Buffer Pool |

CDN 加速：将图片、视频、CSS、JS 等静态资源部署到 CDN，通过就近访问降低网络延迟。适合全国用户访问、大文件下载、静态资源加载慢的场景。

### 异步为什么能提升吞吐

异步处理把非实时任务从主流程中拆出去。主流程只完成必要操作，然后把任务放入消息队列，由后台消费者慢慢处理。

它适合短信通知、日志、积分、报表、图片处理等非强实时任务。

它的代价是处理结果有延迟，还要考虑消息可靠性、重复消费和失败补偿。

### 负载均衡和水平扩展

水平扩展要求应用尽量无状态。用户请求不依赖某一台固定服务器，才能把请求分散到多个实例。

负载均衡负责把请求分发到多个节点，并通过健康检查摘除异常节点。

如果应用有本地会话状态，需要把 Session 放到 Redis 等共享存储，或使用无状态 Token。

### 高可用机制

高可用的核心链路是：

1. 冗余部署，避免单点。
2. 健康检查，发现故障。
3. 故障转移，切到可用节点。
4. 数据复制或备份，保证恢复后数据可用。
5. 监控告警，通知运维处理。

只写”集群部署”不够，还要说明如何发现故障、如何切换、数据如何恢复。

### 单点故障

案例里经常描述”系统部署在一台服务器上，一旦宕机业务全部中断”。核心思路是消除单点故障：Web 服务、应用服务、数据库、缓存等关键组件都要多节点部署，通过负载均衡和健康检查实现故障自动摘除。

### 主备、主从、双活、多活

| 架构 | 特点 |
| --- | --- |
| 主备 | 主节点工作，备节点等待接管，切换有短暂中断 |
| 主从 | 主节点写，从节点读，提升读性能和数据副本 |
| 双活 | 两个节点同时对外提供服务，互为备份 |
| 多活 | 多个机房/区域同时提供服务，任一故障不影响全局 |

案例中如果说”主机房故障导致业务不可用”，可答同城双活、异地多活、两地三中心，并配合数据同步、容灾切换和灾备演练。

### 限流、熔断、降级、隔离

限流控制进入系统的请求量，防止超过系统承载能力。

熔断在下游持续失败时快速失败，避免调用方资源被拖垮。

降级关闭非核心能力，保留核心业务。

隔离把资源分开，例如线程池隔离、服务隔离、数据库隔离，避免一个模块耗尽所有资源。

### 超时与重试

分布式调用必须设置超时，否则调用方可能长期等待，线程和连接资源被耗尽。重试可提高临时故障下的成功率，但必须控制次数，使用指数退避避免重试风暴，且重试接口必须幂等。

答法：服务间调用应设置超时时间和有限重试机制，避免请求长时间阻塞；重试应结合退避策略，防止重试风暴。

### 健康检查与自动恢复

通过心跳检测、健康检查及时发现异常节点，由负载均衡或注册中心将其摘除，待恢复后重新加入集群。配合自动重启、自动扩容和监控告警，保证系统自愈能力。

### 性能优化答题模板

性能题按“定位瓶颈 -> 分层优化 -> 验证效果”答。

```text
先通过日志、监控、链路追踪和压测定位瓶颈；如果瓶颈在数据库，优化 SQL、索引、分页和读写分离；如果瓶颈在应用层，优化线程池、锁竞争和同步调用；如果瓶颈在外部调用，设置超时、重试、熔断并异步化；最后通过压测验证响应时间、吞吐量和资源利用率。
```

这样比直接列“缓存、负载均衡、分库分表”更贴近案例分析。

### 容量指标

性能和高可用题常需要写指标：

- QPS/TPS：每秒查询或事务数。
- 响应时间：平均值、95 分位、99 分位。
- 并发用户数：同时发起请求的用户规模。
- CPU、内存、磁盘 IO、网络带宽。
- 连接池、线程池、队列长度。
- 错误率、超时率、重试次数。

如果题目给出“访问慢”，可以建议增加监控，采集这些指标定位瓶颈。

### 削峰填谷

削峰填谷是把瞬时高峰流量先写入队列，后端消费者按处理能力逐步消费。

适用场景：

- 秒杀下单。
- 批量导入。
- 日志采集。
- 短信、邮件、通知。

限制：

- 用户不能立即得到最终处理结果。
- 队列积压需要监控和扩容。
- 消费失败需要重试、死信和补偿。

### 容灾指标 RTO 和 RPO

RTO 是恢复时间目标，表示故障后多久恢复服务。

RPO 是恢复点目标，表示最多允许丢失多长时间的数据。

例子：

- RTO 10 分钟：系统故障后 10 分钟内恢复。
- RPO 5 分钟：最多丢失最近 5 分钟的数据。

高可用偏“不中断或少中断”，容灾偏“灾难发生后可恢复”。答异地容灾时要写数据复制、备份、演练、切换流程和 RTO/RPO。

### 降级设计怎么写

降级不是随便关功能，要区分核心链路和非核心链路。

常见做法：

- 保留登录、查询、下单、支付等核心能力。
- 关闭推荐、排行榜、评论、报表、个性化等非核心能力。
- 返回兜底数据或静态页面。
- 降低刷新频率或减少返回字段。
- 通过开关平台动态开启或关闭降级策略。

答题时可写：先定义降级预案和开关，高峰或故障时保护核心交易链路，事后恢复非核心功能。

### 批处理与合并请求

频繁访问数据库、循环单条插入、接口频繁调用都会导致性能问题。优化思路：批量查询、批量插入、合并请求、减少 RPC 调用次数、减少数据库连接次数。

### 数据库性能优化快速参考

| 瓶颈 | 优化措施 |
| --- | --- |
| 慢 SQL | EXPLAIN 分析、避免 select *、减少大 Join |
| 索引 | 建立联合索引、覆盖索引、避免索引失效 |
| 读压力大 | 读写分离、主从复制 |
| 写压力大 | 分库分表、批量写入、异步落库 |
| 单表数据量大 | 水平分表、历史数据归档 |
| 连接不足 | 连接池复用 |

### 前端性能优化

页面打开慢不要只答后端，还要答前端：静态资源压缩合并、图片压缩和懒加载、CDN 分发、浏览器缓存、减少 HTTP 请求、首屏优化、异步加载 JS/CSS。

### 连接池与线程池

使用连接池复用数据库、缓存和 HTTP 连接，减少连接创建和释放开销。线程池需合理配置核心线程数、最大线程数、队列长度和拒绝策略，避免线程过多导致上下文切换。

### 热点数据优化

对热门商品、热点排行榜等高频访问数据：缓存预热、本地缓存 + 分布式缓存多级方案、热点 Key 拆分、异步刷新、限流保护。

### 水平扩展与垂直扩展

| 方式 | 含义 |
| --- | --- |
| 垂直扩展 | 提升单机配置，如加 CPU、内存 |
| 水平扩展 | 增加服务器节点，配合负载均衡 |

优先采用水平扩展，通过增加应用节点提升系统吞吐能力。

### 综合场景答题模板

**场景 1：系统访问量暴增，响应慢**

1. 前端静态资源上 CDN
2. 接入层增加负载均衡
3. 应用服务水平扩展
4. 热点数据使用 Redis 缓存
5. 数据库读写分离
6. 慢 SQL 和索引优化
7. 非核心流程 MQ 异步化
8. 高频接口限流降级
9. 增加监控告警和容量评估

**场景 2：数据库成为瓶颈**

1. SQL 优化、建立合理索引
2. 引入缓存
3. 读写分离
4. 分库分表
5. 历史数据归档
6. 批量写入、避免大事务
7. 使用连接池

**场景 3：服务经常不可用**

1. 应用集群部署、负载均衡
2. 健康检查、故障自动摘除
3. 限流、熔断、降级
4. 主备切换
5. 数据备份和容灾
6. 监控告警、自动扩容
7. 灰度发布和回滚机制

**场景 4：秒杀系统设计**

1. 静态页面 CDN
2. 秒杀接口限流、防刷验证码
3. Redis 预扣库存（Lua 脚本原子操作）
4. MQ 异步创建订单
5. 防重复提交（唯一索引、幂等）
6. 数据库最终落库
7. 超卖控制、服务降级、监控告警

### 常见问法与万能答题模板

**如何提高系统可用性？**

> 从消除单点故障、集群部署、负载均衡、主备切换、容灾备份、限流熔断降级、监控告警等方面提高系统可用性。

**如何提高系统性能？**

> 从缓存、CDN、SQL 优化、索引优化、读写分离、分库分表、异步处理、批量处理、连接池、水平扩展等方面提升系统性能。

**如何应对高并发？**

> 前端使用 CDN 和缓存降低请求压力；接入层使用负载均衡；应用层水平扩展；热点数据放入 Redis；数据库采用读写分离和分库分表；非核心流程通过 MQ 异步处理；同时增加限流、熔断、降级和监控告警机制。

**如何避免系统雪崩？**

> 通过限流控制入口流量，通过熔断隔离故障服务，通过降级保障核心功能，通过超时和重试机制避免请求堆积，并配合监控告警及时发现异常。

### 背诵版答案

> 为提高系统高可用性，应避免单点故障，对 Web 层、应用层、数据库、缓存等关键组件进行集群化部署，通过负载均衡、健康检查、故障自动摘除和主备切换保证服务连续性。同时，应建立监控告警、容灾备份和应急恢复机制，控制 RTO 和 RPO。
>
> 为提高系统性能，应从前端、应用、缓存、数据库和架构多个层面优化。前端可采用 CDN、资源压缩和浏览器缓存；应用层可采用异步处理、批量处理、连接池和线程池优化；缓存层可使用 Redis 缓存热点数据，避免缓存穿透、击穿和雪崩；数据库层可进行 SQL 优化、索引优化、读写分离和分库分表；在高并发场景下，还应增加限流、熔断、降级和消息队列削峰填谷机制。

### 关键词清单与记忆口诀

**高可用关键词：** 集群部署、负载均衡、健康检查、故障自动摘除、主备切换、容灾备份、两地三中心、同城双活、限流、熔断、降级、监控告警、灰度发布、快速回滚、RTO、RPO

**性能优化关键词：** CDN、浏览器缓存、Redis 缓存、多级缓存、SQL 优化、索引优化、读写分离、分库分表、消息队列、异步处理、削峰填谷、批量处理、连接池、线程池、水平扩展、热点数据缓存、慢 SQL 分析

**记忆口诀：**

> 高可用：集群负载防单点，限熔降级保核心，备份容灾控 RTO/RPO。
> 高性能：缓存索引先优化，读写分离分库表，异步削峰加 CDN。

案例分析里关键是别只写一个点，要从前端、接入层、应用层、缓存层、数据库层、运维保障多层次回答。
