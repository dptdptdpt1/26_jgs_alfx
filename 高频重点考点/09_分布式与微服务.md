# 分布式与微服务

> 重要程度：P0  
> 考纲定位：系统架构设计、服务化、应用支撑技术和架构演化的高频背景。

## 优先掌握

1. 微服务拆分原则和代价。
2. 服务注册发现、网关、配置中心、链路追踪。
3. 超时、重试、幂等、熔断、降级、限流。
4. 分布式一致性：2PC、TCC、Saga、最终一致。

## 概念和场景

| 重要度 | 内容 | 概念解释 | 场景式解释 |
| --- | --- | --- | --- |
| P0 | 微服务 | 按业务能力拆分、独立部署和治理 | 订单、库存、支付可独立扩容和发布 |
| P0 | 服务注册发现 | 服务实例动态上下线后仍可被调用 | 新增订单服务实例后，调用方自动发现 |
| P0 | API 网关 | 统一入口处理路由、安全、限流 | App 只访问网关，由网关转发到后端服务 |
| P0 | 熔断 | 下游持续失败时快速失败 | 支付服务故障时暂时阻断调用，避免拖垮订单服务 |
| P0 | 降级 | 牺牲非核心功能保核心链路 | 大促时关闭个性化推荐，保证下单支付 |
| P0 | 幂等 | 多次执行效果与一次相同 | 支付回调重复到达，不应重复发货 |
| P1 | 链路追踪 | 跟踪一次请求跨服务的调用路径 | 定位订单查询慢是卡在库存服务还是数据库 |
| P1 | 分布式事务 | 跨服务数据变更的一致性方案 | 下单同时扣库存和创建支付单 |
| P1 | 配置中心 | 统一管理配置并支持动态变更 | 灰度调整限流阈值，不重新发版 |

## 微服务拆分规则

1. 先按业务能力和领域边界拆，不按技术层拆。
2. 高内聚、低耦合，数据归属清楚。
3. 变更频率、扩容需求、团队边界可以作为辅助因素。
4. 共享数据库是风险，服务间应通过接口或事件协作。
5. 拆分后必须补齐治理：注册发现、监控、日志、链路追踪、配置、容错。

## 分布式一致性选择

| 场景 | 方案 |
| --- | --- |
| 银行转账类强一致 | 本地事务或 2PC，控制参与方和超时风险。 |
| 订单履约类长流程 | Saga 或可靠消息，失败时补偿。 |
| 资源预留类业务 | TCC，Try 预留、Confirm 确认、Cancel 释放。 |
| 通知、积分、发券 | 最终一致，消息重试、幂等、对账。 |

## 易混点

| 易混项 | 区分 |
| --- | --- |
| 熔断 vs 降级 | 熔断是防止继续调用故障服务；降级是主动减少功能或降低质量。 |
| 超时 vs 重试 | 超时避免无限等待；重试提高成功率但可能放大流量，必须配合幂等。 |
| 服务拆分 vs 数据拆分 | 服务拆分是业务边界；数据拆分是存储容量和性能手段。 |

## 考纲外重要保留

Service Mesh、DDD 战术模式和具体治理平台不作为主线；题干出现时，只从“服务治理、流量控制、可观测性、复杂度”角度回答。
