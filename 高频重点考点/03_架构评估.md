# 架构评估

> 重要程度：P0  
> 考纲定位：系统架构描述、分析、设计与评估的直接考点。

## 优先掌握

1. ATAM 的目标、参与者、步骤和产出。
2. 质量属性场景、效用树、风险点、敏感点、权衡点。
3. 架构方案比较时如何从质量属性和约束出发。
4. 能把“技术选择”写成“收益、代价、风险、验证方式”。

## 概念和场景

| 重要度 | 概念 | 概念解释 | 场景式解释 |
| --- | --- | --- | --- |
| P0 | ATAM | 以质量属性为核心评估架构决策的方法 | 电商系统要同时满足性能、可用性和安全，评估缓存、异步、分库分表的影响 |
| P0 | 质量属性场景 | 把抽象质量要求转成可验证场景 | “高峰期下单 3 秒内返回结果”比“系统要高性能”更可评估 |
| P0 | 效用树 | 将质量属性逐层分解并按优先级排序 | 顶层是性能，下面拆为查询延迟、支付吞吐、批处理时长 |
| P0 | 风险点 | 架构决策可能导致目标无法达成 | 只做单库部署，订单库故障会导致全站不可下单 |
| P0 | 权衡点 | 一个决策同时影响多个质量属性 | 强一致事务提升正确性，但降低性能和可用性 |
| P1 | 敏感点 | 小变化就显著影响质量属性的设计点 | 缓存过期时间会直接影响命中率和数据新鲜度 |
| P1 | 非风险点 | 当前证据表明风险可控的设计点 | 读多写少场景采用读写分离，已有延迟监控和强制读主库策略 |

## ATAM 答题顺序

1. 描述业务目标和质量属性目标。
2. 提取关键场景，按优先级排序。
3. 识别架构决策和架构方法。
4. 分析每个决策带来的风险点、敏感点、权衡点。
5. 给出改进建议和验证方式。

## 常见风险到建议

| 风险 | 建议 |
| --- | --- |
| 单点组件导致服务不可用 | 冗余部署、心跳检测、自动切换 |
| 同步链路过长导致超时 | 拆分链路、异步消息、超时和降级 |
| 数据一致性目标不清 | 明确强一致或最终一致，设计补偿和幂等 |
| 权限控制分散 | 统一认证授权、最小权限、审计日志 |
| 架构依赖厂商特性过重 | 设计抽象层、保留替代方案、验证迁移成本 |

## 易混点

| 易混项 | 区分 |
| --- | --- |
| ATAM vs SAAM | ATAM 面向多质量属性权衡；SAAM 更偏可修改性场景分析。 |
| 敏感点 vs 权衡点 | 敏感点强调“对某一质量属性敏感”；权衡点强调“多个质量属性互相影响”。 |
| 风险点 vs 缺陷 | 风险点是可能导致目标失败的架构隐患；缺陷通常是已发生的问题。 |

## 边界

CBAM 可以作为成本收益评估补充，但案例分析通常不要求展开经济模型计算。
