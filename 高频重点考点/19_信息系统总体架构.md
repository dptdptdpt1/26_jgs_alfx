# 信息系统总体架构

## 考试中一般怎么考

1. 总体架构分层：要求从业务、应用、数据、技术、安全、运维等角度描述系统。
2. 架构蓝图：给业务目标，要求规划系统模块、数据流、集成关系和部署形态。
3. 现状和目标架构：要求分析当前问题、目标能力和差距。
4. 架构原则：要求说明高内聚低耦合、标准化、复用、安全、可扩展等原则如何落地。
5. 信息化总体架构：问如何支撑跨部门、跨系统、跨业务域的信息共享和协同。
6. 架构治理：问如何控制重复建设、接口混乱、数据口径不一致。
7. 架构方法：问 ADM/TOGAF 如何从业务目标推导到目标架构和迁移计划。

## 针对考法梳理知识点

### 总体架构常见视角

| 视角 | 回答的问题 |
| --- | --- |
| 业务架构 | 业务能力、业务流程、组织协同 |
| 应用架构 | 有哪些系统和模块，职责如何划分 |
| 数据架构 | 主数据、业务数据、数据流向、数据共享 |
| 技术架构 | 中间件、数据库、缓存、消息、云平台 |
| 安全架构 | 认证、授权、加密、审计、边界防护 |
| 运维架构 | 监控、日志、告警、发布、备份和容灾 |

答总体架构题时，不要只画应用模块。要把业务、数据、技术和安全一起说明。

### 总体架构设计输入

总体架构不是凭空设计，常见输入包括：

- 业务战略和发展目标。
- 现状问题和痛点。
- 业务需求和非功能需求。
- 组织结构、业务流程和协同关系。
- 现有系统、接口、数据和基础设施。
- 政策法规、行业监管和安全合规要求。
- 预算、工期、团队能力和技术标准约束。

答题时要先把业务目标和约束讲清楚，再推出应用、数据、技术和安全设计。

### 现状架构和目标架构

| 架构 | 关注 |
| --- | --- |
| 现状架构 Baseline | 当前系统、流程、数据、接口、部署和问题 |
| 目标架构 Target | 未来业务能力、应用蓝图、数据共享、技术平台和治理机制 |

现状架构用于识别问题，例如烟囱系统、重复建设、接口混乱、数据孤岛、安全薄弱。

目标架构用于说明未来形态，例如统一门户、公共能力平台、主数据管理、API 网关、数据共享平台、统一运维和安全体系。

### 差距分析

差距分析是比较现状架构和目标架构，找出需要建设、改造、整合或退役的内容。

常见差距：

- 业务差距：流程割裂、跨部门协同不足。
- 应用差距：功能重复、系统边界不清、公共能力缺失。
- 数据差距：主数据不统一、数据质量差、共享困难。
- 技术差距：性能不足、扩展困难、技术栈混乱。
- 安全差距：认证分散、权限粗放、审计不足。
- 运维差距：监控分散、发布手工化、故障定位困难。

差距分析的结果应转化为迁移项目和实施路线。

### 架构蓝图产物

总体架构蓝图常见产物：

- 业务能力图。
- 业务流程图。
- 应用架构图。
- 数据架构图。
- 集成架构图。
- 技术架构图。
- 部署架构图。
- 安全架构图。
- 运维架构图。
- 架构演进路线图。

考试问“总体架构应包括什么”，可以按这些图和说明展开。

### ADM 和 TOGAF

TOGAF 是企业架构框架，ADM 是其中的架构开发方法。

考试不必展开框架全貌，抓住“从现状到目标架构，再到迁移和治理”的主线：

| 阶段 | 答题要点 |
| --- | --- |
| 预备和架构愿景 | 明确范围、目标、约束、架构原则 |
| 业务架构 | 梳理业务能力、流程、组织协同 |
| 数据和应用架构 | 明确主数据、数据流、应用边界和集成关系 |
| 技术架构 | 选择平台、中间件、数据库、网络和安全技术 |
| 机会与方案 | 比较候选方案，形成实施组合 |
| 迁移规划 | 制定阶段、优先级、依赖和风险控制 |
| 实施治理 | 检查项目实现是否符合架构 |
| 架构变更管理 | 根据业务和技术变化持续演进 |

易错点：ADM 不是只画架构图。它强调需求贯穿全过程，并通过迁移计划和治理把目标架构落到项目实施。

### 业务架构

业务架构关注业务能力和流程。

常见答题点：

- 按业务域划分能力，例如客户、订单、支付、库存、结算。
- 明确核心流程和辅助流程。
- 识别跨部门协同点和审批点。
- 把高频变化的业务规则从核心流程中隔离出来。

### 业务能力模型

业务能力模型把组织需要具备的能力按业务域拆开，比按部门划分更稳定。

例子：

```text
客户管理
  客户档案
  客户分级
  客户服务
订单履约
  下单
  支付
  库存占用
  发货
结算管理
  账单
  对账
  开票
```

业务能力可用于推导应用边界、公共能力和数据域。不要只按组织部门建系统，否则组织调整时系统容易跟着大改。

### 应用架构

应用架构关注系统边界和职责。

常见措施：

- 按业务能力划分应用或服务。
- 共性能力沉淀为统一平台，例如认证、消息、文件、报表。
- 对外系统通过网关或集成平台接入。
- 避免多个系统重复建设同一功能。

易错点：应用拆分不是越细越好。拆分后要考虑数据归属、接口治理和运维能力。

### 应用架构治理

应用架构治理关注应用资产和边界。

常见措施：

- 建立应用清单，记录系统名称、职责、负责人、接口和生命周期。
- 明确应用边界，避免多个系统重复实现同一业务能力。
- 建设公共能力平台，复用认证、组织、消息、文件、报表等能力。
- 对老旧系统制定保留、封装、替换或退役计划。
- 新建系统必须经过架构评审，检查是否重复建设和是否符合标准。

### 数据架构

数据架构关注数据归属、共享和一致性。

常见答题点：

- 建立主数据，例如客户、组织、产品、设备。
- 明确数据权威来源，避免多个系统各自维护同一份核心数据。
- 通过数据服务、数据交换或消息同步实现共享。
- 对分析场景建设数据仓库或大数据平台。
- 统一指标口径和数据权限。

### 数据架构细化

数据架构应说明数据如何归属、共享、治理和保护。

常见内容：

- 数据域：按业务主题划分客户、产品、订单、财务、设备等数据域。
- 主数据：确定客户、组织、产品等核心数据的权威来源。
- 数据标准：统一编码、字段含义、数据格式和指标口径。
- 数据共享：通过数据服务、数据交换、消息同步或数据平台共享。
- 数据质量：校验完整性、准确性、一致性和及时性。
- 数据安全：分级分类、权限控制、脱敏、加密和审计。
- 数据生命周期：采集、使用、归档、销毁和合规留存。

数据架构题常见落点是解决数据孤岛和口径不一致。

### 集成架构

集成架构解决跨系统互联、数据交换和业务协同。

常见组成：

- API 网关：统一入口、认证、路由、限流和审计。
- ESB / 集成平台：协议转换、服务编排、数据转换。
- 消息队列：异步解耦、事件通知、削峰填谷。
- 数据交换平台：批量交换、共享数据和跨部门报送。
- 统一认证：单点登录、身份管理和权限集成。
- 服务目录：记录服务能力、接口契约、版本和负责人。

接口治理要统一接口规范、错误码、版本管理、安全认证、超时重试和监控告警。

### 技术架构

技术架构要服务质量属性。

常见组合：

- 高并发：缓存、负载均衡、异步、水平扩展。
- 高可用：集群、主备、健康检查、故障切换。
- 集成：API 网关、消息队列、ESB、统一认证。
- 数据：关系库、缓存、搜索引擎、对象存储、数仓。
- 云化：容器、编排、弹性伸缩、自动化发布。

### 安全架构

安全架构要覆盖身份、边界、应用、数据和审计。

| 安全域 | 常见措施 |
| --- | --- |
| 身份认证 | 统一身份、单点登录、多因素认证 |
| 访问控制 | 角色权限、最小权限、细粒度授权 |
| 边界防护 | 防火墙、WAF、网闸、DMZ、安全组 |
| 传输安全 | HTTPS、VPN、证书、加密通道 |
| 数据安全 | 分级分类、脱敏、加密、备份 |
| 安全审计 | 操作日志、接口审计、异常告警 |
| 合规 | 等保、隐私保护、行业监管要求 |

总体架构中安全要前置设计，不能只在系统上线前补漏洞扫描。

### 运维架构

运维架构保障系统可运行、可监控、可恢复。

常见内容：

- 监控：主机、容器、数据库、中间件、接口和业务指标。
- 日志：统一采集、检索、留存和审计。
- 链路追踪：定位跨系统调用问题。
- 告警：阈值、通知、升级和值班机制。
- 发布：自动化部署、灰度发布和回滚。
- 备份恢复：数据库、文件、配置和灾备演练。
- 容量管理：容量评估、扩容计划和资源优化。
- 应急预案：故障分级、处置流程和恢复目标。

### 架构原则

常见原则：

- 业务驱动：架构服务业务目标。
- 分层解耦：减少跨层依赖和变化扩散。
- 标准化：统一接口、数据、日志、安全规范。
- 复用优先：共性能力平台化。
- 安全内建：认证、授权、审计和数据保护前置设计。
- 可演进：支持灰度、扩展、替换和迁移。

### 标准规范体系

标准规范用于控制总体架构落地的一致性。

常见标准：

- 技术标准：开发语言、框架、中间件、数据库、云平台选型。
- 接口标准：协议、数据格式、错误码、版本、安全认证。
- 数据标准：编码、字段含义、主数据、指标口径。
- 安全标准：认证、授权、加密、审计、漏洞管理。
- 运维标准：日志、监控、告警、发布、备份和应急。
- 开发规范：代码规范、分支策略、测试和质量门禁。

没有标准，系统越建越多后容易出现接口不兼容、数据口径不一致和运维困难。

### 公共能力平台

公共能力平台用于沉淀共性能力，减少重复建设。

常见公共能力：

- 统一认证和用户中心。
- 组织机构和权限中心。
- 消息通知。
- 文件和对象存储。
- 工作流和规则引擎。
- 报表和数据分析。
- 支付、结算或电子签章等行业公共能力。
- 日志审计和监控告警。

答题时可写：把多个系统重复使用的能力抽象成公共平台，通过标准接口提供服务，提高复用和一致性。

### 架构治理

架构治理解决“系统越来越多但越来越乱”的问题。

常见措施：

- 建立架构原则和技术标准。
- 对新系统进行架构评审。
- 统一接口规范、数据标准和安全规范。
- 建立公共能力平台，减少重复建设。
- 对技术债和遗留系统制定演进路线。

### 架构管控机制

架构治理要有组织和流程支撑。

常见机制：

- 架构委员会或架构评审组。
- 架构原则、技术标准和参考架构。
- 项目立项和方案阶段做架构评审。
- 技术选型评审，控制技术栈无序扩散。
- 架构符合性检查，检查项目实现是否偏离目标架构。
- 例外审批，对确需突破标准的场景记录原因和期限。
- 架构资产库，沉淀模型、接口、数据标准和公共组件。

治理目标不是增加流程，而是控制重复建设、降低集成成本、保证安全和可持续演进。

### 架构演进路线

总体架构通常分阶段演进。

常见路线：

1. 近期：梳理现状、统一标准、建设统一认证和接口规范。
2. 中期：整合重复系统，建设公共能力平台、数据共享平台和主数据。
3. 远期：推进服务化、云化、智能化和持续架构治理。

演进要遵循先标准后整合、先外围后核心、先低风险后高风险、可灰度可回滚。

### 常见问题和改进

| 问题 | 改进 |
| --- | --- |
| 烟囱系统多 | 建设集成平台和公共能力平台 |
| 重复建设 | 应用清单、架构评审、共性能力复用 |
| 接口混乱 | API 网关、接口规范、服务目录、版本管理 |
| 数据孤岛 | 主数据、数据共享平台、数据标准 |
| 指标口径不一致 | 指标字典、数仓建模、数据治理 |
| 安全薄弱 | 统一认证、权限控制、审计、数据分级分类 |
| 运维分散 | 统一监控、日志、告警和自动化发布 |
| 技术栈混乱 | 技术标准、选型评审、架构符合性检查 |

### 总体架构答题模板

```text
从业务架构识别业务域和核心流程；从应用架构划分系统边界和公共能力；从数据架构明确主数据、数据流向和共享方式；从技术架构选择数据库、缓存、消息、网关、容器等支撑能力；从安全和运维架构设计认证授权、审计、监控、备份和容灾；最后用架构治理保证标准统一和可持续演进。
```
