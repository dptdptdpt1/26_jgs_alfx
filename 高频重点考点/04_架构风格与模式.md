# 架构风格与模式

> 重要程度：P0  
> 考纲定位：系统架构设计基本技术、架构选择、架构改进和方案比较。

## 优先掌握

1. 能根据题干场景选择架构风格。
2. 能说明每种风格解决什么问题、带来什么代价。
3. 能把架构风格和质量属性联系起来。
4. 能识别“为技术而技术”的错误选择。

## 概念和场景

| 重要度 | 风格/模式 | 概念解释 | 场景式解释 | 主要代价 |
| --- | --- | --- | --- | --- |
| P0 | 分层架构 | 按职责分为表现、业务、数据等层 | 管理系统需要边界清晰、便于维护 | 层间调用可能增加延迟 |
| P0 | 微服务 | 按业务能力拆成独立服务 | 订单、库存、支付独立演进和扩容 | 分布式复杂度上升 |
| P0 | 事件驱动 | 组件通过事件异步协作 | 下单后异步发券、通知、积分 | 一致性和排错更复杂 |
| P0 | SOA | 通过服务契约集成企业能力 | 多个既有系统通过服务总线复用能力 | 治理成本高，可能变重 |
| P1 | 管道-过滤器 | 数据经过一串处理步骤 | 日志采集、清洗、转换、入库 | 不适合强交互流程 |
| P1 | MVC/MVVM | 分离界面、控制/视图模型、业务数据 | Web 或客户端界面需要降低 UI 与业务耦合 | 不解决后端整体架构问题 |
| P1 | 微内核 | 核心系统加插件扩展 | 规则引擎、IDE、报表平台扩展插件 | 插件接口设计要求高 |
| P2 | C/S 与 B/S | 客户端/服务器或浏览器/服务器 | 内网专用终端可用 C/S，跨地域访问多用 B/S | C/S 部署维护成本较高 |

## 选择规则

1. 业务变化频繁，模块边界清晰：优先分层、领域模块化，再考虑微服务。
2. 多系统集成、复用既有能力：优先 SOA、接口标准、消息或集成平台。
3. 高并发削峰、非核心动作异步化：优先事件驱动和消息队列。
4. 数据处理流水线清晰：优先管道-过滤器。
5. 插件扩展是核心诉求：优先微内核。

## 答题模板

1. 选择某架构风格，因为题干中存在哪些关键约束。
2. 该风格通过哪些机制满足哪些质量属性。
3. 同时说明代价：复杂度、性能、一致性、运维或治理成本。
4. 给出配套措施：监控、限流、接口规范、数据一致性、自动化部署等。

## 易混点

| 易混项 | 区分 |
| --- | --- |
| SOA vs 微服务 | SOA 偏企业级服务复用和集成治理；微服务偏小团队独立交付和独立部署。 |
| 事件驱动 vs 消息队列 | 事件驱动是架构风格；消息队列是常用实现手段。 |
| 分层 vs 分布式 | 分层是职责组织方式；分布式是部署和运行形态。 |

## 考纲外重要保留

DDD、整洁架构、六边形架构不作为本章主线展开；若题干出现“领域模型、适配器、端口”等词，只作为解释微服务拆分和可修改性的辅助概念。
