# 数据库设计

> 重要程度：P0  
> 考纲定位：数据库系统、数据建模、信息系统架构和案例中的数据层设计。

## 优先掌握

1. ER 模型、关系模式、范式和反范式的取舍。
2. 事务、一致性、并发控制、备份恢复。
3. 数据量增长时的分区、分库分表、冷热分离。
4. OLTP、OLAP、数据仓库的边界。

## 概念和场景

| 重要度 | 内容 | 概念解释 | 场景式解释 |
| --- | --- | --- | --- |
| P0 | ER 模型 | 实体、属性和联系的概念模型 | 订单、客户、商品之间的业务关系先画清楚再建表 |
| P0 | 范式 | 减少数据冗余和异常的设计规则 | 客户手机号只维护一处，避免多个订单表重复存储后不一致 |
| P0 | 反范式 | 为查询性能有意增加冗余 | 订单表冗余商品名称，避免历史订单展示频繁联表 |
| P0 | 事务 | 一组操作要么都成功要么都失败 | 支付成功和订单状态更新必须保持一致 |
| P0 | 读写分离 | 写主库、读从库分担压力 | 商品详情页读多写少，用从库承担读请求 |
| P0 | 分库分表 | 将数据按规则拆到多个库表 | 订单量过亿后按用户或订单号分片 |
| P1 | 分区 | 单库内按范围或规则划分物理存储 | 日志表按月份分区便于清理和查询 |
| P1 | 冷热分离 | 高频新数据和低频历史数据分开存储 | 近 3 个月订单在在线库，历史订单进归档库 |
| P1 | 数据仓库 | 面向分析的主题化、集成化数据集合 | 管理层分析销售趋势，不直接查交易库 |

## 数据层设计顺序

1. 先确定业务实体和关系。
2. 再确定事务边界和一致性要求。
3. 再按访问模式设计索引、分区和读写分离。
4. 数据规模超出单机能力时，再考虑分库分表和冷热分离。
5. 分析型需求不要压在线交易库，优先走数据仓库或分析库。

## 常见场景

| 场景 | 处理 |
| --- | --- |
| 查询慢 | 先看 SQL、索引、执行计划和数据量，再考虑缓存或拆分。 |
| 写入慢 | 看事务范围、锁冲突、批量写入、异步化和分片。 |
| 数据不一致 | 明确强一致还是最终一致，补充事务、幂等、补偿和对账。 |
| 历史数据拖慢在线库 | 冷热分离、归档、分区裁剪。 |

## 易混点

| 易混项 | 区分 |
| --- | --- |
| 分区 vs 分表 | 分区通常仍是一张逻辑表；分表会改变路由和应用访问方式。 |
| 分表 vs 分库 | 分表解决单表过大；分库还能分担连接、计算和存储压力。 |
| 范式 vs 性能 | 范式保证一致性和可维护性；性能不足时可有限反范式。 |
| OLTP vs OLAP | OLTP 服务交易；OLAP 服务分析。 |

## 边界

不展开具体数据库内核算法。案例题更关心设计取舍、风险和改进措施。
