# 架构演化与遗留系统改造

## 考试中一般怎么考

1. 遗留系统改造：问旧系统如何逐步拆分、替换、集成或保留。
2. 单体到微服务：要求说明拆分顺序、数据迁移、接口兼容和风险控制。
3. 数据迁移：问如何保证迁移准确性、一致性和可回滚。
4. 灰度演进：问如何降低切换风险，支持新旧系统并行。
5. 技术债治理：问如何评估风险、制定演进路线和控制改造范围。
6. 改造策略：问绞杀者模式、兼容策略、回滚策略和技术债治理。

## 针对考法梳理知识点

### 架构演化原则

常见原则：

- 业务连续优先，不能为了改造中断核心业务。
- 先外围后核心，先低风险后高风险。
- 保持接口兼容，减少对调用方影响。
- 数据迁移可校验、可回滚。
- 每一步都有监控、灰度和回退方案。

### 遗留系统评估

改造前先评估，不要直接推倒重写。

| 维度 | 看什么 |
| --- | --- |
| 业务价值 | 是否仍支撑核心业务，是否有替代流程 |
| 技术风险 | 技术栈老旧、缺文档、缺人员、难扩展 |
| 维护成本 | 缺陷率、变更成本、运维成本 |
| 集成依赖 | 被哪些系统调用，依赖哪些数据和接口 |
| 数据风险 | 数据质量、历史数据、迁移复杂度 |
| 替换难度 | 停机窗口、并行业务、回滚能力 |

业务价值高但技术风险高的系统，通常适合渐进封装和替换。

### 遗留系统处理策略

| 策略 | 适合场景 |
| --- | --- |
| 封装 | 旧系统稳定但接口落后，通过适配层对外提供标准接口 |
| 替换 | 旧系统无法维护或风险过高，逐步用新系统替代 |
| 扩展 | 核心暂不动，在外围增加新能力 |
| 重构 | 功能仍有价值，但内部结构混乱 |
| 退役 | 业务已停止或被新系统覆盖 |

易错点：不要一上来就“全部重写”。核心系统通常要渐进改造。

### 6R 改造策略

| 策略 | 含义 |
| --- | --- |
| Retain 保留 | 暂时不动，继续运行 |
| Rehost 迁移 | 少改造，迁到新基础设施或云上 |
| Replatform 平台改造 | 适度改造，替换运行平台或中间件 |
| Refactor 重构 | 保留功能，改善内部结构 |
| Replace 替换 | 用新系统或产品替代 |
| Retire 退役 | 下线无价值系统 |

选择策略时看业务价值、风险、成本、期限和替代方案成熟度。

### 绞杀者模式

绞杀者模式是用新系统逐步包围并替代旧系统。

常见做法：

1. 在旧系统前增加网关或路由层。
2. 新功能优先在新系统实现。
3. 逐步把某些接口或流量路由到新系统。
4. 新旧系统并行期间保持接口和数据兼容。
5. 某个旧模块被完全替代后再下线。

优点是风险可控、业务连续。代价是新旧系统并行期集成和数据一致性复杂。

### 单体到微服务

常见步骤：

1. 梳理业务域和模块依赖。
2. 选择边界清晰、风险较低的模块先拆。
3. 为旧系统增加 API 或防腐层。
4. 新服务独立部署，并接入注册、配置、监控、日志。
5. 逐步迁移流量和数据。
6. 验证稳定后再拆核心模块。

拆分时要同时考虑数据归属。只拆代码不拆数据，服务之间仍可能强耦合。

### 数据库拆分策略

从单体共享库演进到服务独立数据要谨慎。

常见步骤：

- 先梳理表归属和业务边界。
- 禁止新服务直接访问旧系统表，优先通过接口或事件。
- 对先拆模块建立独立库或独立 Schema。
- 使用全量迁移加增量同步迁出数据。
- 通过消息、CDC、对账和补偿保证最终一致。
- 缩短共享库和双写并行时间。

服务拆分后仍共享数据库，会保留强耦合，难以独立演进。

### 防腐层

防腐层用于隔离新旧系统模型和接口。

作用：

- 把旧系统接口转换为新系统需要的模型。
- 屏蔽旧系统字段、协议、异常格式。
- 避免新系统直接依赖旧系统内部结构。

适合新旧系统长期并行或逐步迁移的场景。

### 兼容策略

新旧系统并行期间要控制兼容性。

| 兼容 | 做法 |
| --- | --- |
| 接口兼容 | 保持旧接口可用，新增字段向后兼容 |
| 数据兼容 | 字段新增先兼容旧逻辑，避免直接删除或改语义 |
| 版本兼容 | 新旧版本共存，明确废弃周期 |
| 流量兼容 | 按用户、地区、机构或比例灰度切流 |
| 回滚兼容 | 新版本失败时旧版本能继续处理数据 |

数据库结构变更应优先采用扩展式变更，例如先加字段、双写、迁移、再删除旧字段。

### 数据迁移

常见做法：

- 迁移前清洗、去重、补全和字段映射。
- 先全量迁移，再增量同步。
- 迁移后做行数、金额、状态、抽样和业务对账。
- 切换前冻结写入或使用双写/日志同步。
- 保留回滚方案和旧数据备份。

易错点：只写“导入数据”不够。案例题通常要写校验、对账、增量同步和回滚。

### 双写和数据一致性

双写常用于新旧系统并行期，但风险高。

常见风险：

- 一个系统写成功，另一个失败。
- 写入顺序不同导致状态不一致。
- 回滚和补偿复杂。

常见控制：

- 以一个系统为主数据源。
- 通过消息、日志或 CDC 同步到另一个系统。
- 建立对账和补偿任务。
- 缩短双写窗口，避免长期并行。

### 灰度迁移

常见灰度方式：

- 按用户、机构、地区、业务类型切流。
- 小比例流量先进入新系统。
- 监控错误率、延迟、业务指标。
- 出现异常快速切回旧系统。

灰度迁移适合降低切换风险，但要求新旧系统接口和数据兼容。

### 回滚和补偿

回滚不只是代码回退。

常见层次：

- 流量回切：网关或路由把流量切回旧系统。
- 应用回滚：回到旧版本应用。
- 配置回滚：恢复旧配置、开关和路由规则。
- 数据补偿：对已产生的新数据做修正、对账或反向操作。
- 备份恢复：极端情况下恢复备份。

数据变更通常最难回滚，因此发布前要设计兼容字段、备份、补偿和对账。

### 技术债治理

技术债是为了短期交付留下的长期维护成本。

治理步骤：

1. 识别技术债，例如重复代码、强耦合、无测试、老旧框架、安全漏洞。
2. 评估影响，按业务风险、修改频率、故障率和维护成本分级。
3. 排定优先级，把高风险债务纳入迭代计划。
4. 小步重构，配合自动化测试和监控。
5. 建立架构评审和编码规范，避免新增债务失控。

不要为了“还债”大范围重写核心系统。技术债治理应和业务演进、风险控制结合。

### 改造风险和控制

| 风险 | 控制 |
| --- | --- |
| 业务中断 | 分阶段、灰度、回滚预案 |
| 数据不一致 | 对账、补偿、主数据源、缩短双写窗口 |
| 性能退化 | 压测、容量评估、监控指标 |
| 接口不兼容 | 版本管理、契约测试、兼容字段 |
| 团队不熟悉新技术 | 技术预研、培训、试点 |
| 改造范围失控 | 边界清晰、优先级、变更控制 |

### 架构演化答题模板

```text
先评估旧系统的业务价值、技术风险和依赖关系；对稳定但难改的能力用接口封装和防腐层隔离；选择边界清晰、风险较低的模块先拆分；通过全量迁移加增量同步完成数据迁移，并做校验、对账和备份；采用灰度切流监控业务指标，异常时快速回滚；最终逐步下线被替代的旧模块。
```
