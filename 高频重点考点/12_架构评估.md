# 架构评估

## 考试中一般怎么考

1. 方法识别：问 ATAM、SAAM、CBAM 分别适合解决什么问题。
2. 质量属性场景：根据题干补刺激源、刺激、环境、制品、响应、响应度量。
3. 风险分析：识别敏感点、权衡点、风险点、非风险点。
4. 方案评价：给出某系统设计，分析哪些设计影响性能、安全、可用性或可维护性。
5. 评估过程：问 ATAM、SAAM、CBAM 的步骤、参与者和输出结果。
6. 改进建议：要求针对风险提出架构调整措施。

## 针对考法梳理知识点

### ATAM

ATAM 是架构权衡分析方法，重点评估架构方案对多个质量属性的影响，并识别风险点、敏感点和权衡点。

常见答题流程：

1. 收集业务目标和质量属性需求。
2. 描述候选架构方案。
3. 构造质量属性场景。
4. 分析架构决策对质量属性的影响。
5. 识别敏感点、权衡点、风险点和非风险点。
6. 形成评估结论和改进建议。

考试里看到“多个质量属性之间取舍”“分析架构决策影响”，优先联想到 ATAM。

### ATAM 详细步骤

ATAM 的重点是用质量属性场景评价架构决策，并识别风险和权衡。

常见步骤：

1. 提出 ATAM 方法，明确评估目标和方式。
2. 提出业务动机，明确系统最重要的业务目标和约束。
3. 描述架构，说明主要模块、接口、部署和关键设计决策。
4. 识别架构方法，例如缓存、冗余、消息队列、分层、加密。
5. 生成质量属性效用树，把质量属性拆成具体场景。
6. 分析架构方法，判断它们如何影响质量属性场景。
7. 识别风险点、非风险点、敏感点和权衡点。
8. 汇总风险主题，形成评估结论和改进建议。

考试中不用机械背步骤名，关键是写出“业务目标 -> 质量属性场景 -> 架构决策分析 -> 风险和权衡 -> 改进建议”。

### ATAM 参与者

架构评估需要多方参与，不能只由架构师单独完成。

常见参与者：

- 评估团队：主持评估过程，组织场景和风险分析。
- 项目决策者：提供业务目标、成本、进度和优先级约束。
- 架构师：说明架构方案和关键设计决策。
- 开发人员：说明实现复杂度、技术约束和修改成本。
- 测试人员：说明测试风险、质量验证和缺陷情况。
- 运维人员：说明部署、监控、故障恢复和运行风险。
- 业务代表和用户代表：说明业务目标、场景重要性和验收关注点。

参与者越完整，越容易发现遗漏的质量属性场景和隐含风险。

### SAAM

SAAM 是软件架构分析方法，重点通过场景分析架构的可修改性、可扩展性和适应能力。

它常用于比较多个架构方案面对变更时的影响范围。

答题关键词：场景、变更、影响分析、方案比较。

### SAAM 详细过程

SAAM 更关注场景和可修改性，适合比较不同架构面对变化时的影响。

常见步骤：

1. 描述候选架构。
2. 开发场景，包括直接场景和间接场景。
3. 评估单个场景，分析该场景是否容易支持。
4. 分析场景交互，判断多个场景是否影响同一组件。
5. 对方案进行总体评价，比较修改成本、复杂度和风险。

直接场景是架构已有能力可以支持的场景。间接场景是需要修改架构才能支持的场景。

如果多个变化场景都集中影响同一模块，说明该模块可能职责过重或耦合过高。

### CBAM

CBAM 是成本效益分析方法，在 ATAM 基础上进一步考虑架构策略的收益、成本、风险和优先级。

它适合资源有限时选择“哪个改进最值得做”。

答题关键词：成本、收益、效用、优先级、投资回报。

### CBAM 详细过程

CBAM 通常建立在 ATAM 的风险和改进建议基础上，用来决定先做哪个架构改进。

常见步骤：

1. 收集候选架构策略，例如引入缓存、主备切换、服务拆分、加密审计。
2. 估算每个策略对质量属性的收益。
3. 估算每个策略的成本和实现风险。
4. 分析策略之间的依赖和冲突。
5. 比较投资回报，确定改进优先级。

考试里如果题目强调“资源有限、预算有限、哪些改进最值得做”，优先联想到 CBAM。

### 三种方法速查

| 方法 | 核心关注 | 常见题眼 |
| --- | --- | --- |
| SAAM | 场景和可修改性 | 变更影响、方案比较 |
| ATAM | 质量属性权衡 | 敏感点、权衡点、风险点 |
| CBAM | 成本收益 | 投资回报、改进优先级 |

### 质量属性场景六要素

| 要素 | 含义 | 例子 |
| --- | --- | --- |
| 刺激源 | 谁触发 | 用户、外部系统、攻击者、管理员 |
| 刺激 | 发生什么 | 发起请求、节点故障、恶意访问 |
| 环境 | 在什么条件下 | 正常运行、高峰期、故障状态 |
| 制品 | 影响哪个部分 | Web 服务、数据库、认证模块 |
| 响应 | 系统如何处理 | 返回结果、切换节点、拒绝请求 |
| 响应度量 | 如何衡量 | 2 秒内、99.9%、丢失数据为 0 |

答题时响应度量要具体。只写“快速恢复”“提高性能”不够，应写“30 秒内切换”“响应时间小于 2 秒”。

### 场景分类

架构评估中的场景可分为：

| 场景 | 含义 | 例子 |
| --- | --- | --- |
| 用例场景 | 系统当前必须支持的典型功能和质量要求 | 高峰期用户查询订单 2 秒内返回 |
| 增长场景 | 未来规模、用户量、数据量增长后的要求 | 用户数增长 10 倍后仍能水平扩展 |
| 探索场景 | 未来可能出现但不确定的变化 | 新增第三方支付渠道需 2 人日内完成 |

SAAM 和 ATAM 都使用场景分析。场景要尽量具体，能映射到架构中的组件、接口、数据和部署节点。

### 敏感点、权衡点、风险点、非风险点

| 概念 | 判断方式 | 例子 |
| --- | --- | --- |
| 敏感点 | 某个设计参数明显影响某个质量属性 | 缓存过期时间影响性能和数据新鲜度 |
| 权衡点 | 一个设计同时影响多个质量属性，且有取舍 | 增加加密提高安全性，但增加性能开销 |
| 风险点 | 当前设计可能导致质量属性目标达不到 | 单数据库节点可能影响可用性 |
| 非风险点 | 当前设计对目标无明显负面影响或已有控制措施 | 只读静态资源使用 CDN 提升性能且不影响一致性 |

考试里最容易混的是敏感点和权衡点。敏感点强调“影响大”，权衡点强调“多个属性之间有取舍”。

### 常见架构决策影响

架构方法也叫架构策略或架构决策，是评估时真正要分析的对象。

| 架构设计 | 提升 | 可能风险 |
| --- | --- | --- |
| 引入缓存 | 性能、可扩展性 | 数据一致性、缓存雪崩 |
| 引入消息队列 | 性能、可扩展性、可用性 | 延迟、重复消费、消息丢失 |
| 服务拆分 | 可维护性、可扩展性 | 分布式事务、调用链复杂 |
| 集群部署 | 可用性、性能 | 状态共享、数据一致性 |
| 加密传输 | 安全性 | CPU 开销、证书管理 |
| 分库分表 | 性能、容量扩展 | 跨库查询、事务和迁移复杂 |

### ATAM 产出物怎么写

ATAM 题通常不是让背定义，而是让输出分析结果。

常见产出：

- 质量属性效用树：把质量属性按业务重要性和风险拆成具体场景。
- 架构方法清单：缓存、集群、异步、分层、加密等设计决策。
- 敏感点：影响某个质量属性的关键参数或设计。
- 权衡点：一个设计带来多属性取舍。
- 风险点：可能导致质量目标无法达成。
- 非风险点：当前设计已经满足目标或风险可控。

如果题目让“评价该架构”，可以先列质量属性场景，再逐个分析架构决策对场景的支持程度。

### 质量属性效用树

效用树用于把抽象质量属性拆成可分析场景。

例子：

```text
性能
  查询性能：高峰期订单查询 2 秒内返回
  写入性能：秒杀活动每秒处理 5000 个下单请求
可用性
  节点故障：应用节点故障后 30 秒内摘除
  数据库故障：主库故障后 1 分钟内切换
安全性
  接口安全：外部接口必须防篡改、防重放
  数据安全：敏感字段加密存储并脱敏展示
```

效用树的关键不是树形格式，而是把“性能好、安全高”拆成可验证场景。

### 效用树优先级

效用树中的场景通常要按两个维度排序：

- 重要性：该场景对业务目标有多重要。
- 风险：当前架构满足该场景的风险有多高。

优先分析“高重要性 + 高风险”的场景。例如核心交易系统中，“下单链路高峰期 2 秒内响应”和“数据库故障后 1 分钟内恢复”通常比普通报表导出更值得优先评估。

答题时如果题目要求选择重点场景，可写：优先选择对核心业务影响大、当前架构风险高、响应度量明确的质量属性场景。

### 风险主题

风险主题是把多个相关风险点归纳成更高层的问题。

例子：

```text
多个风险点：订单库单点、支付回调无重试、应用节点无健康检查。
风险主题：核心交易链路可用性保障不足。
```

风险主题适合放在评估结论中，用来说明主要问题方向，而不是只列零散风险。

### 风险点写法

风险点要写成“设计缺陷 + 影响的质量属性 + 后果”。

不好的写法：

```text
数据库有风险。
```

较好的写法：

```text
订单数据库单点部署，主库故障时没有自动切换机制，会影响订单服务可用性，可能导致用户无法下单。
```

非风险点也要说明为什么不是风险：

```text
静态资源已部署 CDN，即使源站压力较高，用户仍可就近访问缓存资源，因此静态资源访问性能风险较低。
```

### 风险到改进建议映射

改进建议要对应具体风险，不要泛泛写“优化架构”。

| 风险 | 常见改进 |
| --- | --- |
| 单点部署影响可用性 | 主备、集群、负载均衡、自动故障切换 |
| 高峰期响应慢 | 缓存、异步、读写分离、SQL 优化、水平扩展 |
| 消息可能重复或丢失 | 幂等处理、确认机制、重试、死信队列、消息监控 |
| 外部系统不稳定 | 超时、重试、熔断、降级、隔离、接口 Mock |
| 服务拆分后链路复杂 | 注册发现、网关、链路追踪、统一监控告警 |
| 数据一致性风险 | 事务、补偿、最终一致性设计、对账机制 |
| 安全控制不足 | 认证、授权、加密、防重放、审计、最小权限 |
| 可修改性差 | 分层、模块化、接口隔离、配置化、插件化 |
| 发布风险高 | 灰度发布、回滚方案、自动化部署、发布评审 |

建议写法：先指出风险影响的质量属性，再给对应架构措施，最后说明措施如何降低风险。

### 架构评估和测试评审的区别

架构评估发生在设计阶段或早期迭代阶段，关注架构是否能够满足质量属性目标，重点分析设计决策、风险和权衡。

测试发生在实现之后，关注系统运行结果是否符合需求和质量指标。

评审可以覆盖需求、设计、代码、测试和发布，范围更宽。架构评估是面向架构方案和质量属性的专项评审。

易错点：不能等系统做完才做架构评估。架构评估越早，越容易低成本发现质量属性风险。

### 评估题答题步骤

1. 抽取业务目标：系统最关心交易、查询、监管、实时控制还是数据分析。
2. 抽取质量属性：性能、可用性、安全性、可修改性等。
3. 构造质量属性场景：必须有响应度量。
4. 对照架构设计：逐项判断是否支持该场景。
5. 标出敏感点和权衡点：写清楚取舍。
6. 给改进建议：建议要对应风险点，不能泛泛而谈。

### 评估题常用句式

分析架构决策：

```text
该架构采用 X 设计，能够提升 Y 质量属性，因为它通过 Z 机制实现；但会带来 A 风险，需要 B 措施控制。
```

写风险点：

```text
当前 X 设计存在 Y 缺陷，会影响 Z 质量属性，可能导致 A 后果。
```

写权衡点：

```text
X 设计提升了 Y 质量属性，但牺牲或增加了 Z 方面的代价，因此属于权衡点。
```

写改进建议：

```text
针对 X 风险，建议采用 Y 架构措施，使系统在 Z 场景下达到 A 响应度量。
```
