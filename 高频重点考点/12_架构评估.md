# 架构评估

## 考试中一般怎么考

1. 方法识别：问 ATAM、SAAM、CBAM 分别适合解决什么问题。
2. 质量属性场景：根据题干补刺激源、刺激、环境、制品、响应、响应度量。
3. 风险分析：识别敏感点、权衡点、风险点、非风险点。
4. 方案评价：给出某系统设计，分析哪些设计影响性能、安全、可用性或可维护性。
5. 改进建议：要求针对风险提出架构调整措施。

## 针对考法梳理知识点

### ATAM

ATAM 是架构权衡分析方法，重点评估架构方案对多个质量属性的影响，并识别风险点、敏感点和权衡点。

常见答题流程：

1. 收集业务目标和质量属性需求。
2. 描述候选架构方案。
3. 构造质量属性场景。
4. 分析架构决策对质量属性的影响。
5. 识别敏感点、权衡点、风险点和非风险点。
6. 形成评估结论和改进建议。

考试里看到“多个质量属性之间取舍”“分析架构决策影响”，优先联想到 ATAM。

### SAAM

SAAM 是软件架构分析方法，重点通过场景分析架构的可修改性、可扩展性和适应能力。

它常用于比较多个架构方案面对变更时的影响范围。

答题关键词：场景、变更、影响分析、方案比较。

### CBAM

CBAM 是成本效益分析方法，在 ATAM 基础上进一步考虑架构策略的收益、成本、风险和优先级。

它适合资源有限时选择“哪个改进最值得做”。

答题关键词：成本、收益、效用、优先级、投资回报。

### 三种方法速查

| 方法 | 核心关注 | 常见题眼 |
| --- | --- | --- |
| SAAM | 场景和可修改性 | 变更影响、方案比较 |
| ATAM | 质量属性权衡 | 敏感点、权衡点、风险点 |
| CBAM | 成本收益 | 投资回报、改进优先级 |

### 质量属性场景六要素

| 要素 | 含义 | 例子 |
| --- | --- | --- |
| 刺激源 | 谁触发 | 用户、外部系统、攻击者、管理员 |
| 刺激 | 发生什么 | 发起请求、节点故障、恶意访问 |
| 环境 | 在什么条件下 | 正常运行、高峰期、故障状态 |
| 制品 | 影响哪个部分 | Web 服务、数据库、认证模块 |
| 响应 | 系统如何处理 | 返回结果、切换节点、拒绝请求 |
| 响应度量 | 如何衡量 | 2 秒内、99.9%、丢失数据为 0 |

答题时响应度量要具体。只写“快速恢复”“提高性能”不够，应写“30 秒内切换”“响应时间小于 2 秒”。

### 敏感点、权衡点、风险点、非风险点

| 概念 | 判断方式 | 例子 |
| --- | --- | --- |
| 敏感点 | 某个设计参数明显影响某个质量属性 | 缓存过期时间影响性能和数据新鲜度 |
| 权衡点 | 一个设计同时影响多个质量属性，且有取舍 | 增加加密提高安全性，但增加性能开销 |
| 风险点 | 当前设计可能导致质量属性目标达不到 | 单数据库节点可能影响可用性 |
| 非风险点 | 当前设计对目标无明显负面影响或已有控制措施 | 只读静态资源使用 CDN 提升性能且不影响一致性 |

考试里最容易混的是敏感点和权衡点。敏感点强调“影响大”，权衡点强调“多个属性之间有取舍”。

### 常见架构决策影响

| 架构设计 | 提升 | 可能风险 |
| --- | --- | --- |
| 引入缓存 | 性能、可扩展性 | 数据一致性、缓存雪崩 |
| 引入消息队列 | 性能、可扩展性、可用性 | 延迟、重复消费、消息丢失 |
| 服务拆分 | 可维护性、可扩展性 | 分布式事务、调用链复杂 |
| 集群部署 | 可用性、性能 | 状态共享、数据一致性 |
| 加密传输 | 安全性 | CPU 开销、证书管理 |
| 分库分表 | 性能、容量扩展 | 跨库查询、事务和迁移复杂 |

### ATAM 产出物怎么写

ATAM 题通常不是让背定义，而是让输出分析结果。

常见产出：

- 质量属性效用树：把质量属性按业务重要性和风险拆成具体场景。
- 架构方法清单：缓存、集群、异步、分层、加密等设计决策。
- 敏感点：影响某个质量属性的关键参数或设计。
- 权衡点：一个设计带来多属性取舍。
- 风险点：可能导致质量目标无法达成。
- 非风险点：当前设计已经满足目标或风险可控。

如果题目让“评价该架构”，可以先列质量属性场景，再逐个分析架构决策对场景的支持程度。

### 质量属性效用树

效用树用于把抽象质量属性拆成可分析场景。

例子：

```text
性能
  查询性能：高峰期订单查询 2 秒内返回
  写入性能：秒杀活动每秒处理 5000 个下单请求
可用性
  节点故障：应用节点故障后 30 秒内摘除
  数据库故障：主库故障后 1 分钟内切换
安全性
  接口安全：外部接口必须防篡改、防重放
  数据安全：敏感字段加密存储并脱敏展示
```

效用树的关键不是树形格式，而是把“性能好、安全高”拆成可验证场景。

### 风险点写法

风险点要写成“设计缺陷 + 影响的质量属性 + 后果”。

不好的写法：

```text
数据库有风险。
```

较好的写法：

```text
订单数据库单点部署，主库故障时没有自动切换机制，会影响订单服务可用性，可能导致用户无法下单。
```

非风险点也要说明为什么不是风险：

```text
静态资源已部署 CDN，即使源站压力较高，用户仍可就近访问缓存资源，因此静态资源访问性能风险较低。
```

### 评估题答题步骤

1. 抽取业务目标：系统最关心交易、查询、监管、实时控制还是数据分析。
2. 抽取质量属性：性能、可用性、安全性、可修改性等。
3. 构造质量属性场景：必须有响应度量。
4. 对照架构设计：逐项判断是否支持该场景。
5. 标出敏感点和权衡点：写清楚取舍。
6. 给改进建议：建议要对应风险点，不能泛泛而谈。
