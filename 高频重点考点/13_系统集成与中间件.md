# 系统集成与中间件

## 考试中一般怎么考

1. 集成方式选择：比较 RPC、REST、WebService、消息队列、ESB 的适用场景。
2. 集成层次和模式：问表示集成、数据集成、应用集成、流程集成，以及点对点、总线、发布订阅等模式。
3. 同步异步取舍：问为什么用消息队列解耦、削峰、提高可用性。
4. 中间件作用：问 Redis、Elasticsearch、对象存储分别解决什么问题。
5. 一致性和可靠性：问异步消息如何保证不丢、不重复、失败可处理。
6. 耦合分析：指出紧耦合问题，并提出松耦合集成方案。
7. SOA / EAI 实施：问服务如何识别、契约如何设计、服务如何编排和治理。
8. 接口治理：问接口安全、版本管理、限流、熔断、监控和审计。

## 针对考法梳理知识点

### 系统集成层次

系统集成不是只有接口调用，可以从不同层次集成。

| 层次 | 说明 | 适用 |
| --- | --- | --- |
| 表示集成 | 在界面层把多个系统入口整合到一起 | 门户、单点登录、统一工作台 |
| 数据集成 | 在数据层交换、同步、清洗和汇总数据 | 数据仓库、主数据、报表分析 |
| 应用集成 | 通过接口、消息、服务调用连接应用功能 | 订单调用库存、CRM 对接 ERP |
| 业务流程集成 | 按业务流程编排多个系统能力 | 跨系统审批、供应链协同 |

考试里如果问“如何集成多个系统”，要先判断是只需要统一入口、共享数据，还是需要跨系统业务协同。

### 集成模式

常见集成模式：

| 模式 | 特点 | 风险 |
| --- | --- | --- |
| 点对点集成 | 系统之间直接调用 | 接口数量随系统增多快速膨胀，耦合高 |
| 共享数据库 | 多个系统读写同一数据库 | 破坏数据归属，表结构变化影响多个系统 |
| 文件交换 | 通过文件批量传输数据 | 实时性差，需要处理格式、校验、重传 |
| 消息发布订阅 | 发布事件，多个订阅者异步处理 | 需要处理重复、乱序、积压和最终一致 |
| 中心化总线 | 通过 ESB/EAI 平台做路由、转换和编排 | 总线可能成为瓶颈或单点，治理较重 |

点对点适合系统少、关系简单的场景。系统多、异构强、流程复杂时，应考虑 ESB、消息或服务化治理。

### 同步和异步

同步调用要求调用方等待结果，适合需要立即知道处理结果的场景，例如查询库存、确认支付结果。

异步调用把任务交给消息队列或后台任务，调用方不等待最终处理完成，适合通知、日志、报表、积分、图片处理。

| 对比点 | 同步 | 异步 |
| --- | --- | --- |
| 响应 | 调用方等待结果 | 调用方快速返回 |
| 耦合 | 调用方依赖被调用方可用 | 通过消息解耦 |
| 一致性 | 更容易做强一致 | 通常是最终一致 |
| 风险 | 下游慢会拖慢上游 | 消息积压、重复消费、处理延迟 |

### RPC、REST、WebService

RPC 像调用本地方法一样调用远程服务，适合内部服务间高性能通信。

REST 基于 HTTP 和资源建模，适合开放接口、跨语言系统和前后端分离。

WebService 常和 SOAP、WSDL、XML 相关，适合传统企业系统或异构系统集成，但报文较重。

| 方式 | 优点 | 局限 |
| --- | --- | --- |
| RPC | 性能好，接口语义直接 | 跨语言和开放性取决于框架 |
| REST | 简单开放，跨平台好 | 复杂操作和强事务表达不够直接 |
| WebService | 标准化强，适合传统集成 | XML 报文重，开发和调试成本高 |

### 消息队列

消息队列的核心作用：

- 异步处理：非核心任务移出主链路。
- 解耦：生产者不直接依赖消费者。
- 削峰填谷：高峰请求先进入队列，消费者按能力处理。
- 广播通知：一个事件可被多个消费者订阅。

消息队列的代价：

- 处理结果有延迟。
- 需要处理重复消息和幂等。
- 需要处理消息丢失、积压和死信。
- 系统链路变长，排查更复杂。

### 点对点消息和发布订阅

| 模式 | 含义 | 适用 |
| --- | --- | --- |
| 点对点 | 一个消息通常由一个消费者处理 | 任务处理、异步执行、订单扣库存 |
| 发布订阅 | 一个事件可被多个订阅者处理 | 订单创建后通知积分、优惠券、风控、日志 |

如果一个业务事件需要触发多个系统动作，发布订阅比让生产者逐个调用下游更解耦。

### 消息可靠性闭环

异步消息可靠性要覆盖生产、存储、消费和失败处理全链路。

常见机制：

1. 生产者可靠发送：发送失败重试，必要时使用本地消息表或事务消息。
2. Broker 持久化：消息写入可靠存储，避免中间件故障导致消息丢失。
3. 消费者确认：消费者处理成功后再提交 ack。
4. 失败重试：处理失败按策略重试，避免临时故障造成消息丢失。
5. 死信队列：多次失败后转入死信，供人工或补偿任务处理。
6. 幂等消费：使用消息 ID、业务唯一键、状态机或唯一约束防重复处理。
7. 监控告警：监控积压量、消费延迟、失败率和死信数量。

答题时不要只写“使用消息队列保证可靠”。消息队列只提供基础能力，业务还要设计幂等、补偿、监控和对账。

### 消息队列选型关注点

选择消息中间件时可从这些维度分析：

- 吞吐量和延迟。
- 消息持久化和可靠性。
- 顺序消息支持。
- 事务消息或延迟消息能力。
- 消费模型：点对点、发布订阅、消费组。
- 运维复杂度、监控告警和集群高可用。

考试通常不要求背具体产品细节，重点是说明为什么该消息中间件能力匹配业务场景。

### ESB

ESB 是企业服务总线，用于连接多个异构系统，提供协议转换、消息路由、服务编排、数据转换等能力。

它适合传统企业系统多、接口标准不统一、需要集中集成治理的场景。

局限是中心化总线可能成为性能瓶颈和单点，治理过重时会影响系统演进速度。

### EAI 企业应用集成

EAI 用于把企业内部多个异构应用连接起来，实现信息共享和业务协同。

常见能力：

- 适配器：封装不同系统、协议、数据格式和接口差异。
- 数据转换：在不同系统的数据模型之间映射和转换。
- 消息路由：按规则把消息发送到目标系统。
- 流程编排：把多个系统服务组合成业务流程。
- 集成监控：监控接口调用、失败、延迟和积压。

EAI 和 ESB 常一起出现。ESB 可以看作实现企业应用集成的一类基础设施。

### 适配器模式

适配器用于封装老系统或异构系统差异，对外提供统一接口。

适用场景：

- 老系统接口协议落后，但仍需复用。
- 多个外部系统接口格式不同，需要统一接入。
- 不希望调用方直接依赖遗留系统细节。

答题可写：通过适配器屏蔽遗留系统协议、字段和错误码差异，降低调用方与老系统的耦合。

### SOA 实施过程

SOA 不是把接口改成 WebService。它强调围绕业务能力识别服务，并通过契约和治理实现复用。

常见步骤：

1. 服务识别：从业务流程和业务能力中识别候选服务。
2. 服务分类：区分业务服务、应用服务、基础服务和数据服务。
3. 服务契约：定义接口、数据格式、错误码、版本和安全要求。
4. 服务实现：封装已有系统或新建服务，隐藏内部实现。
5. 服务编排：把多个服务组合成跨系统业务流程。
6. 服务治理：管理注册、发现、版本、权限、监控和 SLA。

易错点：SOA 适合企业级异构系统集成和服务复用，但集中治理过重会降低响应速度。

### 服务目录和服务注册

SOA 中常通过服务目录或服务注册库管理服务，微服务中常通过注册中心管理服务实例。

作用：

- 记录服务名称、能力、接口地址、契约、版本和负责人。
- 支持服务查找和复用，避免重复建设。
- 支持权限、SLA、调用统计和生命周期治理。

区别：

| 对比 | SOA 服务目录 | 微服务注册中心 |
| --- | --- | --- |
| 重点 | 服务资产管理、契约、复用和治理 | 运行时服务发现和实例动态变化 |
| 粒度 | 服务能力和接口 | 服务实例和地址 |
| 场景 | 企业级服务治理 | 微服务运行时调用 |

### Redis、Elasticsearch、对象存储

| 中间件 | 解决的问题 | 不适合 |
| --- | --- | --- |
| Redis | 缓存、分布式锁、计数器、会话共享、排行榜 | 替代关系数据库承载复杂事务 |
| Elasticsearch | 全文检索、复杂搜索、日志检索、聚合分析 | 替代数据库作为强一致主存储 |
| 对象存储 | 海量文件、图片、视频、备份、归档 | 频繁小事务更新和复杂查询 |

考试要避免“什么都用 Redis/ES”。中间件通常是补充能力，不应替代核心交易数据库。

### 中间件分类

中间件用于屏蔽底层差异、连接系统组件、提供通用技术能力。

常见分类：

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| 消息中间件 | 异步通信、解耦、削峰 | 消息队列、事件总线 |
| RPC 中间件 | 远程过程调用 | RPC 框架、服务调用框架 |
| 事务中间件 | 协调分布式事务或事务处理 | 事务管理器、TCC 框架 |
| 数据访问中间件 | 屏蔽数据库访问、分库分表、连接池 | 数据库中间件、连接池 |
| Web 应用服务器 | 承载 Web 应用运行 | 应用服务器、Servlet 容器 |
| 缓存中间件 | 提供高速数据访问 | Redis、Memcached |
| 搜索中间件 | 提供全文检索和聚合分析 | Elasticsearch |

考试问“中间件的作用”时，可答：屏蔽异构差异、提供公共服务、降低系统耦合、提高复用和可维护性。

### 紧耦合和松耦合

紧耦合表现：

- 调用方硬编码服务地址。
- 接口变化导致多个系统一起改。
- 下游服务故障直接拖垮上游。
- 多系统共享数据库表。

松耦合改进：

- 通过注册中心发现服务。
- 通过 API 网关统一入口。
- 通过消息队列异步解耦。
- 通过明确接口契约和版本管理降低变更影响。
- 避免多个系统直接共享数据库，改用服务接口或事件同步。

### API 网关和 ESB 区别

| 对比 | API 网关 | ESB |
| --- | --- | --- |
| 位置 | 客户端和后端服务之间 | 企业内部多个系统之间 |
| 重点 | 统一入口、认证、路由、限流、灰度 | 协议转换、消息路由、数据转换、服务编排 |
| 常见场景 | 微服务、移动端、开放平台 | 传统企业应用集成 |
| 风险 | 网关单点或瓶颈 | 总线中心化、治理过重 |

如果题目是“多个微服务对外提供统一入口”，优先 API 网关；如果是“多个异构老系统集成”，优先 ESB。

### 接口契约和版本管理

系统集成题常见风险是接口变化影响调用方。

治理方式：

- 明确接口契约：请求字段、响应字段、错误码、超时、重试规则。
- 保持向后兼容：新增字段尽量不破坏旧客户端。
- 版本管理：例如 `/api/v1/orders` 和 `/api/v2/orders`。
- 废弃策略：旧版本保留过渡期，通知调用方迁移。
- 契约测试：验证服务提供方和消费方对接口理解一致。

### 接口安全

系统集成接口通常跨系统、跨部门甚至对外开放，必须设计安全机制。

常见措施：

- 认证：确认调用方是谁，例如 Token、证书、AK/SK。
- 授权：限制调用方只能访问允许的接口和数据。
- HTTPS：防止传输过程被窃听和篡改。
- 签名：对请求参数和时间戳签名，防止伪造。
- 防重放：使用时间戳、随机数、请求唯一 ID。
- 限流：防止恶意或异常调用压垮系统。
- 审计：记录调用方、时间、接口、参数摘要、结果和异常。
- 脱敏：敏感字段传输、存储和日志中要控制暴露。

接口安全不能只靠内网隔离。跨系统集成中，身份、权限、签名、审计和限流都要考虑。

### 接口稳定性治理

接口治理要保证下游慢、失败或变更时不拖垮整体系统。

| 问题 | 治理措施 |
| --- | --- |
| 下游响应慢 | 超时控制、线程池隔离 |
| 临时失败 | 有限重试、退避策略 |
| 持续失败 | 熔断、降级、快速失败 |
| 流量过大 | 网关限流、调用方配额 |
| 版本变化 | 版本管理、兼容设计、灰度迁移 |
| 难以定位问题 | 日志、监控、告警、链路追踪 |

集成接口要明确 SLA，例如可用性、平均响应时间、超时时间、错误率和故障响应要求。

### 数据集成

数据集成关注不同系统之间的数据交换、同步、清洗和统一管理。

常见方式：

| 方式 | 说明 | 适用 |
| --- | --- | --- |
| ETL | 抽取、转换、加载到目标系统 | 数据仓库、离线报表 |
| ELT | 先加载到数据平台，再在平台内转换 | 大数据平台、湖仓场景 |
| CDC | 捕获数据库变更并同步 | 准实时数据同步 |
| 批量文件 | 定时导出导入文件 | 实时性要求低的对账、报表 |
| API 查询 | 通过接口按需获取数据 | 实时查询、数据量较小 |
| 事件同步 | 业务事件触发数据同步 | 最终一致、异步集成 |

数据集成要关注数据口径、主键映射、重复数据、数据质量、同步延迟和失败补偿。

### 主数据管理 MDM

主数据是多个系统共享的核心基础数据，例如客户、组织、人员、产品、供应商。

MDM 解决的问题：

- 多系统同一对象编码和口径不一致。
- 数据重复、冲突、质量差。
- 不知道哪个系统是权威数据源。

常见做法：

- 明确主数据标准和编码规则。
- 确定权威数据源。
- 建立数据质量校验和去重规则。
- 通过接口、消息或数据同步把主数据分发给其他系统。

### 消息顺序和重复消费

消息队列题常追问“顺序如何保证、重复如何处理”。

顺序消息常见做法：

- 同一业务键的消息发送到同一个分区或队列。
- 单个消费者按顺序消费该分区。
- 避免并发消费同一业务键导致乱序。

重复消费处理：

- 消费者根据消息 ID 去重。
- 业务操作设计为幂等。
- 数据库唯一约束兜底。
- 消费成功后再提交确认。

### 对象存储和文件服务器

对象存储适合海量非结构化文件，例如图片、视频、附件、备份。

优点：

- 容量扩展方便。
- 高可用和多副本由平台提供。
- 可以和 CDN 配合加速访问。
- 减少应用服务器本地磁盘依赖。

局限：

- 不适合频繁随机修改文件内部内容。
- 权限、生命周期、外链有效期需要设计。
- 元数据查询能力不如数据库，通常需要数据库保存文件索引。

### 集成题答题模板

```text
先分析系统间是实时强依赖还是异步弱依赖；实时查询或强交互用 REST/RPC，并配合超时、重试和熔断；非实时任务用消息队列异步解耦，并处理可靠投递、幂等消费和死信；异构老系统较多时可通过 ESB 做协议转换和服务编排；对外统一入口使用 API 网关做认证、路由、限流和审计。
```
