# 构件化复用与标准合规

## 考试中一般怎么考

1. 构件复用：问如何把公共能力抽成构件、服务或平台，减少重复建设。
2. 接口标准：要求说明接口、数据、日志、安全规范如何统一。
3. 构件化设计：问构件边界、接口、依赖、版本和可替换性。
4. 标准合规：问系统设计如何满足行业标准、数据安全、隐私和知识产权约束。
5. 复用风险：问复用带来的耦合、版本冲突、适配成本如何处理。
6. 依赖治理：问构件库、版本兼容、开源许可证和供应链安全。

## 针对考法梳理知识点

### 构件化的核心

构件是可复用、可替换、接口明确的软件单元。

常见构件：

- 统一认证。
- 文件服务。
- 消息通知。
- 支付能力。
- 报表组件。
- 审计日志。
- 工作流引擎。

答题重点不是“抽公共模块”，而是公共能力是否边界清楚、接口稳定、可独立演进。

### 构件、模块、服务和平台

| 形态 | 特点 |
| --- | --- |
| 模块 | 系统内部代码组织单元 |
| 构件 / 组件 | 可复用、接口明确、可替换的软件单元 |
| 服务 | 通过网络接口对外提供能力 |
| 平台 | 聚合多个公共能力，支撑多个业务系统 |

复用范围越大，治理要求越高。平台复用要配套版本、权限、监控、SLA 和运维机制。

### 构件设计要点

常见要点：

- 高内聚：构件内部职责集中。
- 低耦合：通过接口依赖，不依赖内部实现。
- 接口稳定：对外契约清楚，字段、错误码、版本明确。
- 可替换：调用方不直接绑定具体实现。
- 可部署：必要时能独立升级和扩展。

### 黑盒复用和白盒复用

| 方式 | 含义 | 风险 |
| --- | --- | --- |
| 黑盒复用 | 只通过接口使用，不修改内部实现 | 依赖接口质量和扩展点 |
| 白盒复用 | 修改源码或内部实现后使用 | 后续升级和维护成本高 |

优先黑盒复用。只有当构件无法满足扩展需求且源码可控时，才考虑白盒复用。

### 复用方式

| 方式 | 适合场景 | 风险 |
| --- | --- | --- |
| 代码库复用 | 小范围公共工具 | 版本分散、升级困难 |
| 构件复用 | 同类系统共享能力 | 接口设计要求高 |
| 服务复用 | 跨系统共享业务能力 | 网络调用和可用性风险 |
| 平台复用 | 多业务共用基础能力 | 平台治理成本高 |

易错点：复用不是越多越好。变化频繁且差异很大的业务强行复用，会导致公共构件越来越复杂。

### 构件库管理

构件库用于沉淀、发现和治理可复用资产。

常见管理内容：

- 构件分类和标签。
- 构件说明、接口文档和使用示例。
- 版本、依赖和兼容性说明。
- 负责人、维护状态和生命周期。
- 测试报告、安全扫描和许可证信息。
- 使用统计、缺陷反馈和升级通知。

没有构件库，复用容易变成“口口相传”，后续版本和依赖难以治理。

### 构件成熟度评估

复用前应评估构件是否值得复用。

| 维度 | 看什么 |
| --- | --- |
| 功能匹配 | 是否满足核心需求，扩展点是否足够 |
| 稳定性 | 是否在多个项目中验证过 |
| 接口质量 | 是否清晰、稳定、向后兼容 |
| 测试覆盖 | 是否有单元、集成和回归测试 |
| 安全性 | 是否有漏洞、敏感数据风险 |
| 文档 | 是否有接入文档、示例和 FAQ |
| 运维 | 是否有监控、日志、告警和 SLA |

复用不是只看“已有”。适配成本过高时，新建或局部复用可能更合理。

### 接口标准

接口标准常见内容：

- 协议和格式，例如 REST、JSON、HTTPS。
- 命名、字段类型、必填规则。
- 错误码、分页、排序、过滤规则。
- 超时、重试、幂等要求。
- 版本管理和废弃策略。
- 鉴权、签名、审计要求。

接口标准能降低集成成本，也便于测试、监控和治理。

### 版本兼容策略

构件和接口升级要避免影响调用方。

常见做法：

- 语义化版本：主版本表示不兼容变化，次版本表示兼容新增，修订号表示缺陷修复。
- 向后兼容：新增字段不破坏旧客户端。
- 废弃周期：旧接口保留过渡期，通知调用方迁移。
- 兼容测试：验证新版本不破坏已有调用方。
- 回滚机制：新版本异常时能恢复旧版本。

不要随意删除字段、改变字段语义或修改错误码含义。

### 数据标准

数据标准常见内容：

- 主数据编码，例如客户、组织、产品、设备。
- 字段命名、类型、长度、枚举值。
- 指标口径和统计周期。
- 数据质量规则。
- 数据分级分类和访问权限。

易错点：只统一接口不统一数据，系统之间仍会出现口径不一致和重复维护。

### 日志和运维标准

常见标准：

- 统一日志格式，包含 traceId、用户、接口、耗时、结果。
- 统一监控指标，例如 QPS、延迟、错误率、资源利用率。
- 统一告警等级和处理流程。
- 统一发布、回滚、配置和备份规范。

这些标准直接服务可观测性、可维护性和故障定位。

### 标准体系

标准化不只包括接口标准。

| 标准 | 内容 |
| --- | --- |
| 技术标准 | 技术栈、框架、中间件、数据库和部署规范 |
| 接口标准 | 协议、格式、错误码、版本、安全认证 |
| 数据标准 | 主数据、字段、编码、指标口径和质量规则 |
| 安全标准 | 身份、权限、加密、审计、漏洞管理 |
| 运维标准 | 日志、监控、告警、发布、备份和应急 |
| 测试标准 | 测试类型、覆盖要求、质量门禁 |

标准要有例外审批机制。特殊场景可以例外，但要记录原因、影响和退出计划。

### 标准合规

案例题里合规通常表现为约束条件。

常见答题点：

- 涉及个人信息时，要做最小采集、授权同意、脱敏、加密和访问审计。
- 涉及行业监管时，要满足数据留存、审计追踪、权限控制要求。
- 使用第三方软件或组件时，要关注许可证和知识产权风险。
- 跨境、跨机构共享数据时，要明确授权、边界和安全传输。

### 依赖和供应链安全

构件复用会带来依赖风险。

常见风险：

- 依赖版本冲突。
- 第三方库存在安全漏洞。
- 开源许可证不兼容商业使用。
- 构件无人维护。
- 构建和发布链路被篡改。

治理措施：

- 建立依赖清单和软件物料清单 SBOM。
- 定期做漏洞扫描和版本升级。
- 审查开源许可证和知识产权风险。
- 使用可信制品仓库，控制发布权限。
- 对关键构件做签名、校验和来源追踪。

### 复用经济性

复用要比较收益和成本。

收益：

- 减少重复开发。
- 统一用户体验和技术标准。
- 降低集成和运维成本。
- 提升质量和一致性。

成本：

- 抽象和设计成本。
- 接入适配成本。
- 版本兼容和维护成本。
- 平台治理和支持成本。

如果业务差异大、变化频繁，强行复用可能导致公共构件膨胀，反而降低效率。

### 构件化复用答题模板

```text
识别多个系统重复使用的认证、消息、文件、报表、审计等公共能力，将其封装为接口稳定、职责清晰的构件或公共服务；通过统一接口标准、数据标准、日志标准和安全规范降低集成成本；通过版本管理、兼容策略、监控告警和权限控制降低复用带来的耦合和运维风险；涉及个人信息、行业监管和第三方组件时补充合规与知识产权控制。
```
