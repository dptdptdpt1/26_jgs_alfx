# 项目与过程

## 考试中一般怎么考

1. 配置管理：问配置项、基线、变更控制、构建发布、配置审计。
2. 软件过程模型：问瀑布、原型、增量、迭代、螺旋、敏捷适用场景。
3. 项目管理：问范围、进度、成本、沟通和干系人管理。
4. 风险管理：问风险识别、分析、应对、监控的闭环。
5. 测试管理：问不同测试类型验证什么，缺陷如何跟踪闭环。
6. 质量保证：问评审、测试、缺陷跟踪、持续改进如何保证质量。
7. 持续集成：问自动构建、自动测试、自动部署和反馈机制。

## 针对考法梳理知识点

### 配置管理的核心

配置管理不是简单使用 Git。它管理的是项目中需要受控的配置项，例如代码、需求文档、设计文档、配置文件、测试用例、构建脚本、发布包。

配置管理的关键机制：

1. 标识配置项，明确哪些内容受控。
2. 建立基线，形成经评审确认的版本。
3. 控制变更，变更要申请、分析、审批、实施、验证。
4. 记录版本，保证可追溯。
5. 配置审计，检查配置项是否完整、一致。

配置管理常见活动：

| 活动 | 作用 |
| --- | --- |
| 配置项标识 | 确定哪些文档、代码、测试、脚本和发布包受控 |
| 版本控制 | 记录配置项的不同版本和修改历史 |
| 变更控制 | 防止随意修改已受控内容 |
| 配置状态报告 | 说明配置项当前版本、变更状态和发布状态 |
| 配置审计 | 检查配置项是否完整、一致、符合基线 |

配置库用于统一保存和管理配置项。考试里不要把配置管理等同于代码版本管理，它还包括需求、设计、测试、构建和发布物。

### 基线

基线是经过正式评审和确认的阶段性成果。建立基线后，不能随意修改，必须通过变更控制。

常见基线包括需求基线、设计基线、测试基线、发布基线。

考试里如果问为什么要建立基线，答：控制变更、保证一致性、支持追溯、降低随意修改风险。

### 软件过程模型

不同过程模型适合不同项目特点。

| 模型 | 特点 | 适用 |
| --- | --- | --- |
| 瀑布模型 | 阶段顺序清晰，文档完整 | 需求明确、变更少、监管要求强 |
| 原型模型 | 先做原型，让用户确认需求 | 需求不清、界面交互复杂 |
| 增量模型 | 分批交付可用功能 | 希望尽早交付核心能力 |
| 迭代模型 | 反复分析、设计、实现和评估 | 需求逐步明确，需要持续改进 |
| 螺旋模型 | 迭代开发并强调风险分析 | 大型复杂、高风险项目 |
| 敏捷模型 | 小步快跑、持续反馈、拥抱变化 | 需求变化快、业务反馈频繁 |

速判：

- 需求非常明确：瀑布。
- 需求说不清：原型。
- 需要先上线核心功能：增量。
- 风险高、规模大：螺旋。
- 变化快、强调协作和快速反馈：敏捷。

### 敏捷开发

敏捷强调短周期迭代、客户协作、持续交付和响应变化。

Scrum 常见角色：

- 产品负责人 Product Owner：维护产品待办列表，确定需求优先级。
- Scrum Master：保障 Scrum 流程执行，移除团队障碍。
- 开发团队：负责设计、开发、测试和交付增量。

Scrum 常见活动：

- 产品待办列表 Product Backlog：按优先级排列的需求列表。
- Sprint：固定时长迭代，通常 1 到 4 周。
- Sprint 计划会：确定本轮迭代目标和任务。
- 每日站会：同步进展、计划和障碍。
- Sprint 评审会：向干系人展示迭代成果。
- Sprint 回顾会：总结过程问题并改进。

敏捷不是没有计划和文档，而是用更短反馈周期控制需求变化和交付风险。

### 风险管理闭环

风险管理不是“加强管理”。它有固定闭环：

1. 风险识别：找出可能影响目标的事件。
2. 风险分析：评估概率、影响和优先级。
3. 风险应对：规避、减轻、转移或接受。
4. 风险监控：跟踪风险状态，必要时调整措施。

案例题里如果给出人员不足、需求频繁变化、关键技术不成熟，都可以按这个闭环回答。

### 范围管理

范围管理解决“做什么、不做什么”的问题。

常见活动：

1. 收集需求，明确业务目标和边界。
2. 定义范围，形成范围说明书。
3. 创建 WBS，把项目工作分解成可管理的工作包。
4. 范围确认，由用户或干系人正式确认交付内容。
5. 范围控制，通过变更控制防止范围蔓延。

范围蔓延是未经评审和批准不断增加工作内容。案例题中如果出现“客户不断加需求、工期不变”，可答：建立范围基线、变更控制流程、影响分析、优先级排序，必要时调整工期、成本或范围。

### 进度管理

进度管理关注任务顺序、工期、资源和关键路径。

常见活动：

1. 定义活动。
2. 排列活动顺序，识别依赖关系。
3. 估算活动资源。
4. 估算活动持续时间。
5. 制定进度计划。
6. 控制进度，跟踪偏差并纠偏。

常见工具：

- 甘特图：直观展示任务开始时间、结束时间和进度。
- PERT / 网络图：展示任务依赖和关键路径。
- 里程碑：标记关键交付节点。

关键路径上的任务延期会直接影响总工期。压缩进度常见办法包括赶工、快速跟进、增加资源、裁剪范围，但要同时分析成本和质量风险。

### 成本管理

成本管理关注项目预算和费用控制。

常见活动：

1. 成本估算：估算人员、软硬件、云资源、外包、培训、运维等费用。
2. 成本预算：形成成本基准。
3. 成本控制：跟踪实际成本和预算偏差，采取纠偏措施。

成本失控常见原因：需求范围扩大、估算不足、返工多、外部依赖延期、质量问题导致修复成本增加。

答题时可以从范围、进度、质量、资源和风险联动分析，不要只写“加强成本控制”。

### 干系人和沟通管理

干系人包括用户、客户、业务部门、开发团队、测试团队、运维、安全合规、供应商和管理层。

沟通管理常见做法：

- 识别干系人，明确每类干系人的关注点和影响力。
- 制定沟通计划，明确沟通内容、频率、渠道和责任人。
- 定期同步项目状态、风险、问题和变更。
- 对关键需求、范围和验收标准形成书面确认。
- 对跨部门冲突建立协调和升级机制。

案例题中如果出现“部门意见不一致、用户参与不足、信息传递不及时”，可以从干系人识别、沟通计划、评审确认和问题升级机制回答。

### 测试类型

单元测试验证模块内部逻辑。

集成测试验证模块或服务之间的接口和协作。

系统测试验证系统整体是否满足需求。

性能测试验证响应时间、吞吐量、并发能力和资源占用。

安全测试验证权限、漏洞、数据保护和接口安全。

回归测试验证修改后原有功能是否被破坏。

验收测试验证系统是否满足合同、需求规格说明和用户验收标准。

α 测试通常由用户或测试人员在开发方环境中进行。

β 测试通常由真实用户在实际使用环境中进行。

测试阶段常见顺序：

```text
单元测试 -> 集成测试 -> 系统测试 -> 验收测试
```

### 缺陷管理流程

缺陷管理要形成闭环。

常见流程：

1. 提交缺陷，记录复现步骤、环境、输入数据、实际结果和期望结果。
2. 确认缺陷，判断是否有效、严重程度和优先级。
3. 分派缺陷，明确责任人和修复版本。
4. 修复缺陷，提交代码和说明。
5. 回归验证，确认缺陷已修复且没有引入新问题。
6. 关闭缺陷，记录处理结果。
7. 统计分析，发现高发模块和过程问题。

缺陷严重程度表示影响有多大，优先级表示应该多快修。严重程度高不一定优先级最高，但核心业务阻塞通常两者都高。

### 质量保证

质量保证关注过程是否能持续产出符合要求的软件。

常见机制：

- 标准规范：统一开发、评审、测试、发布要求。
- 评审：在需求、设计、代码阶段提前发现问题。
- 测试：验证功能和质量属性。
- 缺陷管理：记录、跟踪、修复、验证缺陷。
- 持续改进：根据缺陷和问题改进过程。

### 评审类型

评审是尽早发现问题的质量保证手段。

常见评审：

| 评审 | 重点 |
| --- | --- |
| 需求评审 | 需求是否正确、完整、一致、可验证 |
| 设计评审 | 架构、接口、数据、质量属性是否满足需求 |
| 代码评审 | 代码质量、规范、安全、可维护性 |
| 测试评审 | 测试计划、测试用例、覆盖范围是否充分 |
| 发布评审 | 缺陷、配置、部署、回滚、用户文档是否就绪 |

评审不能代替测试，测试也不能代替评审。评审偏提前发现问题，测试偏验证实际运行结果。

### 持续集成

持续集成的机制是频繁合并代码，并通过自动构建、自动测试及时发现问题。

它解决的是集成风险后置的问题。越晚集成，冲突和缺陷越难定位。

考试答题可写：代码提交后触发构建、执行自动化测试、生成反馈报告，失败时及时修复。

### 变更控制流程

变更控制不是“同意后修改”这么简单，常见流程：

1. 提出变更申请，说明原因和内容。
2. 分析影响，包括范围、成本、进度、质量、风险。
3. 评审和审批，决定接受、拒绝或延期。
4. 修改相关配置项，包括需求、设计、代码、测试用例。
5. 验证变更结果，执行回归测试。
6. 更新基线和记录，保证可追溯。

案例题中如果出现“客户临时新增需求导致进度失控”，可答建立变更控制委员会、影响分析、审批流程和基线管理。

### 风险分类和应对

| 风险 | 例子 | 应对 |
| --- | --- | --- |
| 需求风险 | 需求频繁变更、不明确 | 原型确认、需求评审、变更控制 |
| 技术风险 | 新技术不成熟、性能达不到 | 技术预研、原型验证、替代方案 |
| 人员风险 | 关键人员离职、能力不足 | 知识共享、交叉培训、备份人员 |
| 进度风险 | 估算不足、依赖延期 | 里程碑跟踪、范围裁剪、资源调整 |
| 质量风险 | 缺陷多、测试不足 | 评审、自动化测试、缺陷闭环 |
| 外部风险 | 第三方接口不稳定 | SLA、接口 Mock、降级和重试 |

应对策略：

- 规避：改变方案消除风险。
- 减轻：降低概率或影响。
- 转移：通过外包、保险、合同转移部分影响。
- 接受：风险较小或成本过高时接受并监控。

### 测试用例设计常见方法

| 方法 | 适用 |
| --- | --- |
| 等价类划分 | 输入范围大，选择代表值 |
| 边界值分析 | 数值范围、长度限制 |
| 判定表 | 多条件组合 |
| 因果图 | 输入条件之间有逻辑关系 |
| 场景法 | 业务流程、主流程和异常流程 |

案例题如果问“如何补充测试”，可以从功能、接口、性能、安全、兼容、异常、回归这些维度写。

### CMMI 过程改进

CMMI 用于评价和改进组织的软件过程能力。

五个成熟度等级：

| 等级 | 名称 | 特点 |
| --- | --- | --- |
| 1 | 初始级 | 过程混乱，依赖个人能力 |
| 2 | 已管理级 | 项目层面有计划、跟踪和管理 |
| 3 | 已定义级 | 组织级标准过程已建立 |
| 4 | 量化管理级 | 用度量数据进行过程控制 |
| 5 | 优化级 | 持续过程改进和缺陷预防 |

考试里如果问“如何提升组织软件过程能力”，可以答：建立标准过程、度量体系、质量保证、配置管理、缺陷分析和持续改进机制。

### 外包和供应商风险

系统集成项目常涉及外包、供应商和第三方服务。

常见风险：

- 第三方交付延期，影响总体进度。
- 质量不达标，导致返工和集成失败。
- 接口文档不完整，联调成本高。
- 知识产权、源码归属和数据安全责任不清。
- SLA、验收标准和故障响应要求不明确。

应对措施：

- 合同中明确范围、交付物、质量标准、验收标准和违约责任。
- 明确接口规范、联调计划、数据安全和保密要求。
- 建立阶段性验收和里程碑付款机制。
- 对关键第三方能力准备替代方案或降级方案。

### DevOps 和项目过程的关系

DevOps 不是只买工具，而是用自动化流水线把开发、测试、发布、运维连接起来。

常见落地点：

- 代码提交触发构建。
- 自动化测试尽早发现缺陷。
- 制品统一管理，保证发布物可追溯。
- 自动部署减少人工操作错误。
- 监控反馈生产问题，推动持续改进。

它提升交付效率，但前提是测试、配置、环境和发布流程标准化。
