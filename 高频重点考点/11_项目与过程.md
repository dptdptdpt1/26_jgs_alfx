# 项目与过程

## 考试中一般怎么考

1. 配置管理：问配置项、基线、变更控制、构建发布、配置审计。
2. 风险管理：问风险识别、分析、应对、监控的闭环。
3. 测试管理：问不同测试类型验证什么。
4. 质量保证：问评审、测试、缺陷跟踪、持续改进如何保证质量。
5. 持续集成：问自动构建、自动测试、自动部署和反馈机制。

## 针对考法梳理知识点

### 配置管理的核心

配置管理不是简单使用 Git。它管理的是项目中需要受控的配置项，例如代码、需求文档、设计文档、配置文件、测试用例、构建脚本、发布包。

配置管理的关键机制：

1. 标识配置项，明确哪些内容受控。
2. 建立基线，形成经评审确认的版本。
3. 控制变更，变更要申请、分析、审批、实施、验证。
4. 记录版本，保证可追溯。
5. 配置审计，检查配置项是否完整、一致。

### 基线

基线是经过正式评审和确认的阶段性成果。建立基线后，不能随意修改，必须通过变更控制。

常见基线包括需求基线、设计基线、测试基线、发布基线。

考试里如果问为什么要建立基线，答：控制变更、保证一致性、支持追溯、降低随意修改风险。

### 风险管理闭环

风险管理不是“加强管理”。它有固定闭环：

1. 风险识别：找出可能影响目标的事件。
2. 风险分析：评估概率、影响和优先级。
3. 风险应对：规避、减轻、转移或接受。
4. 风险监控：跟踪风险状态，必要时调整措施。

案例题里如果给出人员不足、需求频繁变化、关键技术不成熟，都可以按这个闭环回答。

### 测试类型

单元测试验证模块内部逻辑。

集成测试验证模块或服务之间的接口和协作。

系统测试验证系统整体是否满足需求。

性能测试验证响应时间、吞吐量、并发能力和资源占用。

安全测试验证权限、漏洞、数据保护和接口安全。

回归测试验证修改后原有功能是否被破坏。

### 质量保证

质量保证关注过程是否能持续产出符合要求的软件。

常见机制：

- 标准规范：统一开发、评审、测试、发布要求。
- 评审：在需求、设计、代码阶段提前发现问题。
- 测试：验证功能和质量属性。
- 缺陷管理：记录、跟踪、修复、验证缺陷。
- 持续改进：根据缺陷和问题改进过程。

### 持续集成

持续集成的机制是频繁合并代码，并通过自动构建、自动测试及时发现问题。

它解决的是集成风险后置的问题。越晚集成，冲突和缺陷越难定位。

考试答题可写：代码提交后触发构建、执行自动化测试、生成反馈报告，失败时及时修复。

### 变更控制流程

变更控制不是“同意后修改”这么简单，常见流程：

1. 提出变更申请，说明原因和内容。
2. 分析影响，包括范围、成本、进度、质量、风险。
3. 评审和审批，决定接受、拒绝或延期。
4. 修改相关配置项，包括需求、设计、代码、测试用例。
5. 验证变更结果，执行回归测试。
6. 更新基线和记录，保证可追溯。

案例题中如果出现“客户临时新增需求导致进度失控”，可答建立变更控制委员会、影响分析、审批流程和基线管理。

### 风险分类和应对

| 风险 | 例子 | 应对 |
| --- | --- | --- |
| 需求风险 | 需求频繁变更、不明确 | 原型确认、需求评审、变更控制 |
| 技术风险 | 新技术不成熟、性能达不到 | 技术预研、原型验证、替代方案 |
| 人员风险 | 关键人员离职、能力不足 | 知识共享、交叉培训、备份人员 |
| 进度风险 | 估算不足、依赖延期 | 里程碑跟踪、范围裁剪、资源调整 |
| 质量风险 | 缺陷多、测试不足 | 评审、自动化测试、缺陷闭环 |
| 外部风险 | 第三方接口不稳定 | SLA、接口 Mock、降级和重试 |

应对策略：

- 规避：改变方案消除风险。
- 减轻：降低概率或影响。
- 转移：通过外包、保险、合同转移部分影响。
- 接受：风险较小或成本过高时接受并监控。

### 测试用例设计常见方法

| 方法 | 适用 |
| --- | --- |
| 等价类划分 | 输入范围大，选择代表值 |
| 边界值分析 | 数值范围、长度限制 |
| 判定表 | 多条件组合 |
| 因果图 | 输入条件之间有逻辑关系 |
| 场景法 | 业务流程、主流程和异常流程 |

案例题如果问“如何补充测试”，可以从功能、接口、性能、安全、兼容、异常、回归这些维度写。

### DevOps 和项目过程的关系

DevOps 不是只买工具，而是用自动化流水线把开发、测试、发布、运维连接起来。

常见落地点：

- 代码提交触发构建。
- 自动化测试尽早发现缺陷。
- 制品统一管理，保证发布物可追溯。
- 自动部署减少人工操作错误。
- 监控反馈生产问题，推动持续改进。

它提升交付效率，但前提是测试、配置、环境和发布流程标准化。
