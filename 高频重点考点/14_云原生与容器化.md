# 云原生与容器化

## 考试中一般怎么考

1. 容器化改造：问 Docker 解决什么问题，镜像、容器、仓库如何配合。
2. 云服务和部署模式：问 IaaS、PaaS、SaaS，公有云、私有云、混合云、多云如何选择。
3. Kubernetes：问编排、服务发现、滚动升级、弹性伸缩、故障自愈。
4. DevOps：问 CI/CD、自动构建、自动测试、自动部署如何缩短交付周期。
5. 发布策略：比较灰度发布、蓝绿发布、滚动发布。
6. 云上高可用：问多可用区、自动伸缩、云数据库、对象存储如何提高可用性。
7. 云原生治理：问可观测、服务网格、资源调度、镜像安全和运行时安全。

## 针对考法梳理知识点

### 云原生核心理念

云原生不是简单把系统部署到云服务器上，而是让系统更适合云环境中的弹性、自动化和快速交付。

常见关键词：

- 微服务：按业务能力拆分，支持独立开发和部署。
- 容器化：把应用和依赖打包成镜像，保证环境一致。
- DevOps / CI/CD：自动构建、测试、部署和反馈。
- 声明式 API：声明期望状态，由平台自动调谐到目标状态。
- 弹性伸缩：根据负载自动扩缩容。
- 不可变基础设施：通过新镜像替换旧实例，而不是手工修改运行环境。
- 可观测性：通过日志、指标、链路追踪和告警定位问题。

考试答云原生不要只写 Docker 或 Kubernetes，要把容器、编排、自动化交付、弹性和可观测串起来。

### IaaS、PaaS、SaaS

| 模式 | 用户主要管理 | 云厂商主要提供 | 例子 |
| --- | --- | --- | --- |
| IaaS | 操作系统、运行环境、应用和数据 | 计算、存储、网络、虚拟化 | 云服务器、云硬盘、VPC |
| PaaS | 应用和数据 | 运行平台、中间件、弹性、运维能力 | 容器平台、数据库服务、函数平台 |
| SaaS | 业务配置和使用 | 完整软件应用 | 在线办公、CRM、邮件系统 |

速判：

- 需要自己装系统和部署运行环境：IaaS。
- 只关心应用，平台托管运行环境：PaaS。
- 直接使用软件功能：SaaS。

### 公有云、私有云、混合云、多云

| 模式 | 特点 | 适用 |
| --- | --- | --- |
| 公有云 | 资源由云厂商提供，弹性强，按量付费 | 互联网业务、快速扩展、成本弹性 |
| 私有云 | 资源由组织专用，控制力强 | 政务、金融、强合规和数据敏感场景 |
| 混合云 | 私有云和公有云结合 | 核心数据留本地，弹性业务上公有云 |
| 多云 | 使用多个云厂商资源 | 降低厂商绑定，提高容灾和议价能力 |

混合云和多云会增加网络、身份、数据同步、监控和运维复杂度，不能只写“更安全、更可靠”。

### Docker

Docker 把应用及其运行依赖打包成镜像，容器基于镜像运行。

它解决的是环境不一致、部署复杂、迁移困难的问题。

常见概念：

- 镜像：只读模板，包含应用和依赖。
- 容器：镜像运行后的实例。
- 镜像仓库：存放和分发镜像。
- Dockerfile：定义镜像构建过程。

容器不是虚拟机。容器共享宿主机内核，启动更快、资源开销更小，但隔离性弱于虚拟机。

### 镜像构建和安全

镜像是容器交付的核心制品。

常见要求：

- 使用精简、可信的基础镜像，减少体积和漏洞面。
- 利用镜像分层缓存，提高构建和拉取效率。
- 不把密码、密钥、证书写入镜像。
- 镜像推送到私有镜像仓库，控制访问权限。
- 对镜像做漏洞扫描和签名校验。
- 通过版本标签管理镜像，保证发布可追溯。

考试里如果问容器化安全，镜像来源、漏洞扫描、敏感信息、仓库权限和运行时最小权限都要考虑。

### Kubernetes

Kubernetes 用于容器编排，负责部署、调度、扩缩容、服务发现和故障恢复。

常见机制：

- Pod：最小调度单元，通常运行一个或多个紧密相关容器。
- Deployment：声明副本数量和升级策略。
- Service：为 Pod 提供稳定访问入口和负载均衡。
- ConfigMap/Secret：管理配置和敏感信息。
- HPA：根据 CPU、内存或自定义指标自动扩缩容。

考试问“为什么 K8s 提高可用性”，要写：副本机制、健康检查、故障自动拉起、滚动更新、服务发现和负载均衡。

### Kubernetes 核心对象

| 对象 | 作用 |
| --- | --- |
| Node | 集群工作节点，运行 Pod |
| Namespace | 逻辑隔离资源，适合区分环境、团队或项目 |
| Pod | 最小调度单元，包含一个或多个容器 |
| ReplicaSet | 保证指定数量 Pod 副本运行 |
| Deployment | 管理无状态应用的副本、滚动升级和回滚 |
| StatefulSet | 管理有状态应用，提供稳定网络标识和存储 |
| DaemonSet | 在每个或指定节点上运行一个 Pod，适合日志、监控 Agent |
| Job / CronJob | 一次性任务或定时任务 |
| Service | 为 Pod 提供稳定访问入口 |
| Ingress | 管理 HTTP/HTTPS 入口路由 |
| ConfigMap / Secret | 管理普通配置和敏感配置 |
| PV / PVC | 管理持久化存储 |

补图题中如果看到“每个节点都要运行日志采集器”，优先 DaemonSet；看到“定时清理任务”，优先 CronJob。

### Service 和 Ingress

Service 解决 Pod 地址变化带来的访问不稳定问题。

常见 Service 类型：

| 类型 | 作用 |
| --- | --- |
| ClusterIP | 集群内部访问，默认类型 |
| NodePort | 通过节点端口暴露服务 |
| LoadBalancer | 通过云负载均衡器对外暴露服务 |

Ingress 负责七层 HTTP/HTTPS 入口路由，可根据域名和路径把请求转发到不同 Service。

速判：集群内部服务互调用 Service；对外 HTTP 统一入口用 Ingress；云上对外暴露高可用入口常用 LoadBalancer。

### Deployment 和 StatefulSet

| 对比 | Deployment | StatefulSet |
| --- | --- | --- |
| 适用 | 无状态应用 | 有状态应用 |
| Pod 标识 | 副本可替换，名称不稳定 | Pod 有稳定名称和顺序 |
| 存储 | 通常不绑定固定存储 | 通常绑定独立持久化存储 |
| 例子 | Web 服务、API 服务 | 数据库、ZooKeeper、Kafka |

应用服务尽量用 Deployment 并保持无状态。数据库等有状态组件上 K8s 要特别关注持久化、备份、恢复和运维复杂度。

### ConfigMap 和 Secret

ConfigMap 存普通配置，例如配置文件、环境变量、开关和非敏感参数。

Secret 存敏感信息，例如密码、Token、证书和密钥。

注意点：

- 配置应外置化，不写死在镜像中。
- Secret 也要配合 RBAC、加密存储和最小权限。
- 配置变更要有版本、审计和回滚机制。

### 容器网络和存储

容器网络常见概念：

- Pod IP：Pod 在集群网络中的地址，Pod 重建后可能变化。
- Service：为一组 Pod 提供稳定虚拟 IP 和负载均衡。
- CNI：容器网络接口，负责 Pod 网络接入和网络策略实现。
- NetworkPolicy：控制 Pod 之间或 Pod 与外部的访问规则。

容器存储常见概念：

- PV：集群中的持久卷资源。
- PVC：应用对存储的申请。
- CSI：容器存储接口，用于接入不同存储系统。
- 对象存储：适合图片、视频、附件、备份等非结构化数据。

容器本地文件随 Pod 重建可能丢失。需要持久化的数据应使用 PVC、数据库或对象存储。

### 资源限制和调度

Kubernetes 通过资源声明和调度规则管理集群资源。

常见机制：

- requests：容器期望获得的最小资源，用于调度决策。
- limits：容器最多能使用的资源，防止抢占过多资源。
- ResourceQuota：限制命名空间总资源使用。
- 亲和性 / 反亲和性：控制 Pod 尽量部署在一起或分散部署。
- 污点 / 容忍：让特定节点只运行特定 Pod。

如果 Pod 调度失败，常见原因是资源不足、节点选择器不匹配、污点未容忍或 PVC 无法绑定。

### 弹性伸缩

弹性伸缩根据负载自动增加或减少实例。

它适合流量波动明显的系统，例如电商活动、在线教育开课、政务集中申报。

前提是应用尽量无状态，状态放到数据库、缓存或对象存储中。否则新增实例无法直接承接请求。

弹性伸缩常见对象：

- HPA：根据 CPU、内存或业务指标调整 Pod 副本数。
- VPA：调整 Pod 的资源请求和限制。
- Cluster Autoscaler：根据 Pod 调度需求增减集群节点。

弹性伸缩要配合容量指标、冷启动时间和限流降级策略。扩容不是瞬时完成的，高峰流量仍可能需要队列削峰。

### DevOps 和 CI/CD

DevOps 强调开发、测试、运维协作，通过自动化流水线提高交付效率和质量。

CI/CD 常见流程：

1. 提交代码触发流水线。
2. 自动构建。
3. 自动执行单元测试、集成测试和静态检查。
4. 构建镜像或发布包。
5. 部署到测试、预发或生产环境。
6. 监控发布结果，失败时回滚。

它解决的是手工部署容易出错、反馈慢、版本不可追溯的问题。

### 灰度、蓝绿、滚动发布

| 发布方式 | 机制 | 优点 | 局限 |
| --- | --- | --- | --- |
| 灰度发布 | 先让少量用户或流量使用新版本 | 风险可控，便于验证 | 需要流量控制和监控 |
| 蓝绿发布 | 新旧两套环境并存，切换流量 | 回滚快，环境隔离好 | 资源成本较高 |
| 滚动发布 | 分批替换实例 | 资源成本低，过程平滑 | 新旧版本短期共存，需兼容 |

### 云上高可用

云上高可用常见组合：

- 多可用区部署，避免单机房故障。
- 负载均衡，把流量分发到多个实例。
- 自动伸缩，应对流量波动。
- 云数据库主备或多副本，提高数据可用性。
- 对象存储保存静态文件和备份。
- 监控告警和日志服务，及时发现异常。

考试答云架构时，不要只写“上云”。要说明计算、存储、网络、数据库和监控分别如何提升质量属性。

### Kubernetes 故障自愈细化

Kubernetes 的自愈能力来自声明式管理和控制循环。

常见机制：

- 副本数声明：期望运行 3 个副本，少了就自动拉起。
- 存活探针：容器异常时重启容器。
- 就绪探针：未准备好的 Pod 不接收流量。
- 节点故障迁移：节点不可用时，Pod 可调度到其他节点。
- 滚动更新：逐步替换旧版本实例，降低发布中断。

答题时注意：Kubernetes 能拉起进程和调度容器，但不能自动修复业务逻辑错误，应用仍要有监控、日志和回滚策略。

### 容器化改造注意点

不是所有系统直接打包成镜像就算云原生。

改造要点：

- 应用无状态化，把会话、文件、状态放到外部存储。
- 配置外置化，不把环境配置写死到镜像。
- 日志标准输出，便于平台收集。
- 健康检查接口，支持探针判断存活和就绪。
- 优雅停机，处理正在执行的请求。
- 镜像分层和精简，降低构建和拉取成本。

### 云原生可观测性

容器和微服务环境中实例多、生命周期短，必须建设可观测能力。

三类核心数据：

| 类型 | 作用 |
| --- | --- |
| 日志 Logs | 记录事件和错误，适合问题排查 |
| 指标 Metrics | 观察 CPU、内存、QPS、延迟、错误率等趋势 |
| 链路追踪 Traces | 跟踪一次请求跨服务调用路径和耗时 |

配套机制：

- 统一采集标准输出日志。
- 监控 Pod、节点、服务和业务指标。
- 为跨服务请求传递 Trace ID。
- 设置告警阈值和发布观察窗口。

发布、扩缩容和故障恢复都要依赖可观测数据判断是否正常。

### 服务网格 Service Mesh

服务网格把服务治理能力从业务代码中下沉到基础设施层，常通过 Sidecar 代理处理服务间流量。

常见能力：

- 流量治理：灰度、路由、限流、熔断、重试。
- 安全通信：mTLS、服务间身份认证。
- 可观测性：调用指标、日志、链路追踪。
- 策略控制：访问控制、流量规则统一管理。

优点是业务代码侵入小，治理能力统一。代价是架构复杂、资源开销增加、运维门槛提高。

### 云原生安全

云原生安全要覆盖镜像、集群、网络、运行时和权限。

常见措施：

- 镜像安全：可信基础镜像、漏洞扫描、签名、私有仓库。
- 权限控制：RBAC、最小权限、服务账号隔离。
- Secret 管理：敏感信息加密存储，避免写入镜像和日志。
- 网络隔离：Namespace、NetworkPolicy、入口限流和访问控制。
- 运行时安全：非 root 用户运行、只读文件系统、限制特权容器。
- 审计和监控：记录关键操作，监控异常容器行为。

考试中不要只答“用 Secret 存密码”。Secret 还需要权限控制、加密、审计和最小暴露。

### 云数据库和自建数据库

云数据库由云平台托管备份、高可用、监控、扩容和补丁。

优点：

- 运维成本低。
- 主备、高可用、备份能力成熟。
- 可以按需扩容。
- 监控告警和恢复能力较完善。

限制：

- 成本和厂商绑定。
- 参数、插件、底层控制能力不如自建灵活。
- 跨云迁移需要评估兼容性和数据迁移成本。

### 发布策略选择

| 场景 | 建议 |
| --- | --- |
| 新版本风险高，只想让少量用户试用 | 灰度发布 |
| 需要快速回滚，资源允许两套环境 | 蓝绿发布 |
| 普通服务升级，资源有限 | 滚动发布 |
| 数据库结构有不兼容变更 | 先做兼容字段和双写，再灰度应用 |

发布题要补监控指标：错误率、响应时间、业务成功率、资源利用率。发现异常后要能自动或手动回滚。

### Serverless

Serverless 让开发者更少关注服务器和运行环境，由平台按事件触发、自动扩缩容、按量计费。

常见形态：

- 函数计算：事件触发短任务。
- 托管后端服务：对象存储、消息、数据库、API 网关等组合。

适合：

- 图片处理、文件转码。
- 定时任务。
- 事件通知。
- 低频或波动明显的后台任务。

不适合：

- 长时间运行任务。
- 强状态、长连接、低延迟要求极高的服务。
- 启动时间敏感且无法接受冷启动的场景。

### 云迁移策略

常见迁移策略：

| 策略 | 含义 | 适用 |
| --- | --- | --- |
| Rehost | 直接迁移到云上虚拟机 | 快速上云，改造少 |
| Replatform | 适度改造，使用云数据库、容器平台等 | 降低运维成本，提升弹性 |
| Refactor | 重构为云原生架构 | 长期演进，提升可扩展性和交付效率 |
| Retain | 暂时保留原系统 | 依赖复杂、风险高、暂不适合迁移 |
| Retire | 下线无价值系统 | 减少维护成本 |

迁移题常见答法：先评估业务重要性、依赖关系、数据迁移、停机窗口和回滚方案，再选择直接迁移、平台改造或云原生重构。

### 云原生题常见失分点

- 只写 Docker，没有写镜像仓库、部署、配置和监控。
- 只写 Kubernetes，没有写 Service、Deployment、探针、滚动更新。
- 只写自动伸缩，没有说明应用必须无状态。
- 只写灰度发布，没有写流量比例、监控和回滚。
- 只写多可用区，没有写数据复制和故障切换。
- 只写 Secret，没有写 RBAC、加密、审计和最小权限。
- 只写上 K8s，没有写资源限制、探针、日志指标和回滚。
