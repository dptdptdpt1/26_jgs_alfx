# 案例答题模板

## 考试中一般怎么考

1. 综合改进题：给一个系统现状，要求指出问题并提出架构改进措施。
2. 质量属性题：要求判断设计方案提升或损害了哪些质量属性。
3. 技术选型题：要求在多种方案中选择，并说明理由和代价。
4. 风险分析题：要求识别单点、性能瓶颈、安全风险、一致性风险。
5. 机制说明题：要求解释缓存、消息队列、网关、注册中心、分布式事务如何起作用。

## 针对考法梳理知识点

### 综合改进题通用模板

```text
先从业务目标和质量属性出发，识别当前系统在性能、可用性、扩展性、安全性、可维护性方面的问题。针对性能问题，可从缓存、异步、数据库优化、负载均衡和水平扩展优化；针对可用性问题，可通过冗余部署、健康检查、故障转移、限流、熔断、降级和容灾提升；针对扩展性问题，可通过分层、模块化、无状态化、服务拆分和消息队列降低耦合；针对安全问题，可增加认证、授权、加密、签名、防重放、审计和访问控制。最后说明方案代价，例如一致性、复杂度、运维成本和性能开销。
```

### 问“为什么引入缓存”

答题点：

- 缓存热点数据，减少数据库访问。
- 缩短读取路径，提高响应速度。
- 分担数据库读压力，提升吞吐。
- 适合读多写少、热点明显、允许短暂不一致的场景。
- 代价是缓存一致性、穿透、击穿、雪崩、热 Key 和容量管理。

完整句式：

```text
引入缓存可将热点数据放在 Redis 中，用户请求先访问缓存，命中后直接返回，减少数据库查询次数，提高响应速度和系统吞吐量。但需要处理缓存和数据库的一致性，并通过空值缓存、布隆过滤器、互斥重建、过期时间随机化等方式防止穿透、击穿和雪崩。
```

### 问“为什么引入消息队列”

答题点：

- 异步处理，缩短主流程响应时间。
- 解耦生产者和消费者。
- 削峰填谷，保护后端服务。
- 支持事件广播和最终一致。
- 代价是延迟、重复消费、消息丢失、积压和排查复杂。

完整句式：

```text
引入消息队列后，订单创建等核心操作完成后即可返回，短信、积分、通知等非核心任务异步消费，从而缩短同步链路并削峰填谷。消息队列还能降低系统间耦合，但需要通过生产者确认、本地消息表、消费者确认、幂等处理、重试和死信队列保证消息可靠性。
```

### 问“如何提高可用性”

答题点：

- 消除单点：集群、主备、多副本。
- 发现故障：心跳、健康检查、监控告警。
- 自动恢复：故障转移、自动拉起、回滚。
- 控制故障扩散：限流、熔断、降级、隔离。
- 数据恢复：备份、复制、容灾演练。
- 指标：RTO、RPO、故障切换时间、可用性比例。

完整句式：

```text
可通过多实例集群和主备部署消除单点，使用健康检查和心跳及时发现故障，故障后由负载均衡摘除异常节点并自动切换到可用节点。同时对外部依赖设置超时、熔断、限流和降级，避免故障扩散；对关键数据做主从复制、备份和容灾演练，并以 RTO、RPO 和故障切换时间衡量效果。
```

### 问“如何保证分布式一致性”

先判断业务是否允许短暂不一致。

| 场景 | 推荐 |
| --- | --- |
| 单库核心操作 | 本地事务 |
| 跨服务强业务一致 | TCC 或严格补偿 |
| 长流程业务 | Saga |
| 异步通知、积分、日志 | 可靠消息最终一致 |
| 允许事后修复 | 对账和人工补偿 |

完整句式：

```text
跨服务场景不宜直接扩大本地事务边界，应根据业务一致性要求选择方案。强一致场景可采用 TCC，将业务拆成 Try、Confirm、Cancel；长流程可采用 Saga，每个本地事务配补偿动作；异步最终一致场景可用可靠消息、本地消息表、幂等消费、失败重试和定时对账保证最终一致。
```

### 问“如何做安全设计”

答题顺序：

1. 认证：确认用户或调用方身份。
2. 授权：控制功能、接口、数据和字段权限。
3. 传输安全：HTTPS/TLS、VPN。
4. 数据安全：加密存储、脱敏、备份保护。
5. 接口安全：签名、时间戳、Nonce、防重放、限流。
6. 攻击防护：SQL 注入、XSS、CSRF、暴力破解。
7. 审计：关键操作记录日志，支持追踪。

完整句式：

```text
系统应先通过统一认证确认用户身份，再通过 RBAC/ABAC 控制菜单、接口、数据和字段权限；外部通信使用 HTTPS/TLS，敏感数据加密存储并脱敏展示；开放接口增加签名、时间戳、Nonce 和限流，防止篡改、重放和刷接口；关键操作记录审计日志，便于事后追踪。
```

### 问“如何选择架构风格”

答题顺序：

1. 看业务规模和复杂度。
2. 看是否需要独立部署和团队独立演进。
3. 看是否需要异步解耦和削峰。
4. 看是否存在大量异构系统集成。
5. 看目标质量属性和引入代价。

示例：

```text
如果系统规模较小、业务边界简单，可采用分层架构或 MVC，降低开发和维护成本；如果系统复杂、团队多、模块需要独立部署和扩展，可采用微服务，但要配套注册中心、配置中心、网关、监控、链路追踪和分布式一致性方案；如果系统间主要是异步事件通知和削峰填谷，可采用事件驱动或消息驱动架构。
```

### 风险识别清单

| 风险 | 典型表现 | 改进 |
| --- | --- | --- |
| 单点风险 | 单应用、单数据库、单网关 | 集群、主备、多副本 |
| 性能瓶颈 | 慢 SQL、同步链路长、外部接口慢 | 索引、缓存、异步、熔断 |
| 一致性风险 | 缓存旧数据、消息重复、跨库事务 | 删除缓存、幂等、补偿、对账 |
| 安全风险 | 无鉴权、越权、明文传输 | 认证、授权、加密、审计 |
| 可维护性风险 | 模块耦合、职责混乱 | 分层、模块化、接口隔离 |
| 运维风险 | 无监控、无告警、无回滚 | 监控、日志、发布策略、预案 |

### 答题避免空泛

不要写：

```text
加强管理，优化系统，提高性能。
```

要写：

```text
通过慢 SQL 日志和执行计划定位查询瓶颈，对订单查询条件建立联合索引；热点商品信息放入 Redis 缓存，设置随机过期时间防止雪崩；下单后的短信和积分处理改为消息队列异步消费，缩短主链路响应时间。
```
