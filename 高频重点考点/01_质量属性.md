# 质量属性

## 考试中一般怎么考

1. 场景填空：给一段描述，判断是功能性还是质量属性；如果是质量属性，判断具体属性。
2. 属性辨析：区分性能、可用性、可靠性、可修改性、可移植性等易混概念。
3. 场景要素：按质量属性场景六要素补全描述。
4. 架构战术：针对可靠性/可用性，说明故障检测、故障恢复、故障切换策略。
5. 机制比较：比较 `ping/echo` 和心跳机制，常问资源利用率、检测方式、适用场景。
6. 可靠性设计：问可靠性建模、容错、恢复块、N 版本和备份恢复。

## 针对考法梳理知识点

### 1. 功能性和质量属性

| 判断 | 看什么 | 例子 |
| --- | --- | --- |
| 功能性 | 系统做什么 | 数据导出、多语言显示、报表生成 |
| 质量属性 | 系统做得怎么样 | 3 秒内导出、1 小时内恢复、3 天内完成修改 |

常见判断：

| 描述 | 答案 |
| --- | --- |
| 系统可以导出数据 | 功能性 |
| 数据导出在 3 秒内完成 | 性能 |
| 系统支持三种语言界面 | 功能性 |
| 新增一种语言需 1 天完成 | 可修改性 / 可移植性 |

### 2. 常考质量属性速判

| 描述关键词 | 属性 |
| --- | --- |
| 响应时间、吞吐量、并发数、几秒内完成业务操作 | 性能 |
| 故障检测、故障切换、恢复服务、不中断 | 可用性 |
| 平均无故障时间、错误率、故障概率、异常恢复 | 可靠性 |
| 新增模块、修改规则、变更功能、几天内完成修改 | 可修改性 |
| 多语言、跨平台、迁移环境、适配不同部署环境 | 可移植性 |
| 认证、授权、加密、防篡改、防重放、审计 | 安全性 |
| 自动化测试、故障注入、测试接口、可观测 | 可测试性 |

### 3. 易混点

| 易混项 | 区分方式 |
| --- | --- |
| 性能 vs 可用性 | 正常业务处理快是性能；故障检测、恢复、切换快是可用性 |
| 可用性 vs 可靠性 | 可用性关注故障后能否继续服务；可靠性关注少出错、少故障 |
| 功能性 vs 质量属性 | “支持某功能”是功能性；“多快、多稳、多安全、多易改”是质量属性 |
| 可修改性 vs 可移植性 | 改业务/改模块是可修改性；换语言、平台、环境是可移植性 |

### 4. 质量属性场景六要素

| 要素 | 含义 |
| --- | --- |
| 刺激源 | 谁触发 |
| 刺激 | 发生什么 |
| 环境 | 在什么条件下 |
| 制品 | 影响哪个系统部分 |
| 响应 | 系统如何处理 |
| 响应度量 | 用什么指标衡量 |

例子：

| 要素 | 内容 |
| --- | --- |
| 刺激源 | 用户 |
| 刺激 | 发起数据导出请求 |
| 环境 | 系统正常运行 |
| 制品 | 数据导出服务 |
| 响应 | 完成导出并返回文件 |
| 响应度量 | 3 秒内完成 |
| 属性 | 性能 |

### 5. 可靠性/可用性战术

| 目标 | 常用战术 |
| --- | --- |
| 发现故障 | `ping/echo`、心跳、健康检查、异常检测 |
| 避免单点 | 冗余、主备、集群、负载均衡 |
| 故障恢复 | 故障转移、重启、回滚、恢复到安全状态 |
| 控制影响 | 限流、熔断、降级、隔离 |
| 数据恢复 | 备份、复制、快照、容灾 |
| 事后定位 | 日志、监控、告警、链路追踪 |

### 6. 常见质量属性和架构策略

考试里经常要求“指出该设计提高了哪个质量属性”。不要只写技术名，要把技术名和属性建立对应关系。

| 质量属性 | 常用策略 | 答题要点 |
| --- | --- | --- |
| 性能 | 缓存、异步、批处理、CDN、数据库优化、负载均衡 | 减少等待、减少重复计算、缩短链路、提高吞吐 |
| 可用性 | 集群、主备、故障转移、限流、熔断、降级 | 故障时继续提供服务，避免单点和故障扩散 |
| 可扩展性 | 分层、无状态服务、水平扩展、消息队列、微服务 | 新增能力或扩容时尽量少改现有系统 |
| 安全性 | 认证、授权、加密、审计、访问控制、防注入 | 防止非法访问、泄露、篡改、抵赖和攻击 |
| 可维护性 | 模块化、低耦合高内聚、接口隔离、分层架构 | 变更影响范围小，代码和职责清楚 |
| 可靠性 | 冗余、重试、幂等、事务补偿、备份恢复 | 减少失败概率，失败后结果可恢复、可校正 |

### 7. 性能策略怎么写出机制

常见性能策略的机制：

- 缓存：把热点数据放到访问更快的位置，减少数据库查询和重复计算。
- 异步：把非核心、耗时任务从同步链路移出，提高主流程响应速度。
- 负载均衡：把请求分散到多个节点，提高并发处理能力，并可摘除故障节点。
- 数据库优化：通过索引、SQL 优化、读写分离、分库分表减少查询和写入瓶颈。
- CDN：把静态资源缓存到离用户更近的节点，降低源站压力和网络延迟。
- 批处理：把多次小操作合并成批量操作，减少连接、事务和网络开销。

易错点：性能策略可能牺牲一致性、复杂度或实时性。例如缓存会带来一致性问题，异步会带来处理延迟。

### 8. 质量属性指标怎么写

案例题里如果要求“响应度量”，要尽量写成可度量指标。

| 属性 | 常见指标 | 答题示例 |
| --- | --- | --- |
| 性能 | 响应时间、吞吐量、并发数、资源利用率 | 高峰期 1000 并发下，查询 2 秒内返回 |
| 可用性 | 可用时间比例、故障切换时间、恢复时间 | 主节点故障后 30 秒内切换到备节点 |
| 可靠性 | 平均无故障时间、故障率、错误率 | 系统连续运行 7 天错误率低于 0.1% |
| 可修改性 | 修改工作量、影响模块数、上线时间 | 新增一种支付方式 2 人日内完成 |
| 安全性 | 未授权访问次数、加密覆盖率、审计完整性 | 所有管理操作记录审计日志，保留 6 个月 |
| 可测试性 | 自动化覆盖率、故障注入能力、定位时间 | 核心接口自动化测试覆盖率达到 80% |

只写“提高可用性”“增强安全性”通常不够，要补“用什么指标证明”。

### 9. 可修改性和可维护性战术

可修改性关注“未来变化时代价小”，常见战术：

- 信息隐藏：模块只暴露稳定接口，内部实现可以替换。
- 接口隔离：调用方依赖抽象接口，不直接依赖具体实现。
- 配置化：把经常变化的规则、阈值、开关放到配置中。
- 模块化：按职责拆分模块，避免一个模块承担过多功能。
- 分层：界面、业务、数据访问分离，减少变更扩散。
- 插件化：变化点通过插件扩展，核心系统保持稳定。

可维护性答题不要只写“低耦合高内聚”。最好补一句：修改某业务规则时只影响业务规则模块，不影响界面层和数据访问层。

### 10. 质量属性场景答题模板

可以按固定句式写：

```text
在某环境下，当某刺激源对某制品施加某刺激时，系统应做出某响应，并达到某响应度量。
```

例子：

```text
在业务高峰期，当 1000 个用户同时查询订单列表时，订单查询服务应完成查询并返回结果，95% 请求响应时间不超过 2 秒。
```

六要素对应：

- 环境：业务高峰期。
- 刺激源：1000 个用户。
- 刺激：同时查询订单列表。
- 制品：订单查询服务。
- 响应：完成查询并返回结果。
- 响应度量：95% 请求响应时间不超过 2 秒。

### 11. 可靠性和可用性的指标关系

可靠性更偏“少出故障”，可用性更偏“出了故障还能尽快恢复服务”。

常见指标：

- MTBF：平均故障间隔时间，越长越可靠。
- MTTR：平均修复时间，越短越可用。
- 可用性近似等于 `MTBF / (MTBF + MTTR)`。

提高可用性不一定等于提高可靠性。例如服务仍可能故障，但通过主备切换把中断时间缩短，也能提升可用性。

### 12. ping/echo 与心跳机制

| 机制 | 原理 | 特点 |
| --- | --- | --- |
| `ping/echo` | 监控方定期向节点发请求，节点返回响应；超时或多次失败则判定故障 | 主动轮询；实现简单；节点多时请求量大 |
| 心跳 | 被监控节点定期主动上报状态；监控方根据最后心跳时间判断故障 | 节点主动上报；监控方只做接收和超时判断；资源利用率通常更好 |

为什么心跳资源利用率更好：

- `ping/echo` 需要监控方周期性探测所有节点。
- 节点越多，探测请求和响应越多。
- 心跳由节点主动上报，监控方主要维护状态和超时判断。
- 心跳消息小，还可以携带节点状态，适合节点较多的场景。

### 13. 可靠性建模与容错设计

可靠性建模用于分析系统哪里容易故障、故障如何传播、系统能否继续服务。

常见分析对象：

- 故障源：硬件故障、软件缺陷、网络中断、外部依赖异常。
- 故障模式：宕机、超时、数据错误、消息丢失、响应变慢。
- 故障影响：影响哪个功能、是否影响核心业务、是否会扩散。
- 恢复能力：是否能自动切换、重试、回滚、补偿和恢复数据。

常见容错设计：

| 设计 | 机制 | 适用场景 |
| --- | --- | --- |
| 冗余 | 多节点、多副本、主备 | 避免单点故障 |
| N 版本程序设计 | 多个独立版本并行计算，投票决定结果 | 高可靠控制系统 |
| 恢复块 | 主方案失败后切换到备用方案 | 有明确验收条件的处理流程 |
| 检查点 | 周期保存状态，失败后从检查点恢复 | 长任务、批处理 |
| 备份恢复 | 定期备份数据，故障后恢复 | 数据库、文件、配置 |

易错点：可靠性关注“少出错、出错可校正”；可用性关注“服务不中断或尽快恢复”。容错设计通常会增加成本和复杂度。
