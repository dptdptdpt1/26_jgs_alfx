# 质量属性

## 考试中一般怎么考

1. 场景填空：给一段描述，判断是功能性还是质量属性；如果是质量属性，判断具体属性。
2. 属性辨析：区分性能、可用性、可靠性、可修改性、可移植性等易混概念。
3. 场景要素：按质量属性场景六要素补全描述。
4. 架构战术：针对可靠性/可用性，说明故障检测、故障恢复、故障切换策略。
5. 机制比较：比较 `ping/echo` 和心跳机制，常问资源利用率、检测方式、适用场景。

## 针对考法梳理知识点

### 1. 功能性和质量属性

| 判断 | 看什么 | 例子 |
| --- | --- | --- |
| 功能性 | 系统做什么 | 数据导出、多语言显示、报表生成 |
| 质量属性 | 系统做得怎么样 | 3 秒内导出、1 小时内恢复、3 天内完成修改 |

常见判断：

| 描述 | 答案 |
| --- | --- |
| 系统可以导出数据 | 功能性 |
| 数据导出在 3 秒内完成 | 性能 |
| 系统支持三种语言界面 | 功能性 |
| 新增一种语言需 1 天完成 | 可修改性 / 可移植性 |

### 2. 常考质量属性速判

| 描述关键词 | 属性 |
| --- | --- |
| 响应时间、吞吐量、并发数、几秒内完成业务操作 | 性能 |
| 故障检测、故障切换、恢复服务、不中断 | 可用性 |
| 平均无故障时间、错误率、故障概率、异常恢复 | 可靠性 |
| 新增模块、修改规则、变更功能、几天内完成修改 | 可修改性 |
| 多语言、跨平台、迁移环境、适配不同部署环境 | 可移植性 |
| 认证、授权、加密、防篡改、防重放、审计 | 安全性 |
| 自动化测试、故障注入、测试接口、可观测 | 可测试性 |

### 3. 易混点

| 易混项 | 区分方式 |
| --- | --- |
| 性能 vs 可用性 | 正常业务处理快是性能；故障检测、恢复、切换快是可用性 |
| 可用性 vs 可靠性 | 可用性关注故障后能否继续服务；可靠性关注少出错、少故障 |
| 功能性 vs 质量属性 | “支持某功能”是功能性；“多快、多稳、多安全、多易改”是质量属性 |
| 可修改性 vs 可移植性 | 改业务/改模块是可修改性；换语言、平台、环境是可移植性 |

### 4. 质量属性场景六要素

| 要素 | 含义 |
| --- | --- |
| 刺激源 | 谁触发 |
| 刺激 | 发生什么 |
| 环境 | 在什么条件下 |
| 制品 | 影响哪个系统部分 |
| 响应 | 系统如何处理 |
| 响应度量 | 用什么指标衡量 |

例子：

| 要素 | 内容 |
| --- | --- |
| 刺激源 | 用户 |
| 刺激 | 发起数据导出请求 |
| 环境 | 系统正常运行 |
| 制品 | 数据导出服务 |
| 响应 | 完成导出并返回文件 |
| 响应度量 | 3 秒内完成 |
| 属性 | 性能 |

### 5. 可靠性/可用性战术

| 目标 | 常用战术 |
| --- | --- |
| 发现故障 | `ping/echo`、心跳、健康检查、异常检测 |
| 避免单点 | 冗余、主备、集群、负载均衡 |
| 故障恢复 | 故障转移、重启、回滚、恢复到安全状态 |
| 控制影响 | 限流、熔断、降级、隔离 |
| 数据恢复 | 备份、复制、快照、容灾 |
| 事后定位 | 日志、监控、告警、链路追踪 |

### 6. ping/echo 与心跳机制

| 机制 | 原理 | 特点 |
| --- | --- | --- |
| `ping/echo` | 监控方定期向节点发请求，节点返回响应；超时或多次失败则判定故障 | 主动轮询；实现简单；节点多时请求量大 |
| 心跳 | 被监控节点定期主动上报状态；监控方根据最后心跳时间判断故障 | 节点主动上报；监控方只做接收和超时判断；资源利用率通常更好 |

为什么心跳资源利用率更好：

- `ping/echo` 需要监控方周期性探测所有节点。
- 节点越多，探测请求和响应越多。
- 心跳由节点主动上报，监控方主要维护状态和超时判断。
- 心跳消息小，还可以携带节点状态，适合节点较多的场景。
