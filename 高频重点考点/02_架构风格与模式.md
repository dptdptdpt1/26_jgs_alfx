# 架构风格与模式

## 考试中一般怎么考

1. 架构识别：根据题干描述判断是分层、微服务、事件驱动、管道过滤器等。
2. 原理解释：问某种架构为什么能解耦、为什么能扩展、为什么会带来治理复杂度。
3. 场景选型：给业务背景，要求选择合适架构风格并说明理由。
4. 质量属性影响：分析架构风格对性能、可维护性、可扩展性、可用性的影响。

## 针对考法梳理知识点

### 分层架构

分层架构把系统按职责拆成表示层、业务逻辑层、数据访问层等。上层调用下层，下层不依赖上层。

它解决的是职责分离和可维护性问题。界面变化通常影响表示层，业务规则变化主要影响业务层，数据库访问变化主要影响数据访问层。

它的代价是层间调用可能增加开销，过度分层会让简单逻辑变复杂。

### 微服务架构

微服务把系统拆成多个可独立部署的服务。每个服务围绕业务能力构建，通常有自己的数据和接口。

它解决的是复杂系统的独立开发、独立部署和弹性扩展问题。

它的代价是服务治理复杂：注册发现、配置、网关、链路追踪、分布式事务、版本兼容都要处理。

考试里不能只写“微服务可扩展”，还要写“会引入分布式一致性和运维复杂度”。

### 事件驱动架构

事件驱动通过事件或消息连接系统组件。生产者发布事件，消费者订阅并处理事件。

它解决的是异步解耦和削峰填谷问题。生产者不需要等待消费者处理完成，流量高峰可以先进入消息队列。

它的代价是链路追踪困难、处理结果有延迟、消息可能重复或丢失，需要幂等和可靠消息机制。

### 管道过滤器

管道过滤器把处理过程拆成多个过滤器，前一个过滤器的输出作为后一个过滤器的输入。

它适合数据转换、编译、日志处理、图像处理等连续处理流程。

它的优势是每个过滤器职责单一、可复用、可替换。它不适合强交互、复杂状态共享的业务系统。

### MVC

MVC 把表示层拆成模型、视图、控制器。视图负责展示，控制器处理请求，模型承载数据和业务状态。

它解决的是界面逻辑和业务逻辑混杂的问题，提高可维护性和可测试性。

它的代价是结构更复杂，小系统里可能显得过度设计。

### 微内核架构

微内核把系统拆成核心系统和插件。核心系统只保留最基本、最稳定的能力，变化大的业务能力通过插件扩展。

它适合工具平台、IDE、规则引擎、工作流平台等需要灵活扩展的系统。

优势是扩展性和可维护性好，新功能可以通过插件增加。代价是插件接口设计要求高，插件之间兼容性、版本管理和安全隔离要处理好。

### C/S 和 B/S

| 架构 | 特点 | 适用场景 | 局限 |
| --- | --- | --- | --- |
| C/S | 客户端承担部分业务或展示逻辑，服务器提供数据和服务 | 专业客户端、对交互体验或本地能力要求高的系统 | 客户端安装升级成本高，跨平台维护复杂 |
| B/S | 浏览器作为客户端，主要逻辑在服务器端 | 企业管理系统、互联网系统、跨平台访问 | 复杂本地交互和设备能力受浏览器限制 |

考试问“为什么选择 B/S”，常答：部署升级方便、客户端维护成本低、跨平台访问能力好。

### SOA 和微服务

SOA 强调服务复用和系统集成，常通过 ESB、服务契约、服务编排连接多个系统。

微服务强调围绕业务能力拆分、独立部署、独立演进，通常使用轻量通信和自动化运维。

| 对比点 | SOA | 微服务 |
| --- | --- | --- |
| 目标 | 企业级系统集成和服务复用 | 快速交付、独立部署、弹性扩展 |
| 粒度 | 服务粒度通常较粗 | 服务粒度相对更细 |
| 通信 | 常见 ESB、WebService | 常见 REST、RPC、消息 |
| 治理重点 | 服务契约、编排、统一集成 | 注册发现、配置、网关、监控、链路追踪 |

### RESTful

RESTful 不是一种数据库风格，而是面向资源的接口设计风格。

常见判断点：

- 用 URI 表示资源，例如 `/orders/1001`。
- 用 HTTP 方法表达操作，例如 `GET` 查询、`POST` 创建、`PUT` 更新、`DELETE` 删除。
- 通常使用 JSON 作为数据格式。
- 服务端尽量无状态，请求需要携带必要上下文。

优点是简单、开放、跨平台好。局限是复杂事务、强实时双向通信、复杂查询时可能不如 RPC 或专用协议直接。

### 消息驱动架构

消息驱动通过消息队列连接生产者和消费者。生产者只负责发送消息，消费者异步处理。

它适合系统集成、异步任务、削峰填谷和事件通知。

答题要补充限制：消息可能重复、乱序、延迟或积压，所以需要幂等、重试、死信队列、监控告警和补偿机制。

### 场景选型速判

| 场景关键词 | 优先考虑 | 理由 |
| --- | --- | --- |
| 企业管理系统、职责清晰、CRUD 多 | 分层架构、MVC | 职责分离，便于维护 |
| 数据处理流水线、转换、编译、日志清洗 | 管道过滤器 | 每个处理步骤独立、可复用 |
| 多系统异步通知、削峰填谷 | 事件驱动、消息驱动 | 生产者和消费者解耦 |
| 大系统独立部署、团队独立演进 | 微服务 | 服务可独立开发、部署、扩展 |
| 规则频繁变化、插件扩展 | 微内核 | 核心稳定，变化通过插件扩展 |
| 跨企业异构系统集成 | SOA、ESB | 协议转换、服务编排、统一治理 |
| 多终端浏览器访问、部署升级方便 | B/S | 客户端维护成本低 |
| 专业客户端、本地设备能力强 | C/S | 本地体验和设备访问能力好 |

### 架构风格优缺点答题框架

答优缺点时按四个角度组织：

1. 解决什么问题：例如解耦、扩展、复用、独立部署。
2. 提升哪些质量属性：性能、可用性、可维护性、可扩展性。
3. 引入什么代价：复杂度、运维、数据一致性、性能开销。
4. 需要什么配套机制：监控、配置、注册发现、消息可靠性、接口治理。

例子：微服务不能只答“可扩展”。完整答法是：微服务按业务能力拆分，支持独立开发、部署和水平扩展，提高可维护性和可扩展性；但会引入远程调用、分布式事务、链路追踪和运维治理复杂度，需要注册中心、网关、配置中心、监控告警等配套能力。

### 架构改进常见方向

| 问题 | 常见改进 |
| --- | --- |
| 模块职责混乱，修改影响大 | 分层、模块化、接口隔离 |
| 同步链路过长，响应慢 | 异步消息、并行处理、缓存 |
| 单体部署影响面大 | 按业务边界拆服务 |
| 接口调用混乱 | API 网关、统一接口规范、版本管理 |
| 访问量波动大 | 无状态化、负载均衡、水平扩展 |
| 外部系统不稳定 | 超时、重试、熔断、降级、隔离 |

### 常见易错说法

- “用了微服务就一定性能更好”是错的。微服务会增加网络调用和序列化开销，主要提升独立演进和扩展能力。
- “事件驱动一定实时”是错的。事件驱动通常异步，处理结果可能延迟。
- “分层越多越好”是错的。过度分层会增加调用复杂度和理解成本。
- “RESTful 等于 HTTP 接口”不准确。RESTful 重点是资源建模、统一接口和无状态。
