# 数据库

## 考试中一般怎么考

1. 查询慢：要求分析数据库层瓶颈，并说明索引、SQL、分页、统计预计算等优化思路。
2. 数据量大：要求说明为什么要分区、分库分表、冷热分离或历史归档。
3. 读写压力大：要求区分读压力、写压力、容量压力，选择不同方案。
4. 数据一致性：要求判断业务需要强一致还是最终一致，并说明事务、补偿、对账等机制。

## 针对考法梳理知识点

### 查询慢先判断瓶颈

查询慢不等于只加索引。先判断慢在哪里：

- 扫描数据太多：考虑索引、分区、缩小查询范围。
- SQL 写法低效：避免全表扫描、避免不必要的排序和关联。
- 分页过深：避免 `limit offset` 深分页，可用游标、范围查询或搜索引擎。
- 统计计算重：考虑预计算、汇总表、物化视图或数仓。
- 模糊搜索多：不要让数据库承担复杂全文检索，考虑搜索引擎。

### 数据量大为什么要拆

单表或单库数据持续增长后，问题通常不是“存不下”，而是查询、写入、索引维护、备份恢复都会变慢。

常见处理思路：

- 分区表：仍在一个数据库内，按时间或范围管理数据，适合按时间查询和归档。
- 分库分表：把数据拆到多个库表，解决单库单表容量和吞吐瓶颈。
- 冷热分离：热数据留在线库，冷数据移到低频存储。
- 历史归档：把长期不用的数据迁出，降低在线库压力。

分库分表的代价必须写：跨库事务复杂、跨表查询复杂、全局 ID、扩容迁移和运维成本都会增加。

### 读压力和写压力处理不同

读压力大，优先考虑读写分离、只读副本、缓存、搜索引擎。

写压力大，优先考虑批量写入、异步写入、消息队列削峰、分片写入。

读写分离解决的是读压力，不直接解决写入瓶颈。分库分表能分散容量和写入压力，但复杂度更高。

### 数据一致性怎么选

如果是单库内核心业务，优先使用本地事务。

如果跨服务、跨库，先判断业务是否允许短暂不一致：

- 支付、扣款、库存核心扣减：倾向强一致或严格补偿。
- 积分、通知、日志、统计：通常可以最终一致。
- 长流程跨多个服务：可用 Saga、可靠消息、补偿机制。
- 允许事后修复：可加定时对账和人工处理。

考试中不要一看到“分布式”就直接写分布式事务。分布式事务一致性强，但性能和复杂度高。
