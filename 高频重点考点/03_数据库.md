# 数据库

## 考试中一般怎么考

1. 查询慢：要求分析数据库层瓶颈，并说明索引、SQL、分页、统计预计算等优化思路。
2. 数据量大：要求说明为什么要分区、分库分表、冷热分离或历史归档。
3. 读写压力大：要求区分读压力、写压力、容量压力，选择不同方案。
4. 数据一致性：要求判断业务需要强一致还是最终一致，并说明事务、补偿、对账等机制。

## 针对考法梳理知识点

### ER 模型和范式

ER 模型用于表达数据实体、属性和实体之间的关系。案例题里常要求从业务描述中识别实体、联系和主外键。

常见关系：

- 一对一：一个实体实例只对应另一个实体的一个实例。
- 一对多：一个部门有多个员工，一个员工属于一个部门。
- 多对多：学生和课程通常需要中间表拆成两个一对多。

范式用于减少数据冗余和更新异常：

| 范式 | 核心要求 | 常见问题 |
| --- | --- | --- |
| 1NF | 属性不可再分 | 一个字段存多个值 |
| 2NF | 非主属性完全依赖主键 | 联合主键下只依赖部分主键 |
| 3NF | 非主属性不传递依赖主键 | 部门名称依赖部门编号，部门编号又依赖员工 |

反范式是有意保留冗余字段，减少关联查询，提高读性能。代价是写入时要维护一致性。

### 查询慢先判断瓶颈

查询慢不等于只加索引。先判断慢在哪里：

- 扫描数据太多：考虑索引、分区、缩小查询范围。
- SQL 写法低效：避免全表扫描、避免不必要的排序和关联。
- 分页过深：避免 `limit offset` 深分页，可用游标、范围查询或搜索引擎。
- 统计计算重：考虑预计算、汇总表、物化视图或数仓。
- 模糊搜索多：不要让数据库承担复杂全文检索，考虑搜索引擎。

### 数据量大为什么要拆

单表或单库数据持续增长后，问题通常不是“存不下”，而是查询、写入、索引维护、备份恢复都会变慢。

常见处理思路：

- 分区表：仍在一个数据库内，按时间或范围管理数据，适合按时间查询和归档。
- 分库分表：把数据拆到多个库表，解决单库单表容量和吞吐瓶颈。
- 冷热分离：热数据留在线库，冷数据移到低频存储。
- 历史归档：把长期不用的数据迁出，降低在线库压力。

分库分表的代价必须写：跨库事务复杂、跨表查询复杂、全局 ID、扩容迁移和运维成本都会增加。

### 读压力和写压力处理不同

读压力大，优先考虑读写分离、只读副本、缓存、搜索引擎。

写压力大，优先考虑批量写入、异步写入、消息队列削峰、分片写入。

读写分离解决的是读压力，不直接解决写入瓶颈。分库分表能分散容量和写入压力，但复杂度更高。

### 数据一致性怎么选

如果是单库内核心业务，优先使用本地事务。

如果跨服务、跨库，先判断业务是否允许短暂不一致：

- 支付、扣款、库存核心扣减：倾向强一致或严格补偿。
- 积分、通知、日志、统计：通常可以最终一致。
- 长流程跨多个服务：可用 Saga、可靠消息、补偿机制。
- 允许事后修复：可加定时对账和人工处理。

考试中不要一看到“分布式”就直接写分布式事务。分布式事务一致性强，但性能和复杂度高。

### ACID、CAP、BASE

ACID 描述数据库事务特性：

- 原子性：事务内操作要么都成功，要么都失败。
- 一致性：事务前后数据满足业务约束。
- 隔离性：并发事务之间互不干扰到规定程度。
- 持久性：提交后的结果不会因故障丢失。

CAP 用于分布式系统取舍：

| 维度 | 含义 |
| --- | --- |
| 一致性 C | 多副本读到一致结果 |
| 可用性 A | 每个请求都能得到非错误响应 |
| 分区容错性 P | 网络分区时系统仍能运行 |

网络分区不可避免时，通常在一致性和可用性之间取舍。强一致系统可能牺牲部分可用性，最终一致系统可能允许短暂不一致。

BASE 是最终一致性思想：基本可用、软状态、最终一致。适合积分、消息通知、统计同步等允许延迟修复的场景。

### 数据仓库、ETL、OLTP/OLAP

| 概念 | 重点 |
| --- | --- |
| OLTP | 面向在线交易，关注高并发、低延迟、事务一致性 |
| OLAP | 面向分析查询，关注复杂统计、多维分析、批量扫描 |
| 数据仓库 | 面向主题、集成、相对稳定、随时间变化的数据集合 |
| ETL | 抽取、转换、加载，把业务系统数据加工进入数仓 |
| 数据湖 | 存储结构化、半结构化、非结构化原始数据，适合大数据分析和探索 |

考试问“为什么不能直接在业务库上做复杂统计”，可答：会影响交易性能，业务库模型不适合多维分析，历史数据和异构数据整合能力弱。

### 逻辑设计和物理设计

逻辑设计关注业务数据结构，例如实体、关系、属性、主键、外键、约束。

物理设计关注数据库落地方式，例如索引、分区、表空间、存储引擎、分库分表、备份策略。

案例题常见问法：

- “补 ER 图”：优先从名词找实体，从动词找联系。
- “如何提升查询性能”：属于物理设计优化。
- “如何减少数据冗余”：属于逻辑模型和范式问题。
- “如何支持海量历史数据”：属于分区、归档、冷热分离问题。

### 分区、分库分表、冷热分离怎么区分

| 方案 | 解决重点 | 适用条件 | 主要代价 |
| --- | --- | --- | --- |
| 分区表 | 单表数据管理和按范围查询 | 按时间、范围查询明显 | 仍受单库资源限制 |
| 分库分表 | 单库单表容量和吞吐瓶颈 | 数据量、写入量持续增长 | 跨库事务和查询复杂 |
| 冷热分离 | 在线库压力和历史数据膨胀 | 热数据少、冷数据查询低频 | 查询路径变复杂 |
| 历史归档 | 长期数据保存和在线库瘦身 | 老数据很少修改 | 归档查询和恢复成本 |

如果题目只是“历史订单越来越多，近一年查询频繁，早期订单偶尔查”，优先写冷热分离或历史归档，不必直接上分库分表。

### 数据一致性答题层次

答一致性时按强度从低到高写：

1. 单库内：使用本地事务和数据库约束。
2. 主从复制：注意复制延迟，强一致读走主库。
3. 缓存一致性：以数据库为准，更新数据库后删除缓存，过期时间兜底。
4. 跨服务：可靠消息、TCC、Saga、补偿、对账。
5. 资金类核心链路：尽量缩短事务边界，关键状态机落库，异常可追溯可补偿。

不要把所有一致性问题都答成“分布式事务”。很多场景用最终一致和补偿更符合工程取舍。

### 数据库设计常见失分点

- 多对多关系没有拆中间表。
- 把可重复属性直接塞进一个字段，违反 1NF。
- 只写“加索引”，没有说明加在哪些字段、为什么。
- 读写分离后没有说明主从延迟。
- 分库分表后没有说明全局 ID、跨库查询、扩容迁移。
- 统计分析直接查业务库，没有考虑 OLTP 和 OLAP 隔离。
