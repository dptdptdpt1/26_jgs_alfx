# 数据库对比

## 考试中一般怎么考

1. MySQL vs Redis：要求说明两者职责差异，不能把 Redis 当权威数据源。
2. 关系型数据库 vs NoSQL：根据事务、一致性、结构化程度、扩展性选择。
3. 读写分离 vs 分库分表：根据瓶颈是读压力、写压力还是容量压力选择。
4. 强一致 vs 最终一致：根据业务是否允许短暂不一致选择。

## 针对考法梳理知识点

### MySQL 和 Redis 的职责不同

MySQL 通常作为权威数据源，负责持久化、事务、约束和复杂查询。

Redis 通常作为缓存或内存数据结构存储，负责提升热点数据访问速度，降低数据库压力。

两者配合时，常见模式是：先读 Redis，未命中再读 MySQL，然后写回 Redis。更新时以 MySQL 为准，再删除或更新 Redis 缓存。

考试里如果问一致性，重点写：数据库是准，Redis 是缓存，两者通常通过删除缓存、过期时间、消息通知等方式实现最终一致。

### 关系型数据库和 NoSQL 怎么选

关系型数据库适合结构化数据、强事务、复杂查询和核心业务数据。例如订单、支付、用户、库存。

NoSQL 适合高并发、灵活结构、海量数据、弱事务或特定访问模型。例如缓存、日志、文档、行为数据、时序数据。

选择依据不是“哪个更先进”，而是业务是否需要事务、SQL 查询、强约束和一致性。

### 读写分离和分库分表解决的问题不同

读写分离把写操作放主库，读操作放从库。它主要解决读压力大问题。

分库分表把数据拆到多个库或表。它主要解决单库单表容量、写入吞吐和索引维护压力问题。

读写分离的典型问题是主从延迟。分库分表的典型问题是跨库事务、跨表查询、全局 ID 和扩容迁移复杂。

### 强一致和最终一致怎么选

强一致适合支付、扣款、库存核心扣减等不能出错的场景。

最终一致适合积分、通知、日志、统计、消息推送等允许短暂延迟的场景。

跨服务长流程通常不追求全局强事务，而采用可靠消息、Saga、补偿、对账等方式保证最终一致。

### OLTP 和 OLAP 怎么选

OLTP 面向在线交易，关注高并发、低延迟、事务一致性，典型场景是下单、支付、库存扣减。

OLAP 面向分析，关注复杂查询、历史数据、多维统计，典型场景是经营报表、用户行为分析。

如果题目说“白天业务库压力大，统计报表查询慢并影响交易”，应把分析负载从业务库拆出去，通过 ETL 或数据同步进入数据仓库、数据集市或 OLAP 引擎。

### 分区和分表怎么选

分区通常仍在一个数据库实例内，适合按时间或范围管理数据，例如按月份分区订单表，便于查询和归档。

分表把数据拆成多张表，常用于单表过大或写入吞吐不足。

分区更像数据库内部管理手段，分表更像应用或中间件层面的数据拆分。分表后跨表查询、排序、分页、事务会更复杂。

### 技术选型答题顺序

遇到“该选哪种数据库或中间件”，按这个顺序写：

1. 数据类型：结构化、文档、键值、时序、文件。
2. 访问模式：点查、范围查、全文检索、聚合分析、高频读写。
3. 一致性要求：强一致、最终一致、可丢弃、可补偿。
4. 数据规模：容量、增长速度、冷热特征。
5. 运维成本：备份、恢复、扩容、监控、迁移。

这样比直接写“用 MySQL/Redis/ES”更容易拿过程分。
