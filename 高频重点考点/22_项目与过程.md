# 项目与过程

> 重要程度：P2  
> 考纲定位：信息系统开发过程、项目协作、质量保证和配置管理。

## 优先掌握

1. 软件生命周期模型和适用场景。
2. 配置管理、基线、变更控制。
3. 测试、评审、质量保证和缺陷管理。
4. 风险管理和干系人沟通。

## 概念和场景

| 重要度 | 内容 | 概念解释 | 场景式解释 |
| --- | --- | --- | --- |
| P0 | 瀑布模型 | 阶段顺序明确，变更成本高 | 需求稳定、监管严格的系统建设 |
| P0 | 迭代模型 | 分多轮逐步完善 | 先上线核心功能，再补充报表和移动端 |
| P0 | 敏捷 | 小步交付、快速反馈 | 需求变化频繁的互联网业务 |
| P0 | 配置管理 | 控制代码、文档、环境等配置项 | 知道某版本由哪些代码和配置组成 |
| P0 | 基线 | 经评审确认的稳定版本 | 需求基线确认后，变更必须走流程 |
| P1 | 变更控制 | 评估、批准、实施和跟踪变更 | 新增接口影响工期、测试和架构，需评审 |
| P1 | 质量保证 | 确保过程和产物符合要求 | 代码评审、测试覆盖、规范检查 |
| P1 | 风险管理 | 识别、分析、应对和监控风险 | 供应商接口延期，需要替代方案 |

## 过程模型选择

| 场景 | 选择 |
| --- | --- |
| 需求稳定、强文档 | 瀑布或 V 模型。 |
| 需求逐步清晰 | 迭代或增量。 |
| 高风险技术验证 | 原型或螺旋。 |
| 需求变化快、需持续交付 | 敏捷或 DevOps。 |

## 变更控制流程

1. 提出变更申请。
2. 分析影响：范围、进度、成本、质量、风险、架构和接口。
3. 变更控制委员会或负责人审批。
4. 修改计划、需求、设计、代码和测试。
5. 验证结果并更新配置基线。

## 易混点

| 易混项 | 区分 |
| --- | --- |
| 质量保证 vs 测试 | 质量保证关注过程符合规范；测试关注发现产品缺陷。 |
| 配置管理 vs 版本控制 | 版本控制是配置管理的一部分。 |
| 风险 vs 问题 | 风险尚未发生；问题已经发生。 |

## 边界

不展开项目管理师科目的计算题；这里只保留架构案例中常用的过程、质量和变更控制点。
