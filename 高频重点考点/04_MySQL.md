# MySQL

## 考试中一般怎么考

1. 查询慢：问如何通过索引、SQL 优化、分页优化提升查询性能。
2. 索引原理：问为什么索引能加快查询，联合索引为什么有最左前缀原则，索引为什么会失效。
3. 事务与隔离：问 ACID、隔离级别、脏读、不可重复读、幻读。
4. 读写分离：问主从复制如何提升读性能，以及主从延迟带来的问题。
5. 数据量过大：问分库分表、分区表、冷热分离的适用场景和代价。

## 针对考法梳理知识点

### 索引为什么能提升查询性能

MySQL 索引本质上是为数据建立额外的数据结构，常见 InnoDB 索引使用 B+ 树。没有索引时，数据库可能需要扫描大量数据行；有索引时，可以先在索引树上定位到目标范围，再回到数据页读取记录。

答题抓住三点：

- 索引减少扫描的数据量。
- B+ 树适合范围查询和排序。
- 索引不是越多越好，因为插入、更新、删除时也要维护索引。

### 联合索引和最左前缀

联合索引按多个字段的顺序组织。例如 `(a, b, c)`，索引先按 `a` 排，再按 `b` 排，再按 `c` 排。

因此查询条件从最左字段开始连续命中时，索引效果最好：

- `where a = ?` 可以用。
- `where a = ? and b = ?` 可以用。
- `where b = ?` 通常不能充分使用这个联合索引。
- `where a = ? and c = ?` 只能较好利用 `a`，中间断了 `b`。

### 索引失效常见原因

常考的不是背列表，而是能解释“为什么失效”：

- 对索引列做函数或表达式计算，数据库难以直接按索引有序结构定位。
- 隐式类型转换，可能导致索引列被转换后再比较。
- 前置模糊匹配，例如 `like '%abc'`，无法从 B+ 树左侧有序前缀定位。
- 联合索引没有从最左列开始使用。
- 范围查询后面的列，利用能力通常会下降。

### 事务和 ACID

事务用于保证一组数据库操作作为一个整体执行。

- 原子性：要么都成功，要么都失败。
- 一致性：事务前后数据满足业务约束。
- 隔离性：并发事务之间相互隔离。
- 持久性：提交后的结果可靠保存。

案例题里如果出现“扣库存、生成订单、扣款必须同时成功”，优先往事务、一致性、补偿机制上答。

### 隔离级别

隔离级别解决的是并发事务之间互相影响的问题。

- 读未提交：可能读到别人未提交的数据，即脏读。
- 读已提交：只能读到已提交数据，避免脏读。
- 可重复读：同一事务内多次读取结果保持一致，MySQL InnoDB 默认级别。
- 串行化：隔离最强，但并发性能最低。

考试里重点区分：

- 脏读：读到了未提交数据。
- 不可重复读：同一行数据前后读到的值不同。
- 幻读：同一条件前后读到的记录数量不同。

### 主从复制和读写分离

读写分离的基本思路是主库负责写，从库负责读。主库把变更日志同步给从库，从库重放这些日志形成数据副本。

它解决的问题：

- 分担读请求压力。
- 提供数据副本。
- 主库故障时可以切换。

它带来的问题：

- 主从复制有延迟。
- 刚写入的数据如果马上读从库，可能读不到。
- 对强一致要求高的读请求，应读主库或等待复制完成。

### 分库分表

当单库或单表的数据量、吞吐量成为瓶颈时，才考虑分库分表。

它解决的问题：

- 单表数据过大。
- 单库连接数、CPU、IO 压力过高。
- 写入吞吐不足。

它带来的问题：

- 跨库事务复杂。
- 跨表查询、排序、分页复杂。
- 扩容、数据迁移、全局 ID 生成更复杂。

### 执行计划怎么看

查询慢题不要只写“建立索引”，可以补“通过执行计划定位原因”。

常见关注点：

- 是否走索引，还是全表扫描。
- 扫描行数是否过大。
- 是否出现临时表或文件排序。
- 关联查询的驱动表是否合适。
- 返回行数和过滤条件是否匹配。

答题句式：通过 `EXPLAIN` 分析 SQL 执行计划，查看访问类型、使用索引、扫描行数和排序方式，再针对性优化索引、SQL 和分页方式。

### 深分页优化

`limit offset, size` 在 offset 很大时会先扫描并丢弃大量记录，页数越深越慢。

常见优化：

- 基于上一页最后一个主键或时间做范围查询。
- 使用覆盖索引先查主键，再回表查询详情。
- 限制最大可翻页深度。
- 对复杂搜索交给 Elasticsearch 等搜索引擎。

例子：

```sql
select * from orders
where id > ?
order by id
limit 20;
```

这种方式适合按稳定排序字段连续翻页，但不适合任意跳页。

### 覆盖索引和回表

如果查询的字段都在索引中，数据库可以直接从索引返回结果，称为覆盖索引。

如果二级索引中只有索引字段和主键，还需要根据主键再回到聚簇索引读取完整记录，称为回表。

覆盖索引可以减少回表次数，适合高频列表查询。例如订单列表只展示订单号、状态、创建时间，可考虑建立匹配查询条件和展示字段的联合索引。

### 锁和并发问题

MySQL 并发问题常见表现：

- 更新同一行导致行锁等待。
- 大事务持锁时间长，阻塞其他事务。
- 索引不合适导致锁范围扩大。
- 事务隔离级别过高导致并发下降。

优化思路：

- 让事务尽量短，避免事务内做远程调用。
- 更新条件命中索引，减少锁范围。
- 按固定顺序更新资源，降低死锁概率。
- 对热点数据使用拆分、队列串行化或乐观锁。

### 主从延迟处理

读写分离后，刚写完马上读从库可能读到旧数据。

常见处理：

- 写后读主库，用于订单详情、支付结果等强一致读。
- 延迟一小段时间再读从库，适合一致性要求不高的页面。
- 根据主从延迟监控动态决定是否读主库。
- 关键业务返回写入结果，不依赖马上从库查询。

考试答读写分离时，必须补“主从延迟”和“强一致读走主库”。
