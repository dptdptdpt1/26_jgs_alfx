# MySQL

## 考试中一般怎么考

1. 查询慢：问如何通过索引、SQL 优化、分页优化提升查询性能。
2. 索引原理：问为什么索引能加快查询，联合索引为什么有最左前缀原则，索引为什么会失效。
3. 事务与隔离：问 ACID、隔离级别、脏读、不可重复读、幻读。
4. 读写分离：问主从复制如何提升读性能，以及主从延迟带来的问题。
5. 数据量过大：问分库分表、分区表、冷热分离的适用场景和代价。

## 针对考法梳理知识点

### 索引为什么能提升查询性能

MySQL 索引本质上是为数据建立额外的数据结构，常见 InnoDB 索引使用 B+ 树。没有索引时，数据库可能需要扫描大量数据行；有索引时，可以先在索引树上定位到目标范围，再回到数据页读取记录。

答题抓住三点：

- 索引减少扫描的数据量。
- B+ 树适合范围查询和排序。
- 索引不是越多越好，因为插入、更新、删除时也要维护索引。

### 联合索引和最左前缀

联合索引按多个字段的顺序组织。例如 `(a, b, c)`，索引先按 `a` 排，再按 `b` 排，再按 `c` 排。

因此查询条件从最左字段开始连续命中时，索引效果最好：

- `where a = ?` 可以用。
- `where a = ? and b = ?` 可以用。
- `where b = ?` 通常不能充分使用这个联合索引。
- `where a = ? and c = ?` 只能较好利用 `a`，中间断了 `b`。

### 索引失效常见原因

常考的不是背列表，而是能解释“为什么失效”：

- 对索引列做函数或表达式计算，数据库难以直接按索引有序结构定位。
- 隐式类型转换，可能导致索引列被转换后再比较。
- 前置模糊匹配，例如 `like '%abc'`，无法从 B+ 树左侧有序前缀定位。
- 联合索引没有从最左列开始使用。
- 范围查询后面的列，利用能力通常会下降。

### 事务和 ACID

事务用于保证一组数据库操作作为一个整体执行。

- 原子性：要么都成功，要么都失败。
- 一致性：事务前后数据满足业务约束。
- 隔离性：并发事务之间相互隔离。
- 持久性：提交后的结果可靠保存。

案例题里如果出现“扣库存、生成订单、扣款必须同时成功”，优先往事务、一致性、补偿机制上答。

### 隔离级别

隔离级别解决的是并发事务之间互相影响的问题。

- 读未提交：可能读到别人未提交的数据，即脏读。
- 读已提交：只能读到已提交数据，避免脏读。
- 可重复读：同一事务内多次读取结果保持一致，MySQL InnoDB 默认级别。
- 串行化：隔离最强，但并发性能最低。

考试里重点区分：

- 脏读：读到了未提交数据。
- 不可重复读：同一行数据前后读到的值不同。
- 幻读：同一条件前后读到的记录数量不同。

隔离级别和常见措施的关系：

| 措施 | 和隔离级别的关系 |
| --- | --- |
| 本地事务 | 隔离级别只在事务范围内生效，事务越长，锁等待和并发影响越大 |
| MVCC | 通过多版本读减少读写冲突，支撑读已提交、可重复读等隔离效果 |
| 行锁 / 间隙锁 | 用于控制并发写和范围冲突，隔离级别越高，锁范围和等待风险通常越大 |
| 唯一约束 | 防止重复数据，不能只依赖隔离级别判断“是否已存在” |
| 乐观锁 | 通过版本号或状态条件防止并发覆盖，适合库存、余额、状态流转等更新 |
| 幂等和补偿 | 解决重试、超时、消息重复等应用层问题，不由数据库隔离级别单独保证 |

答题时不要把所有并发问题都归结为“提高隔离级别”。

- 隔离级别解决事务间可见性问题。
- 唯一约束、锁、乐观锁用于控制重复写入和并发更新。
- 幂等、补偿用于处理重试、超时和异常恢复。

| **并发问题**   | **现象描述**                 | **核心触发动作**              | **解决协议**                 | **封锁操作细节**                                |
| -------------- | ---------------------------- | ----------------------------- | ---------------------------- | ----------------------------------------------- |
| **丢失修改**   | $T_2$ 覆盖了 $T_1$ 的修改    | `Update` 覆盖 `Update`        | **一级封锁**                 | 写前加 **X 锁**，事务结束才释放。               |
| **读脏数据**   | 读到了别人回滚前的数据       | `Read` 读到了未提交的 `Write` | **二级封锁**                 | 一级基础上，读前加 **S 锁**，**读完即放**。     |
| **不可重复读** | 同一事务内两次读到的内容不同 | `Update` / `Delete` 现有行    | **三级封锁**                 | 二级基础上，读前加 **S 锁**，**事务结束才放**。 |
| **幻读**       | 同一事务内两次读到的条数不同 | `Insert` / `Delete` 新行      | **两阶段封锁(2PL) / 间隙锁** | 锁住记录之间的**间隙（Gap）**，禁止插入。       |

### 主从复制和读写分离

读写分离的基本思路是主库负责写，从库负责读。主库把变更日志同步给从库，从库重放这些日志形成数据副本。

它解决的问题：

- 分担读请求压力。
- 提供数据副本。
- 主库故障时可以切换。

它带来的问题：

- 主从复制有延迟。
- 刚写入的数据如果马上读从库，可能读不到。
- 对强一致要求高的读请求，应读主库或等待复制完成。

### 分库分表

当单库或单表的数据量、吞吐量成为瓶颈时，才考虑分库分表。

它解决的问题：

- 单表数据过大。
- 单库连接数、CPU、IO 压力过高。
- 写入吞吐不足。

它带来的问题：

- 跨库事务复杂。
- 跨表查询、排序、分页复杂。
- 扩容、数据迁移、全局 ID 生成更复杂。

### 执行计划怎么看

查询慢题不要只写“建立索引”，可以补“通过执行计划定位原因”。

常见关注点：

- 是否走索引，还是全表扫描。
- 扫描行数是否过大。
- 是否出现临时表或文件排序。
- 关联查询的驱动表是否合适。
- 返回行数和过滤条件是否匹配。

答题句式：通过 `EXPLAIN` 分析 SQL 执行计划，查看访问类型、使用索引、扫描行数和排序方式，再针对性优化索引、SQL 和分页方式。

### 深分页优化

`limit offset, size` 在 offset 很大时会先扫描并丢弃大量记录，页数越深越慢。

常见优化：

- 基于上一页最后一个主键或时间做范围查询。
- 使用覆盖索引先查主键，再回表查询详情。
- 限制最大可翻页深度。
- 对复杂搜索交给 Elasticsearch 等搜索引擎。

例子：

```sql
select * from orders
where id > ?
order by id
limit 20;
```

这种方式适合按稳定排序字段连续翻页，但不适合任意跳页。

### 覆盖索引和回表

如果查询的字段都在索引中，数据库可以直接从索引返回结果，称为覆盖索引。

如果二级索引中只有索引字段和主键，还需要根据主键再回到聚簇索引读取完整记录，称为回表。

覆盖索引可以减少回表次数，适合高频列表查询。例如订单列表只展示订单号、状态、创建时间，可考虑建立匹配查询条件和展示字段的联合索引。

### 锁和并发问题

MySQL 并发问题常见表现：

- 更新同一行导致行锁等待。
- 大事务持锁时间长，阻塞其他事务。
- 索引不合适导致锁范围扩大。
- 事务隔离级别过高导致并发下降。

优化思路：

- 让事务尽量短，避免事务内做远程调用。
- 更新条件命中索引，减少锁范围。
- 按固定顺序更新资源，降低死锁概率。
- 对热点数据使用拆分、队列串行化或乐观锁。

### 主从延迟处理

读写分离后，刚写完马上读从库可能读到旧数据。

常见处理：

- 写后读主库，用于订单详情、支付结果等强一致读。
- 延迟一小段时间再读从库，适合一致性要求不高的页面。
- 根据主从延迟监控动态决定是否读主库。
- 关键业务返回写入结果，不依赖马上从库查询。

考试答读写分离时，必须补”主从延迟”和”强一致读走主库”。

### 关系型数据库和 NoSQL 怎么选

关系型数据库适合结构化数据、强事务、复杂查询和核心业务数据。例如订单、支付、用户、库存。

NoSQL 适合高并发、灵活结构、海量数据、弱事务或特定访问模型。例如缓存、日志、文档、行为数据、时序数据。

选择依据不是”哪个更先进”，而是业务是否需要事务、SQL 查询、强约束和一致性。

### OLTP 和 OLAP 怎么选

OLTP 面向在线交易，关注高并发、低延迟、事务一致性，典型场景是下单、支付、库存扣减。

OLAP 面向分析，关注复杂查询、历史数据、多维统计，典型场景是经营报表、用户行为分析。

如果题目说”白天业务库压力大，统计报表查询慢并影响交易”，应把分析负载从业务库拆出去，通过 ETL 或数据同步进入数据仓库、数据集市或 OLAP 引擎。

### 技术选型答题顺序

遇到”该选哪种数据库或中间件”，按这个顺序写：

1. 数据类型：结构化、文档、键值、时序、文件。
2. 访问模式：点查、范围查、全文检索、聚合分析、高频读写。
3. 一致性要求：强一致、最终一致、可丢弃、可补偿。
4. 数据规模：容量、增长速度、冷热特征。
5. 运维成本：备份、恢复、扩容、监控、迁移。

这样比直接写”用 MySQL/Redis/ES”更容易拿过程分。

### 表结构设计与范式

案例分析可能给出一个业务场景，要求设计或优化表结构。

核心步骤：

1. 识别实体和属性：从需求中提取核心实体（如用户、订单、商品、支付）及其属性。
2. 确定实体间联系：一对一、一对多、多对多，多对多需要中间表。
3. 确定主键和外键：主键唯一标识记录，外键体现实体间关系。
4. 规范化设计：至少满足第三范式，减少数据冗余和更新异常。
5. 适当反范式：对高频查询场景，可冗余统计字段、冗余名称字段，减少多表 JOIN。

答题模板：

> 首先进行概念结构设计，识别核心实体及实体之间的联系；然后进行逻辑结构设计，为每个实体确定主键、外键和属性；再通过规范化减少数据冗余和更新异常；对于高频查询场景，可适当进行反规范化设计，如冗余统计字段、冗余名称字段，以减少多表 JOIN，提高查询性能。

### 高并发场景实战

案例分析高频场景：库存超卖、重复下单、余额扣减异常。

**库存超卖**

```sql
update stock
set count = count - 1
where product_id = #{productId}
  and count > 0;
```

判断影响行数是否为 1，`count > 0` 条件能防止超卖。高并发下还可配合乐观锁（版本号）或悲观锁（`select ... for update`）。

**重复下单**

在订单表上建立业务唯一索引，如 `(user_id, product_id, activity_id)`，数据库层面防止重复插入。应用层同时做幂等校验。

**余额扣减**

```sql
update account
set balance = balance - #{amount}
where user_id = #{userId}
  and balance >= #{amount};
```

同样通过条件判断 + 影响行数校验保证安全。高并发场景可先在 Redis 预扣，再异步落库。

答题模板：

> 对库存扣减、余额变更等强一致性操作，应放在事务中执行。可以采用悲观锁 `select ... for update` 锁定库存行，或使用乐观锁版本号/CAS 方式更新。为防止重复下单，应增加业务唯一索引。高并发场景下可通过消息队列削峰，并结合库存预扣、异步确认、补偿机制保证最终一致性。

### 数据库高可用与容灾

可能问”数据库宕机如何保证系统可用”。

**高可用方案**

- 主从复制 + 自动故障转移：MHA、MGR（MySQL Group Replication）、InnoDB Cluster。
- 双主互备：两个节点互为主从，适合写入量不大的场景。
- 读写分离集群：一主多从，从库故障不影响读服务。

**备份恢复**

- 全量备份：定期完整备份数据库。
- 增量备份：基于 binlog 备份增量变更。
- 恢复演练：定期验证备份可恢复性，避免备份失效。

**异地容灾**

- 同城双活：两个机房同步复制，RPO 接近 0。
- 异地灾备：异步复制到异地，RPO 取决于复制延迟。

答题模板：

> 数据库高可用可采用主从复制、双主或集群方案，并结合自动故障检测和主从切换机制。数据安全方面，应建立全量备份、增量备份和 binlog 日志备份机制，定期进行恢复演练。对于核心业务，可采用同城双活或异地灾备方案，并明确 RPO 和 RTO 指标。

### 数据库安全设计

可能问”数据库如何防止泄露、越权、SQL 注入”。

- 最小权限原则：不同应用和人员分配不同账号，只授予必要权限。
- SQL 注入防护：使用预编译 SQL 或 ORM 参数绑定，禁止拼接 SQL。
- 敏感字段加密：身份证号、手机号、银行卡等加密存储或脱敏展示。
- 传输加密：数据库连接使用 SSL/TLS。
- 审计日志：记录数据库访问、变更和异常操作。
- 备份加密：备份文件也应加密保存，防止离线泄露。

答题模板：

> 数据库安全应遵循最小权限原则，为不同应用和人员分配不同账号和权限。应用层应使用预编译 SQL 或 ORM 参数绑定，防止 SQL 注入。对于敏感字段，应进行加密存储或脱敏展示。数据库访问、变更和异常操作应记录审计日志，备份文件也应加密保存。

### 缓存与 MySQL 一致性

从 MySQL 视角看缓存一致性，核心是”谁是权威数据源”。

MySQL 是权威数据源，Redis 是缓存。更新时先更新 MySQL，再删除 Redis 缓存。后续查询缓存未命中时，从 MySQL 重新加载。

常见问题和补救：

- 删除缓存失败 → 消息队列重试或延迟双删。
- 并发读写导致旧值回写 → 缓存设过期时间兜底。
- 主从延迟导致读到旧值 → 强一致读走主库。

答题模板：

> 查询时先查缓存，缓存未命中再查数据库，并将结果写入缓存。更新时先更新数据库，再删除缓存。对于高并发场景，可通过消息队列异步删除或更新缓存，并设置合理的过期时间作为兜底。

### 万能答题模板

**数据库性能优化**

> 数据库性能优化可以从表结构、索引、SQL、架构和运维几个方面进行。表结构方面应合理设计字段类型、主键和范式，必要时适当反范式。索引方面应为高频查询条件、排序字段和关联字段建立合适索引。SQL 方面应避免全表扫描、避免 `select *`、减少复杂 JOIN 和大分页。架构方面可采用缓存、读写分离、分库分表、冷热数据分离等方式。运维方面可通过慢查询日志、执行计划、监控告警和容量规划持续优化。

**高并发数据库设计**

> 高并发场景下，应减少数据库直接访问压力。读请求可通过 Redis 缓存和读写分离分担压力；写请求可通过消息队列削峰填谷，异步处理非核心流程。核心数据变更应使用事务保证一致性，并通过乐观锁、悲观锁或唯一索引防止并发冲突。对于大数据量表，应考虑水平分表、冷热数据分离和归档策略。

**MySQL 高可用**

> MySQL 高可用可通过主从复制、一主多从、自动故障转移和定期备份实现。主库负责写操作，从库负责读操作，以提高系统吞吐能力。当主库故障时，应由高可用组件自动选举或切换新的主库。为了防止数据丢失，需要开启 binlog，结合全量备份和增量备份进行恢复，并定期进行容灾演练。
