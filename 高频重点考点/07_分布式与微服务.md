# 分布式与微服务

## 考试中一般怎么考

1. 服务拆分：要求根据业务边界、数据归属、团队职责说明拆分理由。
2. 服务治理：问注册中心、配置中心、网关、熔断、降级、限流分别解决什么问题。
3. 分布式调用：问超时、重试、幂等、链路追踪的机制。
4. 分布式一致性：问 TCC、Saga、可靠消息、补偿、对账的适用场景。

## 针对考法梳理知识点

### 服务拆分不是越细越好

服务拆分的目标是让业务边界清楚、团队可以独立演进、服务可以独立部署。

常见拆分依据：

- 按业务能力拆分，一个服务负责相对完整的业务能力。
- 按领域边界拆分，服务边界尽量和领域模型一致。
- 按数据归属拆分，一个服务尽量管理自己的数据。
- 按变更频率拆分，经常变化的模块可以独立演进。

过细拆分会带来调用链变长、接口增多、分布式事务复杂、排查困难等问题。

### 服务拆分细化规则

服务边界可以按以下问题判断：

- 这个能力是否有相对独立的业务目标。
- 数据是否可以由一个服务负责，不被多个服务直接共享表。
- 变更频率是否和其他模块明显不同。
- 是否需要独立扩容或独立部署。
- 团队是否能独立负责该服务。

不适合拆成独立服务的情况：

- 只是几个简单函数，没有独立业务能力。
- 强依赖同一个事务，拆开后需要频繁分布式事务。
- 数据边界不清，多个服务需要直接改同一张表。
- 运维和监控能力还不足，拆分后治理成本超过收益。

### 注册中心解决什么问题

在单体系统中，模块地址通常是固定的。微服务中服务实例会扩容、下线、故障迁移，地址会变化。

注册中心的机制是：

1. 服务启动时把自己的地址注册到注册中心。
2. 调用方从注册中心获取可用实例列表。
3. 服务实例定期续约或发送心跳。
4. 注册中心发现实例失效后将其剔除。

它解决的是服务发现和实例动态变化问题。

### API 网关解决什么问题

网关位于客户端和后端服务之间，统一处理入口流量。

常考作用：

- 统一认证鉴权。
- 请求路由到不同后端服务。
- 限流、熔断、灰度发布。
- 协议转换和日志审计。

网关本身也可能成为瓶颈或单点，因此需要集群部署和负载均衡。

### 配置中心解决什么问题

配置中心把各服务的配置统一管理，例如数据库连接、开关、限流阈值、灰度策略。

它解决的是配置分散、变更难追踪、上线后难动态调整的问题。

常见机制：

1. 服务启动时从配置中心拉取配置。
2. 配置变更后通知服务刷新。
3. 配置中心记录版本和变更人，支持回滚。

配置中心本身要高可用，敏感配置要加密存储和控制访问权限。

### 超时、重试、幂等

分布式调用一定要设置超时。没有超时，调用方可能长期等待，线程和连接资源被耗尽。

重试可以提高临时故障下的成功率，但必须配合幂等。否则可能重复下单、重复扣款、重复发券。

幂等常见做法：

- 请求唯一 ID。
- 业务流水号。
- 数据库唯一约束。
- 去重表。
- 状态机控制。

### 熔断和降级

熔断是下游服务持续失败时，调用方暂时停止调用，直接快速失败或返回兜底结果，避免故障扩散。

降级是关闭非核心功能，保留核心链路。例如大促时关闭个性化推荐，保证下单支付正常。

两者区别：

- 熔断针对故障扩散。
- 降级针对资源不足或服务能力不足。

### 限流

限流控制进入系统或某个接口的请求量，避免流量超过系统承载能力。

常见位置：

- 网关层：保护整体入口。
- 服务层：保护核心服务。
- 用户或 IP 维度：防止单个调用方过量请求。

常见算法：

| 算法 | 特点 |
| --- | --- |
| 计数器 | 实现简单，但窗口边界可能突增 |
| 滑动窗口 | 比固定窗口更平滑 |
| 漏桶 | 按固定速率流出，流量更平稳 |
| 令牌桶 | 支持一定突发流量 |

### 负载均衡策略

负载均衡不只是“加一台负载均衡器”，还要说明分发策略和健康检查。

常见策略：

- 轮询：请求依次分配到各节点，实现简单。
- 加权轮询：性能更强的节点分配更多请求。
- 最少连接：优先分配给当前连接少的节点。
- 一致性哈希：适合缓存节点，减少节点变化带来的缓存迁移。
- 按地域或就近访问：降低网络延迟。

如果服务有状态，负载均衡会变复杂。应优先无状态化，或把 Session 放到共享存储。

### 链路追踪

微服务调用链长，单靠单个服务日志难以定位问题。

链路追踪通常为一次请求生成 Trace ID，在跨服务调用时继续传递，并记录每段调用的耗时、状态和依赖关系。

它解决的是故障定位、性能瓶颈分析和调用关系可视化问题。

### 分布式一致性

TCC 适合强业务一致性，业务要能拆成 Try、Confirm、Cancel 三个阶段。

Saga 适合长事务，每个步骤都有对应补偿操作。

可靠消息适合异步最终一致，例如订单创建后发送消息扣减积分。

本地消息表用于保证“本地业务操作”和“消息发送”要么都能被可靠推进。

定时对账用于允许延迟修复的场景，常作为最终兜底。

### 2PC、TCC、Saga 对比

| 方案 | 机制 | 适合 | 局限 |
| --- | --- | --- | --- |
| 2PC | 协调者先询问各参与者能否提交，再统一提交或回滚 | 强一致、参与方较少的场景 | 阻塞、性能差、协调者故障风险 |
| TCC | Try 预留资源，Confirm 确认，Cancel 取消 | 业务可拆成预留、确认、取消 | 业务侵入强，每个服务都要实现三阶段 |
| Saga | 多个本地事务串联，每步有补偿操作 | 长流程、最终一致 | 补偿不一定能完全抵消已发生影响 |
| 可靠消息 | 本地事务完成后可靠发送消息，消费者处理 | 异步最终一致 | 有延迟，需要幂等和补偿 |

考试选型时，支付扣款这类强一致链路不宜只写 Saga；通知、积分、日志这类异步场景不宜上 2PC。

### 幂等设计细化

幂等是同一个请求执行一次和执行多次的结果一致。

常见设计：

- 请求号：客户端或服务端生成唯一请求 ID，重复请求直接返回已有结果。
- 业务唯一键：订单号、支付流水号、退款单号唯一。
- 数据库唯一约束：从存储层防止重复插入。
- 状态机：只有合法状态才能流转，例如“待支付”才能变为“已支付”。
- 去重表：消费消息前先记录消息 ID，已处理则跳过。

重试、消息重复投递、接口超时后客户端再次提交，都必须考虑幂等。

### 服务治理答题清单

| 问题 | 机制 |
| --- | --- |
| 服务实例地址变化 | 注册中心、服务发现 |
| 配置分散、动态调整难 | 配置中心、版本和回滚 |
| 客户端入口复杂 | API 网关 |
| 下游服务慢或故障 | 超时、重试、熔断、隔离 |
| 高峰流量过大 | 限流、削峰、降级 |
| 调用链难排查 | 日志聚合、链路追踪、监控告警 |
| 跨服务数据一致 | TCC、Saga、可靠消息、补偿、对账 |

### 消息可靠投递和死信队列

消息队列常用于异步解耦，但必须回答“消息会不会丢、会不会重复、失败怎么办”。

可靠投递常见做法：

1. 生产者发送消息后等待 Broker 确认。
2. 业务数据和消息记录写入本地事务。
3. 后台任务扫描未发送或未确认消息并重试。
4. 消费者处理成功后再确认消息。
5. 消费失败按策略重试，超过次数进入死信队列。

死信队列保存多次消费失败、过期或无法路由的消息，便于告警、人工处理和补偿。
