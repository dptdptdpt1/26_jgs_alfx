# Redis

## 考试中一般怎么考

1. 缓存设计：问 Redis 为什么能降低数据库压力、提升响应速度。
2. 缓存异常：问缓存穿透、击穿、雪崩的原理和解决方案。
3. 缓存一致性：问数据库更新后如何处理 Redis 缓存。
4. Redis 高可用：问主从、哨兵、集群分别解决什么问题。
5. 分布式锁：问 Redis 如何实现分布式锁，以及为什么要设置过期时间。

## 针对考法梳理知识点

### Redis 在系统中的角色

Redis 常作为内存缓存层，放在应用和数据库之间。热点数据先查 Redis，命中后直接返回；未命中再查数据库，并把结果写入 Redis。

它解决的问题：

- 减少数据库访问压力。
- 缩短热点数据读取路径。
- 支持计数器、排行榜、分布式锁、会话等高频访问场景。

它不是权威数据源。核心业务数据通常仍以数据库为准，Redis 和数据库之间多采用最终一致。

### 缓存穿透

缓存穿透是指请求查询一个不存在的数据。Redis 中没有，数据库中也没有。如果大量这类请求直接打到数据库，会绕过缓存保护。

常用处理：

- 参数校验，拦截明显非法请求。
- 缓存空值，让不存在的数据短时间内也命中缓存。
- 使用布隆过滤器，先判断数据是否可能存在。

### 缓存击穿

缓存击穿是指某个热点 Key 过期，瞬间大量请求同时打到数据库。

常用处理：

- 互斥锁：只有一个请求回源数据库并重建缓存。
- 逻辑过期：缓存不物理删除，过期后异步刷新。
- 热点 Key 不设置普通过期时间，由后台任务更新。

击穿的关键是“单个热点 Key 失效”。

### 缓存雪崩

缓存雪崩是指大量 Key 同时失效，或 Redis 整体不可用，导致请求集中打到数据库。

常用处理：

- 给过期时间加随机值，避免同一时间集中失效。
- 多级缓存，降低 Redis 故障影响。
- 限流、降级，保护数据库。
- Redis 主从、哨兵、集群提升可用性。

雪崩的关键是“大面积失效或缓存层整体故障”。

### 缓存一致性

常见方案是“先更新数据库，再删除缓存”。原因是数据库是权威数据源，删除缓存后，后续请求会重新从数据库加载新值。

常见问题：

- 删除缓存失败，会留下旧缓存。
- 并发读写可能导致旧值被重新写回缓存。
- 主从数据库延迟时，读从库可能读到旧值。

常用补救：

- 设置缓存过期时间，作为最终兜底。
- 延迟双删，降低并发导致的不一致。
- 通过消息队列或订阅数据库变更删除缓存。

### Redis 高可用

主从复制：主节点写，从节点复制数据，提供读扩展和数据副本。

哨兵：监控主节点状态，主节点故障时自动选举新的主节点。

集群：把数据分片到多个节点，提升容量和吞吐，同时避免单机容量瓶颈。

考试区分：

- 主从解决副本和读扩展。
- 哨兵解决故障发现和自动切换。
- 集群解决数据分片和水平扩展。

### Redis 分布式锁

基本思路是利用 Redis 的原子写入能力，只有一个客户端能成功写入锁 Key。

常见写法强调：

- 使用 `SET key value NX EX seconds`。
- `NX` 保证不存在时才写入。
- `EX` 设置过期时间，避免持有锁的服务宕机后死锁。
- 释放锁时要校验 value，避免误删别人的锁。

### 常用数据结构怎么选

| 数据结构 | 常见用途 | 答题要点 |
| --- | --- | --- |
| String | 缓存对象、计数器、分布式锁 | 简单高效，适合单值 |
| Hash | 用户信息、商品信息 | 适合同一对象多个字段 |
| List | 简单队列、最新消息列表 | 可两端 push/pop |
| Set | 去重、共同好友、标签集合 | 元素不重复，支持集合运算 |
| ZSet | 排行榜、延迟队列 | 按分数排序 |
| Bitmap | 签到、在线状态 | 用 bit 压缩布尔状态 |
| HyperLogLog | UV 统计 | 近似去重计数，节省内存 |

考试里如果只是缓存对象，String 或 Hash 都可；如果题目强调排行榜，优先 ZSet；强调去重集合，优先 Set。

### 热 Key 和大 Key

热 Key 是少数 Key 被大量访问，可能导致某个 Redis 节点压力过高。

处理思路：

- 本地缓存或多级缓存分担访问。
- 热 Key 拆分成多个 Key。
- 提前识别热点并扩容。
- 对热点接口限流和降级。

大 Key 是单个 Key 对应的数据过大，例如一个 Hash 或 List 内元素过多。

风险：

- 读写阻塞 Redis 单线程。
- 网络传输大。
- 删除或过期时造成抖动。

处理思路：拆分 Key、分批读取、分批删除，避免把大量数据放在单个 Key 中。

### 内存淘汰和过期策略

Redis 过期删除不是所有 Key 到期立刻删除，通常结合惰性删除和定期删除。

- 惰性删除：访问 Key 时发现过期再删除。
- 定期删除：周期性抽样检查并删除过期 Key。
- 内存淘汰：内存不足时按配置策略淘汰 Key。

常见淘汰思路：

- 最近最少使用。
- 即将过期优先。
- 随机淘汰。
- 不淘汰，写入时报错。

缓存题如果出现“内存满了怎么办”，要写淘汰策略、容量监控、热点数据保护和数据重建机制。

### 分布式锁常见坑

- 锁过期时间太短，业务没执行完锁就释放。
- 释放锁时不校验 value，误删其他线程的锁。
- 获取锁失败后无限重试，放大系统压力。
- Redis 主从切换时，锁状态可能丢失。

对强一致要求极高的场景，不要轻易把 Redis 锁当作唯一保护手段。关键约束仍应通过数据库唯一约束、状态机或事务校验兜底。
