# Redis

## 考试中一般怎么考

1. 缓存设计：问 Redis 为什么能降低数据库压力、提升响应速度。
2. 缓存异常：问缓存穿透、击穿、雪崩的原理和解决方案。
3. 缓存一致性：问数据库更新后如何处理 Redis 缓存。
4. Redis 高可用：问主从、哨兵、集群分别解决什么问题。
5. 分布式锁：问 Redis 如何实现分布式锁，以及为什么要设置过期时间。

## 针对考法梳理知识点

### Redis 典型使用场景

| 场景 | 说明 |
| --- | --- |
| 缓存 | 用户信息、商品详情、字典表、首页热点、权限菜单 |
| 会话/Token | 登录态、JWT Token、验证码 |
| 计数器 | 访问量、点赞数、库存扣减（String + INCR/DECR） |
| 排行榜 | 热度榜、积分榜（ZSet） |
| 分布式锁 | 秒杀防重复下单、定时任务防重（SET NX EX） |
| 消息队列 | 简单任务队列（List）、可靠消息（Stream） |
| 去重与集合运算 | 共同好友、标签集合（Set） |
| 签到与状态 | 用户签到、在线状态（Bitmap） |
| UV 统计 | 大规模去重计数（HyperLogLog） |

### Redis 在系统中的角色

Redis 常作为内存缓存层，放在应用和数据库之间。热点数据先查 Redis，命中后直接返回；未命中再查数据库，并把结果写入 Redis。

它解决的问题：

- 减少数据库访问压力。
- 缩短热点数据读取路径。
- 支持计数器、排行榜、分布式锁、会话等高频访问场景。

它不是权威数据源。核心业务数据通常仍以数据库为准，Redis 和数据库之间多采用最终一致。

### Redis 为什么快

案例题可能问"为什么用 Redis"，需要答清楚原因：

- 基于内存操作，读写延迟极低。
- 单线程模型避免线程切换和锁竞争（网络 IO 在新版有多线程优化，但命令执行仍是单线程）。
- IO 多路复用机制，单线程可处理大量并发连接。
- 高效的底层数据结构（SDS、ziplist、skiplist 等）。
- 命令执行简单，多数操作时间复杂度为 O(1)。

### 缓存穿透

缓存穿透是指请求查询一个不存在的数据。Redis 中没有，数据库中也没有。如果大量这类请求直接打到数据库，会绕过缓存保护。

常用处理：

- 参数校验，拦截明显非法请求。
- 缓存空值，让不存在的数据短时间内也命中缓存。
- 使用布隆过滤器，先判断数据是否可能存在。
- 接口限流，控制请求频率，防止恶意请求打垮数据库。

### 缓存击穿

缓存击穿是指某个热点 Key 过期，瞬间大量请求同时打到数据库。

常用处理：

- 互斥锁：只有一个请求回源数据库并重建缓存。
- 逻辑过期：缓存不物理删除，过期后异步刷新。
- 热点 Key 不设置普通过期时间，由后台任务更新。

击穿的关键是“单个热点 Key 失效”。

### 缓存雪崩

缓存雪崩是指大量 Key 同时失效，或 Redis 整体不可用，导致请求集中打到数据库。

常用处理：

- 给过期时间加随机值，避免同一时间集中失效。
- 热点数据提前预热，在活动开始前加载到缓存。
- 多级缓存，降低 Redis 故障影响。
- 限流、降级，保护数据库。
- Redis 主从、哨兵、集群提升可用性。

雪崩的关键是“大面积失效或缓存层整体故障”。

### 缓存一致性

常见方案是“先更新数据库，再删除缓存”。原因是数据库是权威数据源，删除缓存后，后续请求会重新从数据库加载新值。

常见问题：

- 删除缓存失败，会留下旧缓存。
- 并发读写可能导致旧值被重新写回缓存。
- 主从数据库延迟时，读从库可能读到旧值。

常用补救：

- 设置缓存过期时间，作为最终兜底。
- 延迟双删，降低并发导致的不一致。
- 通过消息队列或订阅数据库变更删除缓存。

### Redis 高可用

主从复制：主节点写，从节点复制数据，提供读扩展和数据副本。

哨兵：监控主节点状态，主节点故障时自动选举新的主节点。

集群：把数据分片到多个节点，提升容量和吞吐，同时避免单机容量瓶颈。

考试区分：

- 主从解决副本和读扩展。
- 哨兵解决故障发现和自动切换。
- 集群解决数据分片和水平扩展。

### Redis 分布式锁

基本思路是利用 Redis 的原子写入能力，只有一个客户端能成功写入锁 Key。

常见写法强调：

- 使用 `SET key value NX EX seconds`。
- `NX` 保证不存在时才写入。
- `EX` 设置过期时间，避免持有锁的服务宕机后死锁。
- value 设置唯一标识（如 UUID），释放锁时用 Lua 脚本先校验 value 再删除，保证判断和删除的原子性，避免误删别人的锁。
- 高可靠场景可使用 Redisson，它内置看门狗机制自动续期，避免业务未执行完锁就过期。

### 常用数据结构怎么选

| 数据结构 | 常见用途 | 答题要点 |
| --- | --- | --- |
| String | 缓存对象、计数器、分布式锁 | 简单高效，适合单值 |
| Hash | 用户信息、商品信息 | 适合同一对象多个字段 |
| List | 简单队列、最新消息列表 | 可两端 push/pop |
| Set | 去重、共同好友、标签集合 | 元素不重复，支持集合运算 |
| ZSet | 排行榜、延迟队列 | 按分数排序 |
| Bitmap | 签到、在线状态 | 用 bit 压缩布尔状态 |
| HyperLogLog | UV 统计 | 近似去重计数，节省内存 |
| Stream | 消息队列 | 支持消费组、消息确认、持久化，比 List/Pub/Sub 更可靠 |

考试里如果只是缓存对象，String 或 Hash 都可；如果题目强调排行榜，优先 ZSet；强调去重集合，优先 Set。

### 热 Key 和大 Key

热 Key 是少数 Key 被大量访问，可能导致某个 Redis 节点压力过高。

处理思路：

- 本地缓存或多级缓存分担访问。
- 热 Key 拆分成多个 Key。
- 提前识别热点并扩容。
- 对热点接口限流和降级。

大 Key 是单个 Key 对应的数据过大，例如一个 Hash 或 List 内元素过多。

风险：

- 读写阻塞 Redis 单线程。
- 网络传输大。
- 删除或过期时造成抖动。

处理思路：拆分 Key、分批读取、分批删除，避免把大量数据放在单个 Key 中。

### 内存淘汰和过期策略

Redis 过期删除不是所有 Key 到期立刻删除，通常结合惰性删除和定期删除。

- 惰性删除：访问 Key 时发现过期再删除。
- 定期删除：周期性抽样检查并删除过期 Key。
- 内存淘汰：内存不足时按配置策略淘汰 Key。

常见淘汰思路：

- 最近最少使用。
- 即将过期优先。
- 随机淘汰。
- 不淘汰，写入时报错。

缓存题如果出现”内存满了怎么办”，要写淘汰策略、容量监控、热点数据保护和数据重建机制。

### Redis 持久化

案例题可能问”Redis 宕机后数据是否丢失”，需要答清楚持久化机制。

**RDB（快照持久化）**

- 定期将内存数据生成快照写入磁盘。
- 恢复速度快，适合备份和灾难恢复。
- 缺点是两次快照之间的数据可能丢失。

**AOF（追加日志持久化）**

- 记录每次写操作命令，追加写入日志文件。
- 数据安全性更高，可配置同步策略（每次写/每秒/系统决定）。
- 缺点是文件体积较大，恢复速度相对慢。

**混合持久化**

- 生产环境常用 RDB + AOF 混合模式。
- AOF 重写时先写 RDB 格式，再追加增量 AOF 日志。
- 兼顾恢复速度和数据可靠性。

答题模板：

> Redis 可开启 RDB 和 AOF 持久化机制。RDB 恢复速度快但可能丢失最近数据；AOF 数据可靠性更高但文件较大。生产环境可采用混合持久化，在性能和可靠性之间取得平衡。

### Redis 用作消息队列

Redis 可以实现简单的消息通信，但不同方式差异大：

| 方式 | 特点 | 适用场景 |
| --- | --- | --- |
| List（LPUSH + BRPOP） | 简单队列，不支持消费组 | 点对点简单任务队列 |
| Pub/Sub | 消息不持久化，消费者离线会丢消息 | 实时通知、事件广播 |
| Stream | 支持消费组、消息确认、持久化 | 需要可靠投递的消息队列 |

答题模板：

> Redis 可通过 List、Pub/Sub 或 Stream 实现消息通信。若要求消息可靠性和消费确认，优先使用 Stream；若只是简单通知，可使用 Pub/Sub，但其不保证离线消息可靠投递。

### 秒杀系统中的 Redis

秒杀是架构师案例分析高频场景，Redis 在其中承担关键角色：

秒杀的核心挑战：瞬时高并发、库存超卖、重复下单、数据库压力。

Redis 的作用：

- 缓存商品和库存信息，减少数据库查询。
- 预扣库存：用 INCR/DECR 或 Lua 脚本原子扣减，防止超卖。
- 分布式锁：防止重复下单。
- 限流：控制进入后端的请求量。
- 异步削峰：扣减成功后写入消息队列，后台异步创建订单。

典型流程：

```
活动开始前：库存预加载到 Redis
用户请求 → 限流 + 资格校验 → Redis 原子扣库存
扣减成功 → 写入消息队列 → 后台异步创建订单 → 最终落库
扣减失败 → 直接返回售罄
```

答题模板：

> 秒杀场景下，可将库存预加载到 Redis，利用 Lua 脚本保证扣减库存的原子性；请求成功后写入消息队列异步创建订单，从而削峰填谷，保护数据库。

### 分布式锁常见坑

- 锁过期时间太短，业务没执行完锁就释放。
- 释放锁时不校验 value，误删其他线程的锁。
- 获取锁失败后无限重试，放大系统压力。
- Redis 主从切换时，锁状态可能丢失。

对强一致要求极高的场景，不要轻易把 Redis 锁当作唯一保护手段。关键约束仍应通过数据库唯一约束、状态机或事务校验兜底。
