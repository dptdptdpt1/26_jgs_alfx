# 层次式架构设计

> 重要程度：P1  
> 考纲定位：案例分析典型架构之一，常用于信息系统和应用系统设计。

## 优先掌握

1. 表现层、应用层、业务层、数据访问层、数据层的职责。
2. 层间依赖规则和接口隔离。
3. 二层、三层、四层架构的区别。
4. 分层如何提升可维护性、可修改性和可测试性。

## 概念和场景

| 重要度 | 层 | 概念解释 | 场景式解释 |
| --- | --- | --- | --- |
| P0 | 表现层 | 负责界面展示和用户交互 | Web 页面收集查询条件并展示结果 |
| P0 | 应用层 | 编排用例和流程 | 下单用例协调库存、优惠、支付 |
| P0 | 业务层 | 封装核心业务规则 | 判断订单是否可取消、价格如何计算 |
| P0 | 数据访问层 | 屏蔽数据库访问细节 | 通过 DAO/Repository 查询订单表 |
| P0 | 数据层 | 存储和管理数据 | MySQL、Redis、文件存储等 |
| P1 | 接口层 | 对外暴露服务接口 | App、第三方系统通过 API 调用业务能力 |

## 分层设计规则

1. 上层依赖下层，下层不要反向依赖上层。
2. 跨层访问要受控，表现层不要直接访问数据库。
3. 业务规则放业务层，不要散落在页面或 SQL 中。
4. 层与层通过接口或 DTO 交互，避免内部模型泄露。
5. 公共能力如认证、日志、异常处理可作为横切机制统一处理。

## 常见场景

| 场景 | 设计 |
| --- | --- |
| 业务规则经常变化 | 规则集中在业务层，表现层只做展示。 |
| 多端接入 | Web、App、小程序共用应用服务或接口层。 |
| 数据库可能替换 | 数据访问层封装 SQL 和存储差异。 |
| 系统难测试 | 分层解耦，业务层可单独测试。 |

## 易混点

| 易混项 | 区分 |
| --- | --- |
| 应用层 vs 业务层 | 应用层编排流程；业务层表达规则和领域逻辑。 |
| 数据访问层 vs 数据层 | 数据访问层是代码封装；数据层是数据库、缓存和存储。 |
| MVC vs 分层架构 | MVC 主要组织界面交互；分层架构组织整个系统职责。 |

## 边界

不展开具体框架目录结构；案例题重点是职责划分、依赖方向和质量属性收益。
